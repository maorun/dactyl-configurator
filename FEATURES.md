## Keymap and Actions

### Key Pairs (`userKeyPairs`)

- A key pair holds two HID action codes (standard keys and modifiers `1..255`, media keys `0x120..0x126`, Mac Globe / Fn `0x127`, mouse actions `0x130..0x134`). It is pressed first-then-second and released in reverse order. It works as a tap action and as a hold action, also for combo candidates.
- The app stores the list in `keyPairs` (`{ first, second }`, max. 16); `server.py` renders it between `[[[START_KEY_PAIRS]]]` / `[[[END_KEY_PAIRS]]]`. Layer, mouse movement, pair, macro, umlaut, and one-shot codes are rejected as members.
- Commands: `CLEAR_PAIRS`, `ADD_PAIR <first> <second>` (appends the next index), `SAVE_PAIRS` (NVS keys `num_pairs`, `pairs_data`). A persisted count of `0` overrides the compiled-in list at boot. An unassigned index sends nothing.
- When `loadKeymapFromNVS()` applies new app defaults over a stored keymap, it removes `num_pairs`/`pairs_data`, because the new keymap references the compiled-in pairs. A plain repository flash keeps the stored pairs.
- `CLEAR_PAIRS` first releases every pair that is held at the host; the physical release of that key then sends nothing.
- Every pair can be deleted in the app. Keys reference pairs by index, so `removeKeyPairAt` renumbers the references in all layers (tap, hold, double-tap) and in combo actions: references to the deleted pair become `NONE`, higher indices move down by one. The deletion is a snapshot pending change; the next full sync sends the renumbered keys (`SET_K`) and the new pair list.

### Mouse movement (`ACT_MOUSE_UP` .. `ACT_MOUSE_RIGHT_MOVE`)

- Codes `0x135` (up), `0x136` (down), `0x137` (left), `0x138` (right) in `DactylCommon.h`; names `MOUSE_UP`, `MOUSE_DOWN`, `MOUSE_LEFT_MOVE`, `MOUSE_RIGHT_MOVE` in `js/keycodes.js` and `server.py`. The picker group "Maus-Aktionen" lists them.
- A held key moves the pointer. `mouseMoveTick()` runs in `processDeferredKeys()` and sends one step each `MOUSE_MOVE_INTERVAL_MS` (10 ms) through `bleKeyboard.mouseMove(x, y)` (Report ID 3). The step grows with the hold time: `1 + held / MOUSE_MOVE_ACCEL_MS` (80 ms), at most `MOUSE_MOVE_MAX_STEP` (16). The release stops the movement at once; a new press starts again at step 1. Held keys add up (up + right = diagonal); the sum is limited to `-127..127`.
- Works as tap, hold and double-tap action and as a buffered combo candidate (the movement starts when the combo window ends). A combo that consumes the key stops its movement. Without a Mac connection or in config mode nothing is sent and the acceleration restarts at step 1 (no jump to full speed after the reconnect); the key release still ends the movement. Entering the config mode clears all movement (`resetMouseMove`). The left half queues a step like a diagnostic event (at most half full), so 100 steps per second never take the room of a key release.
- `ADD_COMBO` with a movement code returns `ERR ARGS`; the app import rejects it too (`validateConfigShape`).
- Not a combo action (`ADD_COMBO` movement is not executed; `server.py` and the app reject it), and not repeatable (`isRepeatableAction`).
- The left half sends the movement as `SPLIT_OP_MOUSE_MOVE` (op 25, `arg` = X step, `code` low byte = Y step as int8; `(0, 0)` and `-128` are invalid). The master calls `mouseMove` on its BLE HID connection without any held state. The op is never retried (`splitEventRetryable`): a duplicate would jump twice, a lost step goes unnoticed. `DACTYL_FW_VERSION` 6 added it: flash both halves.

### Mouse precision and turbo keys (`ACT_MOUSE_SLOW`, `ACT_MOUSE_FAST`)

- Codes `0x13B` (`MOUSE_SLOW`) and `0x13C` (`MOUSE_FAST`) in `DactylCommon.h`; same names in `js/keycodes.js` and `server.py`. The picker group "Maus-Aktionen" lists them. Tests compare the codes.
- While `MOUSE_SLOW` is held, `mouseMoveTick()` and `wheelHoldTick()` cap the step at 1 without acceleration. While `MOUSE_FAST` is held, `mouseMoveTick()` uses `MOUSE_MOVE_MAX_STEP` from the first tick. If both or neither are held, the standard acceleration applies (`effectiveMouseSpeed()`). `MOUSE_FAST` does not change the wheel step.
- The keys run through the same path as the movement keys (`isMouseMoveAction()`, `mouseMoveStart()` and `mouseMoveStop()`), but move nothing themselves. They work as tap, hold and double-tap action and as a buffered combo candidate. They are not a combo action and not repeatable; `ADD_COMBO`, `server.py` and the app import reject them like a movement key.
- Across the split link: each half reports its held keys with `SPLIT_OP_MOUSE_SPEED` (op 31, both directions, `code` bit 0 = `MOUSE_SLOW`, bit 1 = `MOUSE_FAST`, `arg` 0, `code` > 3 is invalid). The packet carries the whole state, so the newest one wins. The sender sends it at each change and each `SPLIT_LAYER_REFRESH_MS` while it holds a key. The receiver keeps the mirror (`remoteMouseSpeed`) and lets it expire after `MOUSE_SPEED_REMOTE_TIMEOUT_MS` (3 s) without a packet, at `RELEASE_ALL` of the left half, at link loss and at host loss. No HID effect, no activity, retried like `SPLIT_OP_OSL`.
- After a change the sender sends one more copy after `SPLIT_LAYER_REPEAT_MS`, so a lost release packet does not hold the speed until the timeout. A `RELEASE_ALL` of the left half clears the mirror on the master; if the left half still holds `MOUSE_SLOW` (link recovery), the next refresh restores it within `SPLIT_LAYER_REFRESH_MS` (1 s).
- `DACTYL_FW_VERSION` is 35. Flash both halves: an old half ignores the op, so a key on the other half has no effect on the pointer speed.

### Horizontal scroll and held wheel keys (`ACT_MOUSE_WHEEL_LEFT`, `ACT_MOUSE_WHEEL_RIGHT`)

- Codes `0x139` (left) and `0x13A` (right) in `DactylCommon.h`; names `MOUSE_WHEEL_LEFT`, `MOUSE_WHEEL_RIGHT` in `js/keycodes.js` and `server.py`. The pickers list them next to the wheel keys.
- The mouse report (Report ID 3) has 5 bytes: buttons, X, Y, wheel and **AC Pan** (usage `0x0238`, Consumer page, one signed byte). `bleKeyboard.mousePan(step)` sends a positive step to the right. `dactylBuildMouseReport()` (`DactylHidDescriptor.h`) builds the bytes, so the unit tests check them.
- A wheel key (`MOUSE_WHEEL_UP`, `MOUSE_WHEEL_DOWN`, left, right) sends one step at the press. When the key stays held, `wheelHoldTick()` (in `processDeferredKeys()`) sends a step each `WHEEL_REPEAT_INTERVAL_MS` (40 ms) after `WHEEL_REPEAT_DELAY_MS` (300 ms). The step grows from 1 by 1 each `WHEEL_ACCEL_MS` (400 ms) of extra hold time, at most `WHEEL_MAX_STEP` (8). The release stops the repeat at once; a new press starts at step 1.
- Without a Mac connection or in config mode nothing is sent and the acceleration restarts. A combo that consumes the key, `resetMouseMove()` (config mode) and the key release stop the repeat.
- The keys work as tap, hold and double-tap action, as buffered combo candidate, as combo action (one step), in key pairs (one step at the press), and with `REPEAT`. `ALT_REPEAT` maps left to right and the reverse.
- Macros do not accept wheel or pan steps.
- The left half sends a pan step as `SPLIT_OP_MOUSE_SCROLL` with `code` 1 (`code` 0 = wheel, `arg` = step). The op is never retried. `isValidSplitHidEvent` accepts only `code` 0 and 1.
- **Pair again on macOS.** The report map changed (see "Consumer report and macOS system keys"). Both features share one report map change, so macOS needs one new pairing.

### Consumer report and macOS system keys (`ACT_MEDIA_BRIGHTNESS_UP` .. `ACT_MEDIA_LAUNCHPAD`)

- The Consumer report (Report ID 2, `MEDIA_KEYS_ID`) is 24 bits wide: 20 single-bit usages and 4 bits of padding. `MediaKeyReport` has 3 bytes; `mediaReportBits()` reads it as one mask.
- The existing 16 usages keep bit 0 .. 15 (Next 1, Previous 2, Stop 4, Play/Pause 8, Mute 16, Vol+ 32, Vol- 64, Globe `0x0400`). The new usages take bits 16 .. 19: Display Brightness Increment (`0x006F`, `0x010000`), Display Brightness Decrement (`0x0070`, `0x020000`), AC Desktop Show All Windows = Mission Control (`0x029F`, `0x040000`) and AC Desktop Show All Applications = Launchpad (`0x02A2`, `0x080000`).
- Codes `0x128` .. `0x12B` (`ACT_MEDIA_BRIGHTNESS_UP`, `ACT_MEDIA_BRIGHTNESS_DOWN`, `ACT_MEDIA_MISSION_CONTROL`, `ACT_MEDIA_LAUNCHPAD`); names `MEDIA_BRIGHTNESS_UP`, `MEDIA_BRIGHTNESS_DOWN`, `MEDIA_MISSION_CONTROL`, `MEDIA_LAUNCHPAD`. `isMediaAction()` and `mediaKeyForAction()` in `DactylLogic.h` map an action to its report; all paths (key, combo, key pair, repeat, macro) use them.
- Key pairs accept the new codes and the pan codes (`isValidKeyPairMemberCode`, `isKeyPairMember`, `KEY_PAIR_ALLOWED_ACTIONS`).
- Macros accept every Consumer key, the old ones too (Globe, Play/Pause, ...). A step is `{ type, code: 0, ms: <action code> }` on the wire: `MacroStep.code` stays 0 and `ms` carries the action (`0x120` .. `0x12B`). The app keeps `{ type, code: "MEDIA_LAUNCHPAD" }`; `macroStepTuple()` and `macroTupleActionNumber()` convert in both directions (`ADD_MACRO_STEP 1 0 299`, `MACRO_DATA`). `server.py` writes the same form (`MACRO_CONSUMER_CPP`). Mouse and pan stay invalid as macro steps. The dynamic macro records only keyboard codes.
- Split: the 20-bit mask goes over the air as `code` (bits 0 .. 15) and `arg` (bits 16 .. 19) of the `MEDIA_*` ops. `arg` outside `0 .. 15` is invalid. `makeSplitMediaEvent()` and `splitMediaEventBits()` convert.
- `DACTYL_FW_VERSION` is 28. Flash both halves: an old half cannot read the new `arg` and the new macro steps.
- **Pair again on macOS.** macOS caches the HID report map (see `AGENTS.md`, "macOS Bluetooth GATT Report Map Caching"). After the flash: (1) open the Bluetooth settings of macOS, (2) forget the keyboard ("Dieses Gerät ignorieren..."), (3) put the keyboard into pairing mode and pair it again. Without the new pairing, the old report map stays and the new keys do nothing.

### Key overrides (`userKeyOverrides`)

- A modifier plus a key gives another key, for example `Shift` + `Backspace` = `Delete` without `Shift`. The key alone stays unchanged. The list lives only on the master (right half) and applies to both halves, because only the master sees the modifiers of both halves.
- An entry is `{ mods, key, replacement, layerMask }`. `mods` is a bit mask of modifier classes (`KEY_OVERRIDE_MOD_CTRL` 1, `SHIFT` 2, `ALT` 4, `GUI` 8; left and right count the same). `key` and `replacement` are keyboard codes `1..255` and no modifier. `layerMask` (`1..255`, default `0xFF`) has bit `i` set when the override applies on layer `i`. At most 16 entries (`MAX_KEY_OVERRIDES`). The app stores them in `keyOverrides` (`{ mods: ["shift"], key, replacement }`, plus `layerMask` when it is not `0xFF`); `server.py` renders them between `[[[START_KEY_OVERRIDES]]]` / `[[[END_KEY_OVERRIDES]]]` in `dactyl_right.ino`. A config for the left half with a non-empty list returns an error.
- Logic: `SplitArbitratedKeyboard` (`DactylSplitHid.h`) checks the table in `press()` and `leftKeyPress()`. `keyOverrideFind` (`DactylKeyOverride.h`) needs all `mods` classes held and the active layer (`getActiveLayer`, passed with `setKeyOverrides`) in `layerMask`; with several matches the entry with the most modifiers wins, then the earlier entry. Only explicit modifier keys count; the implicit `Shift` of a shifted character (`!`) does not, so a key never overrides itself.
- A match releases the held modifiers of the required classes, presses `replacement` and sends both in one report (`beginReportBatch`). The release of the key releases `replacement` and presses the modifiers again, if a half still holds them. A modifier that was released before the key is not pressed again. Modifiers of other classes stay in the report. The override does not use or consume a One-Shot modifier.
- State per key and half (`ovrRight`, `ovrLeft`): the replacement and the released modifiers. `releaseAll()` of the right half keeps an active left override (`pressSet` presses the replacement, not the key). `splitResetForHostLoss()` clears the state.
- Commands: `CLEAR_OVERRIDES`, `ADD_OVERRIDE <mods 1..15> <key> <replacement> [<mask 1..255>]` (appends the next index; without a mask all layers apply; `ERR ARGS` for a wrong value, a modifier code or a full list), `SAVE_OVERRIDES` (NVS keys `num_ovr`, `ovr_v2`: 4 bytes per entry with the layer mask; the old `ovr_data` with 3 bytes per entry stays readable and counts as all layers; a save removes `ovr_data`). A persisted count of `0` overrides the compiled-in list at boot. `saveKeyOverridesToNVS` writes the data first and the count last. If the data write fails, the old count stays, no longer matches the stored length and the load keeps the compiled-in list; the command answers `ERR NVS SAVE_OVERRIDES` and the app stops the sync. A stored entry that is not valid is ignored. When `loadKeymapFromNVS()` applies new app defaults over a stored keymap, it removes `num_ovr`/`ovr_v2`/`ovr_data`. Only the master compiles the commands (`DACTYL_KEY_OVERRIDES` in `dactyl_right.ino`); the left half answers `ERR UNKNOWN`.
- `GET_CONFIG` (master only) sends `OVERRIDE_COUNT:<n>` and `OVERRIDE_DATA:{"o":<offset>,"e":[[mods,key,replacement,layerMask],...]}` (6 per line; firmware before version 40 sends three values, the app reads them as all layers) between the key pairs and the macros. A device without the count (left half, or `DACTYL_FW_VERSION` below 7) has nothing to compare; an unfinished block makes the list state `incomplete`.
- The app (`js/key-overrides-ui.js`, card "Tasten-Überschreibungen" in the combo tab) is visible only for the master profile (`profile.master`). The full sync sends the list after the key pairs (`CLEAR_OVERRIDES`, `ADD_OVERRIDE`, `SAVE_OVERRIDES`). A device that answers `ERR UNKNOWN CLEAR_OVERRIDES` skips the phase with a flash hint. The layout diff lists the differences as "Überschreibung <n>".
- Every source of a key press counts: a macro, a key pair or a Mod-Tap hold that holds a modifier and then presses a covered key triggers the override too. The replacement is the key that goes to the host, so One-Shot modifiers and Caps Word act on the replacement and are consumed as for a normal key.
- If a replacement is already held by another input (the other half, or another override), its release waits for the last holder. A replacement that sets a shifted character (`A`) gives back a held `Shift` after its release.
- The layer mask needs `DACTYL_FW_VERSION` 40. The app card has a checkbox per layer; the table and the layout diff add "(Ebene 0, 2)" for a restricted entry. Both halves share the version, so the app hint "Beide Hälften flashen" appears until both halves run it. Only the master needs the code; the left half gets no list. An old master skips the sync phase with a flash hint.

### Macros (`userMacros`)

- A macro is a list of at most 32 steps (`MacroStep { type, code, ms }`, 4 bytes): `tap` (press, release in the next step), `down` (press and hold), `up` (release) with a keyboard code `1..255`, and `pause` with `1..5000` ms. Max. 16 macros. Codes in `DactylCommon.h` (`ACT_MACRO_BASE`, `MACRO_STEP_*`), `server.py` (`MACRO_STEP_TYPES`) and `js/keycodes.js` must match; tests compare them.
- Non-blocking: `startMacro()` sends the first step on press; `macroTick()` in `processDeferredKeys()` sends at most one HID event per `loop()` pass, with `MACRO_STEP_GAP_MS` (5 ms) between two events. At the end, every code that a `down` step still holds is released. A `pause` as the last step runs to its end before the macro ends. Only one macro runs at a time; a press while a macro runs (also of another macro key) starts nothing. The key release sends nothing. Each executed step resets `lastActivityTime`, so standby does not slow a long macro.
- Works as tap, hold and double-tap action and as a buffered combo candidate. Combos do not support macros: `ADD_COMBO` rejects macro codes, `server.py` and `validateConfigShape` reject them as combo actions. Macros are not key pair or step members.
- Cancel: `CLEAR_MACROS`, `ADD_MACRO`, `ADD_MACRO_STEP` and deep sleep (right) release the open codes; a triggered combo, the config combo, config mode entry, deep sleep (left) and `restartEspNow` stop the macro before their `releaseAll()`. Without a host connection or in config mode, `macroTick` ends the macro without sending (like every key).
- Left half: `MACRO_OUTPUT_READY()` is `queueHasRoomForMacro(sendQueue)` (`DactylLeftLogic.h`). A step waits while fewer than `MACRO_QUEUE_RESERVE` (16) of the 64 queue entries are free, so a long macro never drops an event and never takes the room of the user's own keys.
- Known limit: an `up` step of a modifier also releases it at the host when the user holds the same modifier physically.
- Commands: `CLEAR_MACROS`, `ADD_MACRO` (appends an empty macro, `OK ADD_MACRO <idx>`), `ADD_MACRO_STEP <type> <code> <ms>` (appends to the last macro, `OK ADD_MACRO_STEP <idx> <n>`; one step per command because lines are limited to 256 characters), `SAVE_MACROS`. Invalid values return `ERR ARGS`. The app syncs macros after the key pairs; firmware without macros answers `ERR UNKNOWN CLEAR_MACROS`, and the app shows a flash hint and skips the phase.
- NVS: `num_macros`, `macro_lens` (one byte per macro) and `macros_data` (only the used steps, packed). A persisted count of `0` overrides the compiled-in list; data with a wrong length is ignored. `saveMacrosToNVS()` removes `num_macros` first and writes it last, only after `macro_lens` and `macros_data` succeeded: an interrupted or failed write loads the compiled-in macros at the next boot, never a mix; the previously stored set is lost in that case (accepted trade-off, the app syncs the full list again). New app defaults over a stored keymap remove the three keys (like key pairs). Full macros need about 66 of about 500 NVS entries (`min_spiffs`, 20 KB). The `STATUS` line of both halves shows `NvsUsed=<n> NvsFree=<n>`.
- `server.py` renders `macros` (`[{ name, steps: [{ type, code | ms }] }]`) between `[[[START_MACROS]]]` / `[[[END_MACROS]]]`. The `name` stays in the app; the firmware knows only the index.
- App: section "Makros" in the combos tab. Saving or deleting a macro is a snapshot pending change with the flag `macros`; a connected half gets it with the next full live sync (see "Full live sync"). An import and a loaded layout profile also set `macros`. Deleting renumbers the references in all layers (`removeMacroAt`); its undo (`restoreMacroAt`) inserts the macro again, moves higher references back and restores only the cleared positions that are still empty, so later key changes stay. `normalizeConfig` replaces an invalid macro with an empty one and keeps the indices.
- Macro library (`buildMacroExport`, `parseMacroImport` in `js/config-model.js`; buttons in `js/macros-ui.js`): "Makro exportieren" saves the macro in the editor, or the last macro of the list, as JSON `{ format: "dactyl-macro", version: 1, name, repeat?, steps }`. "Makro importieren" checks the file with the macro limits (1..32 steps, `isValidMacroStep`, pause 1..5000 ms) and puts the macro into the first free slot as a snapshot pending change with the flag `macros`; undo restores the old list. It rejects invalid JSON, a wrong format or version, bad steps, more than 32 steps and a full list (16 macros). The file holds no slot and no key assignment.
- Repeat while held (`userMacroRepeat[]`, `ADD_MACRO [0|1]`, from `DACTYL_FW_VERSION` 39): with `ADD_MACRO 1` the macro restarts from step 0 as long as the key that started it stays physically held (`keyState`). `startMacro()` takes the key (`r`, `c`) from the press paths (tap, hold and buffered combo candidate); starts from a leader sequence or the dynamic macro have no key and play once. `macroTick()` ends the run at once when the key is released (`stopMacro(true)`: open `DOWN` codes and a pending `TAP` are released). It ends too on host loss, config mode, `RELEASE_ALL` and every other cancel path above. Another pass starts after `MACRO_STEP_GAP_MS`. `ADD_MACRO` without argument or with `0` plays once; any other argument returns `ERR ARGS`. NVS key `macro_rep` (one byte per macro, written before `num_macros`; a missing or wrong-length key means no repeat; app defaults over a stored keymap remove it). `MACRO_DATA` carries `"r":1` only for a repeating macro. `server.py` renders `bool userMacroRepeat[MAX_MACROS]` from `macro.repeat` (boolean). The app keeps `repeat: true` in the macro (checkbox "Wiederholen" in the macro editor, `↻` in the list) and sends `ADD_MACRO 1` only for such a macro, so firmware before 39 stays usable for macros without repeat. The layout diff compares the steps and the flag. `normalizeConfig` keeps `repeat` only when it is `true`; any other value means no repeat and the steps stay. `MACRO_DATA` with `"r":1` stays under 160 characters (`test_get_config_lines_stay_short_at_maximum`).
- Macro presets (`MACRO_PRESETS`, `applyMacroPreset(presetKey, slotIndex, macros)` in `js/config-model.js`; dropdown "Makro-Vorlage" in `js/macros-ui.js`): ready-made macros (`git status`, `git commit -m ""`, `git push`, `() => {}`, Markdown link, code block, `console.log()`). Each preset builds its steps with `textToMacroSteps` (US layout) plus cursor key taps, so the cursor ends inside the brackets. `applyMacroPreset` returns a new list or `null` for an unknown key, a slot outside `0..macros.length` or `>= MAX_MACROS`, or an invalid macro (more than 32 steps). It replaces the whole slot (name, steps; the repeat flag is cleared). The dropdown fills the slot of the open macro editor, otherwise the first free slot, as a snapshot pending change with the flag `macros`; undo restores the old list.
- `GET_CONFIG` sends the macros (see "Layout diff" and "GET_CONFIG lists"); the layout diff compares them.
- Text as macro: the field "Text als Makro" in the macro editor appends the steps of a text to the draft (`textToMacroSteps` in `js/config-model.js`, no DOM). Lowercase letters, digits and unshifted characters are one `tap`. Uppercase letters and shifted characters (`!@#$%^&*()_+{}|:"~<>?`) are wrapped in `down`/`up` of left Shift; neighbouring shifted characters share one pair. A line break is `Enter`. `ä ö ü Ä Ö Ü` send `Alt` down, `u`, `Alt` up, then the vowel (with Shift for capitals); `ß` sends `Alt` + `s`. Shift is released before a dead key sequence. The app shows the step count and blocks "Text anhängen" if the text has a character without a mapping (named in the hint, for example `€`; option characters need a key pair) or if the draft would exceed `MAX_MACRO_STEPS` (32). A tab is `Tab`; `§` is the ISO key. No firmware change.

### macOS layout "U.S." and special characters (`DE_MAC_CHARS`, umlauts)

- The Mac uses the input source "U.S.". The firmware sends US HID codes, and macOS prints the US character. App labels, presets and templates must use US labels (`KEY_SEMICOLON` = `;`, never `Ö`).
- `DE_MAC_CHARS` in `js/keycodes.js` (picker group "Sonderzeichen (macOS US)") lists special characters. ASCII entries store the character itself (`+`, `~`, `<`; Shift implicit via `dactylAsciiToHid`). `§` is the ISO key `KEY_NON_US_BACKSLASH` (`0xEC`, HID `0x64`). This assumes the macOS keyboard type ISO; with ANSI, macOS swaps HID `0x35` and `0x64`, and `§` does not appear on the ISO key.
- Umlauts use their own actions `UMLAUT_AE` .. `UMLAUT_SZ` (`0x150` .. `0x156`, `ACT_UMLAUT_*` in `DactylCommon.h`). `sendUmlaut()` taps the dead key `Alt` + `u` and then the vowel (`'A'` for `Ä`, Shift implicit); `ß` is `Alt` + `s`. The sequence is sent once on press (also as forced hold, buffered combo candidate and combo `KEY_PRESS`); the release sends nothing. Modifiers that this half holds at the host (keys, key pairs, `MODIFIER_HOLD` combos; a held shifted ASCII code counts as left Shift; members of an active combo do not count) are released before the sequence and pressed again after it (`heldModifierMask`). On the left half, every step is a separate `PRESS`/`RELEASE` event; the `delay(5)` only delays the queueing, so the dead key needs a hardware check. Umlauts are not key pair members.
- The `.ino` defaults of both halves still contain German-layout codes (`;` for `ö`). A repository flash keeps the NVS keymap, so they do not reach the device. The preset "Deutsch QWERTZ (macOS US-Layout)" and `default_config*.json` use the umlaut actions.
- Option characters (`° € ´`) need a key pair (`Alt` + key). Their select value `CHAR_PAIR_<i>` is never stored: on "Änderung übernehmen", `resolveCharPairActions` reuses an equal pair or appends one (pending change) and writes `PAIR_<n>`. With 16 pairs a new one is rejected. The key change and the new pair go to the device together in the next full sync (see "Full live sync").
- Combo actions show only the single-code characters (combos do not support pairs). A search field above each action select filters its options (`applySelectFilter`, pure part `filterOptionNodes`). The search compares the option text without the prefix `Halten = ` / `2× Tippen = ` and never changes the selection. A hidden selected option stays selected and is named in a hint; without a match, the hint blocks "Änderung übernehmen" or "Combo speichern". The selects of the key pairs (`keyPairFirstSelect`, `keyPairSecondSelect`) and of the macro step (`macroStepCode`) have the same search; without a match it blocks "+ Tastenpaar hinzufügen" or "+ Schritt". Choosing the step type "Pause" and opening the macro editor clear the search of `macroStepCode`. `FILTER_BLOCKS_BUTTON` lists every searchable select. The live monitor maps `UMLAUT_*` to `KeyU` / `KeyS` with held Alt (`findKeyForEventCode`).

### One-Shot Modifiers and Caps Word (`DactylOneShot.h`)

- The master keeps the state for both halves (`OneShotState` in `SplitArbitratedKeyboard`). `DactylLogic.h` calls `bleKeyboard.oneShotPress(mask)` / `oneShotRelease(mask)` / `capsWordToggle()`; the left half sends them as `SPLIT_OP_ONE_SHOT_PRESS` / `SPLIT_OP_ONE_SHOT_RELEASE` (mask 1..255) and `SPLIT_OP_CAPS_WORD_TOGGLE`. A one-shot key on one half therefore acts on the next key of either half.
- Tap without another input in between: the modifier is armed for the next key or mouse press. A second tap disarms it. Several one-shot modifiers stack. Held while other keys are pressed: it acts as a normal modifier for each of them and arms nothing.
- The armed modifiers go into the same HID report as the key press; the next report releases them (`pressWithMods`). A modifier that is already in the report is not pressed or released again. Modifier keys do not consume the armed state.
- A press while Alt is in the report (umlaut dead key, key pair with Alt) consumes nothing and does not change Caps Word. So an armed Shift before `UMLAUT_AE` gives `Ä`.
- A held one-shot key does not count in `heldModifierMask()`: an umlaut pressed while a one-shot key is held sends the plain sequence, and the held one-shot modifier does not reach the umlaut (Alt in the report blocks it). `test_umlaut_while_one_shot_key_held_sends_plain_sequence` fixes this behavior.
- A `CAPS_WORD` key that is a combo candidate is buffered like a normal key: a triggered combo does not toggle Caps Word; a quick tap toggles it on release, a hold after `comboTimeoutMs` (`processDeferredKeys`, forced hold in `activateTapHoldAsHold`). One-shot keys are not buffered; a triggered combo releases them without arming (`releaseAll()`).
- Caps Word: `a`..`z` and `-` get Shift. Digits, `_`, Backspace, Delete and modifiers keep it on; every other key ends it. The key toggles it.
- Caps Word idle timeout: Caps Word ends after `CAPS_WORD_IDLE_MS` (5000 ms) without a key press of either half. `oneShotExpire()` (called from `loop()` on the master) measures the time; each key press and each toggle (`capsActivity`) restarts it. It does not depend on `oneShotTimeoutMs`. The left half needs no code, because the master holds the state.
- Umlauts in Caps Word: `UMLAUT_AE`, `UMLAUT_OE` and `UMLAUT_UE` send `Alt`+`u`, then the vowel. Alt is released before the vowel, so the vowel gets Shift (`Ä`, `Ö`, `Ü`) and Caps Word stays on, also from the left half. `test_caps_word_umlaut_sequence_is_uppercase_and_keeps_caps_word` fixes this. A key press with the Alt dead key counts as activity.
- `RELEASE_ALL`, a right `releaseAll()` (combos) and the link timeout release a held one-shot key without arming it. A host loss clears the state. `CAPS_WORD_TOGGLE` is never retried (a duplicate would undo it); one-shot press and release are idempotent.
- Combos support both actions with `KEY_PRESS` (one-shot = tap). `MODIFIER_HOLD` holds only codes 1..255, so `server.py` (`generate_combos_cpp`) and the combo dialog reject `OSM_*` and `CAPS_WORD` with `MODIFIER_HOLD`. Older saved configs, profiles and imports with this pair are migrated to `KEY_PRESS` (`migrate_config` in `server.py`, `migrateConfig` in `validateConfigShape`); before, such a combo sent nothing. Key pairs do not accept them as members.

### One-shot timeout (`oneShotTimeoutMs`)

- Setting per half: `0` = off (default), otherwise `500..10000` ms. An armed one-shot modifier (`OSM_*`) or an armed one-shot layer (`OSL_n`) expires when the time passes without a consuming key press.
- Command `SET_ONESHOT_TIMEOUT <0|500..10000>` (`OK SET_ONESHOT_TIMEOUT <ms>`, otherwise `ERR ARGS`; a value of 1..499, a non-digit or more than 5 characters is rejected). NVS key `osm_to`, `DEVICE_INFO` field `ot`. The compiled-in default is `oneShotTimeoutMs` in the settings block (`server.py`, `SETTINGS_RANGES`); the app clamps 1..499 to 500 (`clampSetting`).
- Modifiers: the master holds the state (`OneShotState`). `oneShotExpire()` (`DactylOneShot.h`) runs in `loop()` of `dactyl_right.ino`. Layers: `oslExpireLocal()` (`DactylLogic.h`) runs in `loop()` of both halves. Each half expires only its own armed layers; the mirror of the other half keeps its own limit (`OSL_REMOTE_TIMEOUT_MS`).
- The time starts at the first `loop()` pass that sees a changed armed state. Every change (a new arm, a disarm, a consumed key) starts it again for all armed items. Held one-shot keys and Caps Word stay untouched.
- The app sends the command in the full sync as optional (`optional: "args"`): firmware without it answers `ERR UNKNOWN` or `ERR ARGS`, and the sync continues. The input is `#oneShotTimeoutInput`.
- Limit: a clear and a re-arm that leave the same armed bits within one `loop()` pass keep the old timer, because the timer compares the state, not a counter.
- `DACTYL_FW_VERSION` 37. Flash both halves.
- Tests: `test_firmware_logic.cpp` (`test_osl_expires_after_timeout_without_key`, `test_osl_never_expires_when_timeout_is_zero`, `test_osl_consumed_before_timeout_stays_consumed`, `test_osl_timeout_survives_millis_wrap`, `test_one_shot_timeout_nvs_rejects_invalid_values`, `test_one_shot_timeout_command_and_device_info`), `test_split_hid.cpp` (`test_one_shot_modifier_*`), `tests/test_app_logic.js`, `tests/test_server.py` (`test_one_shot_timeout_setting`).

### Dynamic macro (`ACT_DM_REC`, `ACT_DM_PLAY`)

- `ACT_DM_REC` (`0x16C`, app name `DM_REC`, keycap label `DM Rec`) starts and stops the recording of one macro; `ACT_DM_PLAY` (`0x16D`, `DM_PLAY`, `DM Play`) plays it. A user who repeats an edit many times records it on the keyboard and needs neither the app nor a sync.
- Only the master has the slot (`DynamicMacro dynMacro` in `SplitArbitratedKeyboard`, `DactylDynamicMacro.h`, enabled by `DACTYL_DYNAMIC_MACRO` in `dactyl_right.ino`). On the left half both actions do nothing: `server.py` (`validate_config`) and the app (`validateConfigShape`) reject them there, as tap, hold or double-tap action. A combo cannot use them (`ADD_COMBO`, `generate_combos_cpp`, the app).
- Recording happens at the shared HID path, so the keys of both halves arrive in the order the Mac sees them: `press`/`release` of the right half and `leftKeyPress`/`leftKeyRelease` of the left half call `noteDown`/`noteUp`. A press records a `MACRO_STEP_DOWN`, the release a `MACRO_STEP_UP`. The release counts only when the other half does not hold the code any more (`SplitArbitratedKeyboard` arbitration), so one `Shift` on each half gives one `DOWN` and one `UP`. A key held before the recording has no `DOWN`, so it records no `UP`. `releaseAll()` (combo) and a host loss close each open `DOWN` with a `UP` (`noteReleaseAll`), except a code that the left half still holds.
- Pauses are not recorded; the playback uses the gap of the macro engine (`MACRO_STEP_GAP_MS`). Media keys, mouse buttons and layer actions are not recorded: the slot holds keyboard codes only.
- One-shot modifiers (`OSM_*`) and Caps Word are not recorded as steps. They apply to the keys at playback time, so a recorded key plays with the modifier that is armed when `DM_PLAY` runs, not the one that was armed while recording.
- Limit: `MAX_MACRO_STEPS` (32) steps. At the limit the recording stops by itself (`DM_REC:0`). Each key needs two steps (`DOWN`, `UP`), so the slot holds 16 key taps. A new `DM_REC` replaces the old slot.
- `DM_REC` while recording stops it. `DM_PLAY` while recording also stops it and plays nothing, so the playback cannot run into the slot. `DM_PLAY` with an empty slot sends nothing. While any macro runs (the slot or a user macro), `DM_REC` and `DM_PLAY` do nothing, so the keys of a running macro never enter the slot. The recording also ends when the Mac disconnects or the config mode starts (`dynamicMacroService`, `splitResetForHostLoss`). Neither action needs a held key; both act at the press (as tap, hold, double-tap or buffered combo candidate).
- The playback runs through the normal macro engine with the slot index `DM_SLOT_INDEX` (`0xFF`): `macroLengthOf`, `macroStepOf`, `startMacro`-like start in `dynamicMacroPress`. It stops like any macro (`stopMacro`) on config mode, host loss and deep sleep. The actions need a Mac connection and do nothing in config mode.
- RAM only: a restart, deep sleep and `enterConfigMode()` (`dynamicMacroReset`) clear the slot. It is never written to the NVS and `GET_CONFIG` never sends it, because it can hold a password. `RESET_CONFIG` needs no change. The slot is not part of the layout profiles, the backups or the layout diff.
- State on USB serial: `DM_REC:1` when the recording starts, `DM_REC:0` when it ends (also at the limit, by `DM_PLAY`, by a lost Mac and by a reset). `dynamicMacroService()` prints one line per change in `loop()` (`dynamicMacroTakeLine`), nothing at the start, and never over BLE. `GET_INFO` (the app connecting) repeats the current state once (`dynamicMacroResend`) (no keylogger channel, no extra load next to the sync acks). The app shows the pill "Makro REC" (`#dmRecPill`, `noteDmRec` in `js/serial.js`) only for a line of the master (`parseDmRecLine` in `js/side-routing.js`) and only over USB; a closed connection hides it.
- `DACTYL_FW_VERSION` 25: an older firmware does not know `0x16C`/`0x16D` and ignores them. Only the master needs the code. Both halves share the version value, so the app hint "Beide Hälften flashen" appears until the left half runs version 25 as well; flash both halves to clear it.
- Tests: `test_firmware_logic.cpp` (`test_dynamic_macro_*`: record and play back, serial line, step limit, own keys not recorded, RAM only and reset, host and config mode, hold action, no combo, `releaseAll`), `test_split_hid.cpp` (`test_dynamic_macro_*`: both halves, same code on both halves, no recording, `KEY_WRITE` and host loss, `releaseAll` with a left key held), `tests/test_app_logic.js` (code, label, combo and left-half rule, `DM_REC` line), `tests/test_server.py` (code, combo, left half), `tests/test_side_profiles.js` (master only, no NVS, no BLE, config mode).

### Leader key (`ACT_LEADER`, `DactylLeader.h`)

- `ACT_LEADER` (`0x16E`, app name `LEADER`, keycap label `Leader`) starts a capture on its own half. The next keys of that half form a sequence of up to `LEADER_MAX_KEYS` (4) keys. A sequence from `userLeaderSeqs[]` (`LeaderSeq { uint8_t keys[4]; uint16_t action; }`, up to `MAX_LEADER_SEQS` = 16 per half) that matches runs its action once: a keyboard code (tap), a key pair (`PAIR_n`, tap) or a macro (`MACRO_n`). No match sends nothing. Rare actions get a short sequence and need no key position or combo.
- Each half has its own list and captures only its own keys (`leaderState`). The list is not shared between the halves, and the master runs no left sequence. `dactyl_right.ino` and `dactyl_left.ino` both hold the marked block `START_LEADER` .. `END_LEADER` and the setting `leaderTimeoutMs`; the logic is `DactylLeader.h` (no Arduino or BLE dependency) with the hooks in `DactylLogic.h`.
- The keys of a sequence send no HID event, neither at the press nor at the release (`leaderConsumeKey`, `leaderConsumed[][]`). A consumed key does not count for Repeat, does not start a combo (`checkUserCombos` skips consumed keys), and does not send later as a buffered combo candidate (`keySentToHost` is set). The flag is cleared by the next press of the same key, so the release of a consumed key never stays unpaired and no key is left held.
- Matching (`leaderCapture`): after each key, a sequence that matches exactly and has no longer sequence with the same start runs at once. If a longer sequence with the same start exists, the capture waits; when the time expires, the exact shorter sequence runs (`leaderExpire`). A key that no sequence continues ends the capture and sends nothing. The fifth key does not exist: at four keys the capture ends.
- Time: `leaderTimeoutMs` (100..5000, default 1000; NVS key `leader_to`, command `SET_LEADER_TIMEOUT <ms>`, `DEVICE_INFO` field `ld` (older firmware: `leader_timeout_ms`)). It counts from the Leader key and then from the last captured key. `leaderTick` (`processDeferredKeys`) ends the capture after the time. A timeout without a matching sequence sends nothing, also not the captured keys.
- Which keys count: only keyboard codes 1..255 without modifiers (`0x80..0x87`) (`leaderKeyCodeValid`). Layer keys, modifiers, media and mouse actions pass through unchanged and do not end the capture, so a user can hold a layer key and press the sequence keys on that layer. A Mod-Tap key whose hold resolves as a modifier or layer also passes through; its tap resolves as a normal key and is captured. Actions that send their own output to the Mac (key pair, macro, umlaut, `REPEAT`, `ALT_REPEAT`, `DM_REC`, `DM_PLAY`, one-shot modifier, Caps Word, another Leader key) end the capture without a sequence, so nothing else is sent during a capture. A second Leader key press ends the running capture and starts a new one. An armed one-shot layer is consumed by the Leader key like by any other key press.
- Combo candidates: a Leader key that is a combo candidate is buffered like other keys. The capture starts on a quick release or after the combo window (`leaderBuffered`); a combo that fires leaves no capture behind. A consumed key never completes a combo, also not as the third key.
- The capture needs a Mac connection and no config mode. Without them, the Leader key does nothing. It ends (without sending) on a lost host, a link loss, config mode and `RELEASE_ALL` (`oslClearAll` calls `leaderReset`), and on `CLEAR_LEADER`. The Leader key is no combo action (`ADD_COMBO`, `generate_combos_cpp`, the app reject it) and `REPEAT` does not repeat it.
- Commands: `CLEAR_LEADER`, `ADD_LEADER <action> <key1> [<key2> [<key3> [<key4>]]]` (decimal tokens; keys 1..255 without modifiers; action a key, `PAIR_n` (`0x140..0x14F`) or `MACRO_n` (`0x170..0x17F`); two sequences with the same keys are rejected with `ERR ARGS`; a prefix of another sequence is allowed), `SAVE_LEADER` and `SET_LEADER_TIMEOUT <ms>`. Ack: `OK ADD_LEADER <index>`, `OK SAVE_LEADER`, `OK SET_LEADER_TIMEOUT <ms>`; errors as usual (`ERR ARGS`, `ERR NVS`).
- NVS: `num_leader` and `leader_data` (6 bytes per sequence: 4 keys, action as 16 bit little endian). The data is written first and the count last (`saveLeaderSeqsToNVS`). A stored list overrides the compiled-in list, also an empty one. A stored list with one invalid sequence is ignored. A new layout from the app (`KEYMAP_DEFAULTS_ID` != 0) over a stored keymap discards the stored list, because sequences point to the compiled-in key pairs and macros (`PAIR_n`, `MACRO_n`).
- `GET_CONFIG` sends `LEADER_COUNT:<n>` and `LEADER_DATA:{"o":<offset>,"e":[[action,k1,k2,k3,k4],...]}` (4 entries per line, unused keys 0) from both halves, before the macros. See "GET_CONFIG lists".
- App: the card "Leader-Folgen" (`js/leader-ui.js`) shows on both halves. The config field is `leaderSequences: [{ keys: ["KEY_A", "KEY_B"], action: "MACRO_0" }]`; the setting is `settings.leaderTimeoutMs`. `validateConfigShape` and `normalizeConfig` (`js/config-model.js`) and `generate_leader_cpp` (`server.py`) apply the same rules as the firmware. The full sync sends `SET_LEADER_TIMEOUT` with the settings, then `CLEAR_LEADER`, `ADD_LEADER` per sequence and `SAVE_LEADER` as the last phase, after `SAVE_MACROS`; a failure after `CLEAR_LEADER` shows a toast, because the list in RAM is then only partly sent and not saved; firmware without them answers `ERR UNKNOWN` and the app continues with a hint. The layout diff lists the sequences.
- A sequence that uses `PAIR_n` or `MACRO_n` counts as use of that pair or macro (delete confirmation, layout check, action search with the hit kind `leader`). Deleting a pair or a macro removes each sequence that uses it and renumbers the others; undo restores them.
- `DACTYL_FW_VERSION` 26: an older firmware does not know `0x16E` and ignores it. Both halves share the version value, so flash both halves.
- Tests: `test_firmware_logic.cpp` (`test_leader_*`: match, no sequence key at the host, release of all keys after the sequence, timeout, timeout setting, no match, key pair and macro action, prefix sequence, four-key limit, no host, release-all, layer keys and modifiers, combos, commands, NVS, `GET_CONFIG`, `DEVICE_INFO`), `tests/test_app_logic.js` (validation, tuples, snapshot round trip, diff, sync steps, pair and macro deletion), `tests/test_server.py` (constants, rendering for both halves, setting range, combo rejection).


### Combo and leader presets (`COMBO_PRESETS`, `LEADER_PRESETS`)

- `COMBO_PRESETS` and `LEADER_PRESETS` in `js/config-model.js` are ready-made templates. A combo preset names two keyboard codes and one action (for example `J + K` -> `Escape`). A leader preset names one or two keyboard codes and one action (for example `G, U` -> `Page Up`).
- `applyComboPreset(presetKey, config)` finds each key on layer 0 of the edited half: the first cell with exactly this tap action and no hold or double-tap action. It returns `{ combos, combo }` (new list, the config stays unchanged) or `{ error }` for an unknown key, a full list (`MAX_COMBOS`), a missing key, or an existing combo on the same cells (any action, any order).
- `applyLeaderPreset(presetKey, sequences)` returns `{ sequences, sequence }` or `{ error }` for an unknown key, a full list (`MAX_LEADER_SEQS`), or an existing sequence with the same keys (`hasDuplicateLeaderSequence`).
- App: the dropdown "Combo-Vorlage" (`js/editor-events.js`, `applyComboPresetFromUI`) and "Leader-Vorlage" (`js/leader-ui.js`, `applyLeaderPresetFromUI`). Each choice adds one entry as a snapshot pending change; undo restores the old list. An error shows a toast.
- Combos use `KEY_PRESS` and all layers. Tests: `tests/test_app_logic.js` ("Combo-Vorlagen", "Leader-Vorlagen").

### BLE host slots (`ACT_HOST_BASE`, `DactylBleHost.h`)

- Actions `HOST_1` .. `HOST_3` (`0x188` .. `0x18A`; `0x170` .. `0x17F` belong to the macros) switch the BLE host of the master. Master only: the left half has no BLE host, so `server.py` and `js/config-model.js` reject the actions on the left half. Combos reject them.
- Each slot has its own static random address: `bleHostAddress()` takes the BLE base MAC, sets the top 2 bits of `addr[0]` (`|= 0xC0`) and mixes the slot into byte 1. The addresses of slot 1..3 and of the config mode (`DactylConfigBle.h`) are pairwise different, so each host bonds on its own and macOS caches the report map per address.
- A switch to another slot calls `releaseAll()` (both halves, macro, mouse movement and one-shot state are cleared), stores the slot in the NVS (namespace `dactyl`, key `ble_host`, default 1, invalid value = 1) and restarts the board. The start sets the address of the slot (`DactylBleComposite::hostSlot`). The action for the active slot only releases the keys. In config mode, the action does nothing. It works without a Mac connection, so a lost host never blocks the change to another one. A failed NVS write sends `ERR NVS BLE_HOST` and keeps the slot.
- The config mode keeps its own address (`startConfigModeBle`). It does not change the stored slot.
- The master sends the line `BLE_HOST:<n>` before each `DEVICE_INFO` (own line, because `DEVICE_INFO` has only a few bytes of reserve under 512). The app shows the pill `Host <n>` (`#bleHostPill`).
- Every slot, slot 1 included, now uses a static random address. The bond of the old controller address does not match it: pair the keyboard once again on each host after the update ("Dieses Gerät ignorieren..." in macOS first).
- `DACTYL_FW_VERSION` is 30. Flash both halves.

### Sentence case (`ACT_SENTENCE_CASE`, `DactylOneShot.h`)

- The key `SENTENCE_CASE` (`0x18C`) toggles the mode. While it is on, a `.`, `!` or `?` followed by one or more `Space` presses arms a Shift for the next lowercase letter (`a`..`z`). The letter gets Shift in the same report, then the arming ends. The state (`OneShotState.sentenceCase`, `sentenceStage`) lives on the master and counts the keys of both halves (`sentenceCaseStep`).
- Any other key before the letter ends the arming: digits, navigation keys, Backspace, Enter and capital letters. A `Space` without a sentence end does nothing. Modifiers do not change the state (a sentence end typed with Shift is `Shift` + `/` or `1`). A press while Alt is in the report (umlaut dead key) is ignored like for Caps Word.
- The left half sends `SPLIT_OP_SENTENCE_CASE_TOGGLE` (30, no values); it is never retried (a duplicate would undo it). Media keys and mouse buttons cancel the armed Shift too. An Alt chord (for example Option+Left) leaves it unchanged, because the umlaut dead key uses Alt. The mode lives in RAM only: a reboot or deep sleep switches it off. A host loss keeps the mode and drops only the armed Shift (no indicator shows the mode; press the key again to check). With Shift held, `/` and `1` count as `?` and `!`. The key is a combo candidate like `CAPS_WORD` (buffered), works with `KEY_PRESS` combos and not with `MODIFIER_HOLD`, and `REPEAT` repeats it.
- Codes in `DactylCommon.h`, `server.py` and `js/keycodes.js` must match; tests compare them. `DACTYL_FW_VERSION` is 33; flash both halves.

### Num Word (`ACT_NUM_WORD`)

- `ACT_NUM_WORD` (`0x18D`, app name `NUM_WORD`, keycap label `NumWd`) turns the layer `numWordLayer` on with a tap. It solves a number run without a held layer key or a toggle that the user must switch off again.
- Setting `numWordLayer` (`0..7`, default `1`, `0` = Num Word does nothing): `SET_NUM_WORD_LAYER <n>` (NVS key `nw_layer`, `DEVICE_INFO` field `nwl`). Each half has its own value. The app sends the command in the full sync as an optional step (`optional: "args"`): older firmware answers `ERR UNKNOWN` and the sync goes on.
- The layer is a `TG` layer (`toggleLayers[]`, state `numWordActive`, `numWordOn`, `numWordLastMs` in `DactylLogic.h`), so the layer sync (`SPLIT_OP_LAYER_STATE`) carries it to the other half. Keys of the other half therefore also use the layer, but only the keys of the half that holds the state end it.
- The following keys keep Num Word on and restart the idle timer `NUM_WORD_IDLE_MS` (5000 ms): digits `0`..`9`, `.` `,` `-` `+` `*` `/` `=`, modifiers (`0x80`..`0x87`), keypad keys (`0xDC`..`0xEB`), layer keys (`MO_n`, `TG_n`, `LAYER_UP`, `LAYER_DOWN`, `LAYER_LOCK`, `OSL_n`), an empty action and `NUM_WORD` itself. A key counts as such a key only if all of its resolved actions (tap, hold, double tap) are in this list.
- The first other key (a letter, `Space`, `Enter`) ends Num Word. `numWordNoteKeyPress` runs after the first resolve of the key and, on an ending key, resolves it again on the layer below. This key therefore comes from layer 0 (`Space` is a space), not from the Num Word layer. A second tap of `NUM_WORD`, 5000 ms without a key press (`numWordExpire` in `loop()`), `oslClearAll` (`RELEASE_ALL`, link loss, host loss, config mode) and a layer that the user turns off by hand also end it.
- `ACT_NUM_WORD` is no combo action: `ADD_COMBO`, `server.py` (`NUM_WORD_CPP`) and the app reject it. `REPEAT` does not repeat it. The state lives in RAM only. `DEVICE_INFO` grows by `"nwl":N,` (7 bytes); the line stays under the BLE limit of 512 bytes (a test checks it).
- Codes in `DactylCommon.h`, `server.py` and `js/keycodes.js` must match; tests compare them. `DACTYL_FW_VERSION` is 43; flash both halves.

### Tap-Toggle layer keys (`ACT_TT_BASE`)

- `ACT_TT_BASE` (`0x193`) and `NUM_TT_ACTIONS` (8) define the actions `TT_0` .. `TT_7` (`0x193` .. `0x19A`, one for each layer `0..7`). The helpers `isTapToggleAction(a)` and `tapToggleLayer(a)` are in `DactylCommon.h`.
- One key does the work of `MO_n` and `TG_n`. Hold the key: the target layer is active like `MO_n` (`momentaryLayers[]`). Release the key: the momentary layer ends.
- Tap the key two times quickly: the second press comes less than `tappingTermMs` after the first release. The second press toggles the target layer on or off like `TG_n` (`toggleLayers[]`). `TT_0` clears all toggled layers like `TG_0`.
- A single tap ends the momentary layer at the release. A press held for `tappingTermMs` or longer does not arm a double tap. A second press that comes too late acts as a new first press.
- The window is `tappingTermMs` of the half. A per-key tapping term does not apply. The state is per layer, not per key: do not assign the same `TT_n` to two keys.
- The state (`tapToggleArmed[]` and the time stamps in `DactylLogic.h`) lives in RAM only. `RELEASE_ALL`, a link loss and the loss of the host clear it (`tapToggleReset`).
- The layer sync (`SPLIT_OP_LAYER_STATE`) carries the momentary and toggled layers to the other half like for `MO_n` and `TG_n`. Num Word keeps its layer on this key like on `MO_n`.
- `TT_n` is no combo action: `ADD_COMBO`, `server.py` and the app reject it. The app palette shows the keys in the group "Layer Umschalter" and in the layer palette. The keycap label is `TTn`.
- "Ebenen tauschen" (`swapLayersWithRefs`) swaps `TT_n` references like `MO_n`, `TG_n` and `OSL_n`. The layer graph check counts `TT_n` as a reachable and lockable layer.
- Codes in `DactylCommon.h`, `server.py` and `js/keycodes.js` must match; tests compare them. `DACTYL_FW_VERSION` is 50; flash both halves.
- Tests: `firmware/tests/test_firmware_logic.cpp` ("test_tap_toggle_hold_release_and_double_tap_latch"), `firmware/tests/test_left_logic.cpp`, `tests/test_app_logic.js`, `tests/test_server.py`.

### Tapping term tune keys (`ACT_TT_UP`, `ACT_TT_DOWN`)

- `ACT_TT_UP` (`0x18E`, app name `TT_UP`, keycap label `TT+`) and `ACT_TT_DOWN` (`0x18F`, app name `TT_DOWN`, keycap label `TT-`) change `tappingTermMs` of the half during real typing. The user does not open the app to find a good value.
- A tap acts on the release: `TT_UP` adds and `TT_DOWN` subtracts `TT_STEP_MS` (10 ms), clamped to `TAPPING_TERM_MIN_MS..TAPPING_TERM_MAX_MS` (`100..500`). The change lives in RAM only (`ttRelease` in `DactylLogic.h`). A reboot without a save restores the NVS value (`tap_term`).
- Hold both keys of the same half for `TT_SAVE_HOLD_MS` (1000 ms): `ttExpire` in `loop()` saves the value once with `saveTappingTermToNVS`. While both keys are held, and until both are released, neither key counts as a tap. A single key held for a long time is still a tap on release.
- Put `TT_UP` and `TT_DOWN` on plain keys (a tap action without hold or double-tap action). A key with a hold or double-tap action decides at the release, so it cannot take part in the save chord. A second press of one key while the other stays held starts a new chord and saves again after `TT_SAVE_HOLD_MS`.
- The keys keep Num Word on (`isNumWordKeepAction`), so the user can tune the term during a number run.
- Each half has its own value and its own keys. The keys send nothing to the host. `oslClearAll` (`RELEASE_ALL`, link loss, host loss, config mode) resets the key state; a late release then changes nothing. The Leader capture ends on these keys.
- The keys are no combo action: `ADD_COMBO`, `server.py` (`TT_CPP`) and the app reject them. `REPEAT` does not repeat them. A later full sync from the app writes the app value with `SET_TAPPING_TERM` and replaces a tuned value.
- Codes in `DactylCommon.h`, `server.py` and `js/keycodes.js` must match; tests compare them. `DACTYL_FW_VERSION` is 44; flash both halves.

### Boot layer (`bootLayer`)

- Setting `bootLayer` (`0..7`, default `0`, `0` = off): `SET_BOOT_LAYER <n>` (NVS key `boot_layer`, `DEVICE_INFO` field `bl`). Each half has its own value. The app shows it as "Start-Ebene" in the settings. The full sync sends the command as an optional step (`optional: "args"`): older firmware answers `ERR UNKNOWN` and the sync goes on.
- `applyBootLayer()` runs in `setup()` of both sketches after `loadKeymapFromNVS()`, so at each power-on and after each wake-up from deep sleep (the board restarts). It turns the layer on as a `TG` layer and marks it in `layerLockedMask`, so `layerTimeoutMs` does not drop it. `TG_0` or a toggle of the layer turns it off like any `TG` layer. The layer sync (`SPLIT_OP_LAYER_STATE`) carries it to the other half.
- Set the same value on both halves. The master takes over the toggle layers of the left half through the layer sync without a lock bit, so `layerTimeoutMs` can drop a boot layer that only the left half holds, and a different value on the other half can switch the layer off again. This needs a hardware check.
- `DEVICE_INFO` grows by `"bl":N,` (7 bytes) and the field `quick_tap_ms` became `qt` (10 bytes less) to stay under the limit; the line stays under the BLE limit of 512 bytes (a test checks it). `DACTYL_FW_VERSION` is 45; flash both halves.

### Keep-awake key (`ACT_KEEP_AWAKE`)

- `ACT_KEEP_AWAKE` (`0x190`, app name `KEEP_AWAKE`, keycap label `Awake`) keeps the Mac awake during a video call or a long read. A tap on the master toggles `keepAwakeActive` (`keepAwakeToggle` in `DactylLogic.h`).
- While active, `keepAwakeTick` in `loop()` sends two mouse reports every `KEEP_AWAKE_INTERVAL_MS` (60000 ms): `+1` pixel on X, then `-1`. The net move is zero.
- Each physical key press of either half restarts the 60 s timer (`notePriorKeyPress`), because real input already keeps the Mac awake.
- The state lives in RAM only. `RELEASE_ALL`, host loss, link loss and the config mode (`oslClearAll`), `enterStandby` and a tick without BLE link or in config mode end it. A reboot starts with Keep-awake off.
- Standby ends the state after `standbyTimeoutMinutes` without key presses (default 5 min), because the nudges do not count as activity. Press the key again after a wake-up. A tap while the Mac is not connected or in config mode changes nothing.
- The key sends no keycode. It works only on the master: the left half has no mouse, and `server.py` and the app reject the action on the left half.
- The key is no combo action: `ADD_COMBO`, `server.py` (`KEEP_AWAKE_CPP`) and the app reject it. `REPEAT` does not repeat it. It keeps Num Word on (`isNumWordKeepAction`) and ends a Leader capture.
- Codes in `DactylCommon.h`, `server.py` and `js/keycodes.js` must match; tests compare them. `DACTYL_FW_VERSION` was 47 for this key; flash both halves.

### Deep-sleep key (`ACT_DEEP_SLEEP`)

- `ACT_DEEP_SLEEP` (`0x191`, app name `DEEP_SLEEP`, keycap label `Sleep`) puts the keyboard into deep sleep before transport. The board has no battery switch.
- A press outside the config mode sets `deepSleepRequested` (`DactylLogic.h`). The key sends no keycode.
- `deepSleepKeyDue` in `loop()` of each sketch returns true once, as soon as no key of this half is held. It checks `keyState` and `rawKeyState` (`anyRightKeyHeld`, `anyLeftKeyHeld`). A held key would wake the board at once through `ESP_EXT1_WAKEUP_ANY_HIGH`.
- Master: `enterDeepSleep()` sends `SPLIT_OP_SLEEP` (`sendSplitSleep()`) to the left half and sleeps. Left half: the key on the left half enters its own `enterDeepSleep()` after the release. A key on one half does not wake or sleep the other half, unless the master sends `SPLIT_OP_SLEEP`.
- The request lives in RAM only. `enterConfigMode()` clears it (`deepSleepClear`); a press in config mode changes nothing, and `deepSleepKeyDue` drops a request that meets config mode.
- The key is no combo action: `ADD_COMBO`, `server.py` (`DEEP_SLEEP_CPP`) and the app reject it. It ends a Leader capture. The key works on both halves.
- Codes in `DactylCommon.h`, `server.py` and `js/keycodes.js` must match; tests compare them. `DACTYL_FW_VERSION` was 48 for this key; flash both halves.

### Clear-state key (`ACT_CLEAR_STATE`)

- `ACT_CLEAR_STATE` (`0x192`, app name `CLEAR_STATE`, keycap label `Clear`) is a panic key. One press resets the half and, through the master, the shared text modes. The key sends no keycode.
- `clearStatePress()` (`DactylLogic.h`) stops a running macro and all mouse movement (`stopMacro`, `resetMouseMove`), calls `oslClearAll()` (One-Shot layers, Num Word, Swap Hands, Tapping-Term keys, Keep-awake, Leader capture), clears every toggle layer and the Layer Lock mask (back to layer 0), drops a deep-sleep request, and releases all held HID keys (`releaseAll`).
- `bleKeyboard.clearState()` resets the One-Shot state on the master (`oneShotReset`): One-Shot modifiers, Caps Word and Sentence Case. Unlike a host loss, it also switches off the Sentence Case mode. On the left half, the proxy sends `SPLIT_OP_CLEAR_STATE` (32, left -> master, no values) after `RELEASE_ALL`; the master runs it with `leftClearState()`. The packet is never retried (a late duplicate would undo a mode that the user turned on again) and counts as a press op (waiting master taps go first). The master also runs `clearStatePress()` itself, like a local press and also without a Mac connection (`onSplitClearState` under `configMutex`; a busy mutex sets `clearStatePending` and `processSplitEvents` retries at the next pass), so a press on the left half also stops its macro, mouse movement, toggle layers, Num Word, Swap Hands, Leader capture and Keep-awake. It also clears a held One-Shot key in the arbitrated report.
- A press on the master does not clear the left half: the master sends no clear packet, so macros, Num Word, Swap hands and Leader capture on the left half stay on. Press the key on that half too. The toggle layers of the left half follow the normal layer sync.
- Layer state of the other half follows through the normal layer sync. A key that is still held stays physically down; release and press it again.
- The key is no combo action: `ADD_COMBO`, `server.py` (`CLEAR_STATE_CPP`) and the app reject it. It keeps Num Word on (`isNumWordKeepAction`; the key then ends Num Word itself) and ends a Leader capture. It works on both halves.
- Codes in `DactylCommon.h`, `server.py` and `js/keycodes.js` must match; tests compare them. `DACTYL_FW_VERSION` is 49; flash both halves.

### Key lock (`ACT_KEY_LOCK`, `DactylKeyLock.h`)

- `ACT_KEY_LOCK` (`0x16F`, app name `KEY_LOCK`, keycap label `KeyLock`) arms the lock. The next key press or mouse button press of either half stays held after the physical release of the key. A second press of the same input releases it. Use it for a long drag with a mouse button, a held `Shift` for a selection or a held game key.
- State (`KeyLockState` in `SplitArbitratedKeyboard::keyLock`, on the master only): `armed` plus one slot per input (`KL_FREE`, `KL_HELD`, `KL_ON`, `KL_SWALLOW`). The id of an input is its keycode 0..255, or `256 + bit` for the mouse buttons left, right and middle. `klOnPress` locks the armed input and consumes the arming; `klOnRelease` returns true while the input is locked, so the release never reaches the report. The second press (`KL_ON`) releases the input in the report and swallows its own release (`KL_SWALLOW`).
- What is lockable: keys with a keycode 1..255 (also modifiers) and the three mouse buttons. These calls use `pressLockable` and `mousePressLockable` (`DactylLogic.h`): a plain key press, the quick tap of a combo candidate, the hold decision of a Mod-Tap key, the buffered press after the combo window and the mouse buttons. Not locked: layer keys (`MO`, `TG`, `OSL`, `LAYER_*`), `KEY_LOCK` itself (it arms, so a second `KEY_LOCK` changes nothing), macros and dynamic macros, key pairs, umlauts, media keys, the wheel, mouse movement, one-shot modifiers, Caps Word, `REPEAT` and the Leader key. These actions leave the arming in place; the next lockable input uses it. A key pair or macro that sends a key does not use the lockable path, so it is never locked.
- Both halves: the left half sends `SPLIT_OP_KEY_LOCK` (no values) to arm the master. A physical key press or mouse press of the left half carries `arg 1` in `SPLIT_OP_KEY_PRESS` / `SPLIT_OP_MOUSE_PRESS`; `arg 0` (macro, key pair, umlaut) is never locked. `isValidSplitHidEvent` accepts `arg` 0 or 1 for these two ops only, `SPLIT_OP_KEY_LOCK` needs `arg 0` and `code 0`. `splitIsPressOp` does not list it. It is idempotent, so the retry queue may repeat it. The left half has no lock state. `DactylSplitKeyboard::keyLockReleaseAll` does nothing; `pressLockable` and `mousePressLockable` only set the flag.
- A lock belongs to the input, not to a half. The other half pressing the same code while it is locked counts as the second press and releases it. Shift is kept for a held shifted character (`releaseKeepingShift`), and a locked input with a key override is released through `overrideRelease`.
- Release of all locks (`keyLockReleaseAll`): the locks and the arming end on `RELEASE_ALL` of the master (`releaseAll`, also used by a combo, the config combo and the config mode), `RELEASE_ALL` of the left half (`splitReleaseHeld` calls `leftKeyLockRelease`, also when the left half holds nothing), a link timeout of the left half, an overflow of the receive ring, a lost Mac (`splitResetForHostLoss`) and the standby (`enterStandby` calls `keyLockReleaseAll`). `releaseAll` of the master and the host loss reset the whole state. A link timeout, an overflow and the standby release only locked inputs (`KL_ON`); a key that is still held physically stays in the report, and its release works as usual.
- Without a Mac connection or in config mode, `KEY_LOCK` arms nothing (like the Leader key). As a combo candidate it is buffered (`keyLockBuffered`) and arms on a quick release or after the combo window; a combo that fires leaves no arming behind. `KEY_LOCK` is no combo action (`ADD_COMBO`, `generate_combos_cpp`, `validateConfigShape` and the app reject it) and `REPEAT` does not repeat it (`isRepeatableAction`).
- Dynamic macro: a locked key is recorded with its `DOWN` at the first press and its `UP` at the release of the lock (`noteDown` / `noteUp` in the master).
- `DACTYL_FW_VERSION` 27: an older master ignores `0x16F` and `SPLIT_OP_KEY_LOCK`; an older left half never sends `arg 1`. Flash both halves.
- Tests: `test_firmware_logic.cpp` (`test_key_lock_*`: mouse button held and released by a second press, key across halves, only the next input, layer keys, `KEY_LOCK` and macros not locked, `RELEASE_ALL`, standby, no host, no combo action, combo candidate), `test_split_hid.cpp` (`test_key_lock_*`: left mouse and key lock, `arg 0` not locked, link timeout, host loss, `RELEASE_ALL` of the left half, standby keeps physically held keys, validation), `test_left_split_keyboard.cpp` (`test_left_key_lock_*`), `tests/test_app_logic.js` and `tests/test_server.py` (code, label, round trip, combo rejection).

### Swap hands (`ACT_SWAP_HANDS`)

- `ACT_SWAP_HANDS` (`0x18B`, app name `SWAP_HANDS`, keycap label `Swap`) mirrors the key lookup of its own half. Use it when one hand holds the mouse or an object and the other hand must reach the keys of both sides.
- Hold: while `SWAP_HANDS` is held, a key press resolves the action of the mirrored matrix position (`swapMirrorCol` in `DactylLogic.h`). Finger rows: column `c` becomes `FINGER_COLS - 1 - c`. Thumb row (table `SWAP_THUMB_MIRROR` in `DactylMatrixConstants.h`, one per half): right `R5C0`<->`R5C3`, `R5C1`<->`R5C4`, `R5C2`<->`R5C6`, `R5C5` stays; left `R5C1`<->`R5C4`, `R5C2`<->`R5C5`, `R5C3`<->`R5C6`, `R5C0` stays. The mirror is an involution. It uses the layer, tap, hold and double-tap actions of the mirrored key (`resolveKeyActions`).
- Tap time: `swapHandsRelease` uses the scan time of the matrix event (`swapEventMs`), so a replayed release from the deferred queue measures the real press length. A key that a combo consumed is no tap.
- Tap (press and release inside the tapping term with no other key press): arms a one-shot swap (`swapArmed`) for the next key press. That press clears it. A tap while a swap is locked releases the lock.
- An armed swap has no timeout, like `OSL_n`: it waits for the next key press or a reset trigger. A key press of another key clears the armed swap and breaks a running double-tap.
- Double-tap (second tap inside the tapping term): locks the swap (`swapLocked`) until the next tap of `SWAP_HANDS`.
- A `SWAP_HANDS` key never mirrors itself, so a lock can always be released.
- Release while a key is held: `dispatchRelease` reads `pressedAction[r][c]`, which holds the action of the press. The mirrored action therefore releases cleanly, whatever the swap state is at the release.
- Reset: `oslClearAll()` calls `swapClearAll()`. It runs on `RELEASE_ALL`, link timeout, host loss, entering config mode and a BLE host switch. `enterStandby()` on both halves calls `swapClearAll()` too. In config mode the action does nothing.
- Scope: the state lives on each half. The left half and the master do not share it. `SWAP_HANDS` is no combo action (`ADD_COMBO`, `generate_combos_cpp`, `validateConfigShape` and the app reject it) and `REPEAT` does not repeat it.
- `DACTYL_FW_VERSION` is 32. Flash both halves.
- Tests: `test_firmware_logic.cpp` (`test_swap_hands_*`: mirror table, hold, thumb keys, tap one-shot, double-tap lock, slow second tap, hold with key press, reset triggers, config mode, no combo action), `tests/test_app_logic.js` and `tests/test_server.py` (code, label, round trip, combo rejection).

### Repeat the last action (`ACT_REPEAT`, `SPLIT_OP_REPEAT`, `SPLIT_OP_REPEAT_RUN`)

- `ACT_REPEAT` (`0x169`, app name `REPEAT`) runs the last resolved action again. A held `REPEAT` acts like the held original: it presses the action and releases it with the key. Each half records its own last action in `lastRepeatAction` (`DactylLogic.h`, `recordRepeatAction`). It stores the resolved action, not the matrix position.
- Recorded: plain codes, media keys, mouse actions, key pairs, umlauts, macros, one-shot modifiers, `CAPS_WORD` and combo actions (`KEY_PRESS` and `MODIFIER_HOLD`). Not recorded: layer actions (`MO_n`, `TG_n`, `LAYER_UP`, `LAYER_DOWN`, combo `LAYER_TOGGLE`), a lone modifier code `0x80`..`0x87` (a repeated `Shift` would only press `Shift`) and `REPEAT` itself. `REPEAT` before the first recorded action sends nothing.
- An action counts only when it reaches the host: nothing is recorded without a Mac connection or in config mode. The member keys of a combo never count, because a triggered combo consumes both keys. A combo candidate counts when its key is really sent: on a quick release, after `comboTimeoutMs` (`processDeferredKeys`) or at a forced hold (`activateTapHoldAsHold`).
- `REPEAT` works as tap, hold and double-tap action, as a forced hold and as a buffered combo candidate. A combo can run `REPEAT` with `KEY_PRESS` (a tap on the first member key); `server.py` (`ONE_SHOT_CPP`), the combo dialog and `ADD_COMBO` reject it with `MODIFIER_HOLD`. Older saved configs with that pair are migrated to `KEY_PRESS`, like one-shot keys. A key pair or a macro step does not accept it.
- A running repeat always ends with its key, also after a host loss or a combo (`dispatchRelease`, `cancelTapHoldForCombo`). `releaseHeldKeyPairs` (`CLEAR_PAIRS`) also releases a pair that a `REPEAT` holds, on this half and (hook `REPEAT_RELEASE_HELD_PAIRS`) on the left half for a run of the master.
- Across both halves: each half runs a repeat itself, because only it knows its key pairs and macros. The master knows which half recorded last (`SplitLeftHeld.repeatLastLeft`). The left half sends the note `SPLIT_OP_REPEAT` with `code` 2 after each recorded action (`REPEAT_RECORDED`) and with `code` 3 when it starts (nothing recorded). A recorded right action clears the flag. A note needs no Mac connection. A link timeout leaves the flag: the left half keeps its action.
  - `REPEAT` on the right, left recorded last: the master sends `SPLIT_OP_REPEAT_RUN` (master -> left only, `code` 1 = press, 0 = release, `arg` = number 1..127) and the left half repeats its own action (`processMasterRepeat`, `dactyl_left.ino`).
  - `REPEAT` on the left: the left half sends `SPLIT_OP_REPEAT` with `code` 1 or 0 and a key number `arg` 1..127 (retry of the send queue; a release drains a full queue first). Right recorded last: the master repeats its own action (`SPLIT_REPEAT_REQ_RIGHT`). Left recorded last: the master sends `REPEAT_RUN` back (`SPLIT_REPEAT_REQ_LEFT`).
  - A retry duplicate has the same key number and changes nothing. A press with another number replaces an open key whose release was lost (`splitRepeatLeftKey`); the master ends the old repeat first.
  - The master has no send queue with retry. It sends each `REPEAT_RUN` again after `SPLIT_REPEAT_COPY_MS` (30 ms) and `SPLIT_REPEAT_COPY2_MS` (100 ms), also after a failed `esp_now_send`, and refreshes an open press every `SPLIT_REPEAT_REFRESH_MS` (1 s) with the same number (`SplitRepeatSender`). The left half ends a run without a refresh after `SPLIT_REPEAT_RUN_TIMEOUT_MS` (3 s), so a lost release holds no key for good (`splitRepeatLeftRunTick`). A new press number replaces an open run and releases its action first (`splitRepeatLeftRunEvent`).
  - A late copy of an older press must not cut a newer run short: the left half takes a press only when its number is newer in the cyclic order 1..127 (`splitRepeatSeqNewer`), or when the left half was quiet for `SPLIT_REPEAT_STALE_MS` (500 ms; a restarted master starts its numbers at a random value).
  - The left half receives `REPEAT_RUN` in an ordered ring (`masterRepeatRing`), not in the "newest wins" mailbox of the layer state, because press and release must both arrive. The ring is reset before the receive callback is registered.
  - The note `code` 2 is kept until the send queue has room (`leftRepeatServiceNote`), so a full queue never loses it. The left half sends it again every `LEFT_REPEAT_NOTE_EVERY_MS` (5 s) while it holds a recorded action, so a restarted master (end of config mode) or a note that was lost after all retries still learns it. A `REPEAT` press on a full queue is dropped without a key number, so its release sends nothing; the release itself drains a full queue first (`leftRepeatRelease`, `queuePushAfterDrain`). The master releases a key pair that a left `REPEAT` key holds before `CLEAR_PAIRS` changes the table (`splitRepeatTakeHeldPair`; `ADD_PAIR` only appends and keeps the indices).
  - `RELEASE_ALL`, a link timeout, a full receive ring and a host loss end an open left `REPEAT` key (`splitRepeatLeftCancel`): the master releases its own action or sends the `REPEAT_RUN` release. A `REPEAT` press counts as a left key press: the master sends its waiting double-tap taps first (`onBeforeLeftPress`).
  - If `configMutex` is busy (BLE `GET_INFO`) for 200 ms, the master prints `WARN: configMutex busy` and keeps a release or `RELEASE_ALL` (`SplitRepeatDeferred`, `splitRepeatDeliver`). The next pass runs it, so the right key never stays held at the Mac. A second release of another key replaces the first with `RELEASE_ALL`. A press that arrives while the mutex is busy is lost.
- The logic of both halves is in `DactylSplitHid.h` (`splitRepeatMasterEvent`, `splitRepeatLeftRunEvent`) and `DactylLeftLogic.h` (`LeftRepeatLink`); the `.ino` files only connect it (`onSplitRepeat`, `processMasterRepeat`). `test_split_hid.cpp` and `test_left_split_keyboard.cpp` test it. The wiring in the `.ino` files has no host test.
- Mixed firmware (`DACTYL_FW_VERSION` 3): an older master rejects op 21, so `REPEAT` on the left does nothing and the master never learns the left action; an older left half rejects op 22, so `REPEAT` on the right after a left key does nothing. Each half still repeats its own last action when it recorded last. Flash both halves.
- A spoofed left MAC can send `SPLIT_OP_REPEAT` and run the last right action again (for example a macro). It carries no keycode and no config command; the ESP-NOW encryption (`DactylSplitCrypto.h`) closes it unless the key leaks. A spoofed master MAC can send `REPEAT_RUN` and run the last left action again. It can also keep a held one pressed: a refresh packet with the same number renews the run timeout. The encryption is the only defense.
- Known limits: `REPEAT` of a macro starts nothing while another macro runs (like every macro start). A key pair index that is empty on the half that repeats it sends nothing. The latency of a repeat across both halves (one radio hop) and the hand-over between the halves are not measured on hardware.

### Alternate repeat (`ACT_ALT_REPEAT`)

- `ACT_ALT_REPEAT` (`0x16B`, app name `ALT_REPEAT`, keycap label `AltRep`) runs the opposite of the last recorded action. A user who moves too far with an arrow key, or deletes too much, taps it to go back. It uses `lastRepeatAction`, `repeatStartAt(r, c, alt)` and `repeatPress` of "Repeat the last action"; it records nothing itself, so a second tap gives the opposite again, not the original.
- The pure function `altRepeatAction(code)` (`DactylCommon.h`) holds the table and returns `0` for an action without an opposite; the key then sends nothing. Pairs: Left and Right, Up and Down, Page Up and Page Down, Home and End, Backspace and Delete, wheel up (`0x133`) and wheel down (`0x134`), volume up (`0x122`) and volume down (`0x123`), next track (`0x124`) and previous track (`0x125`). Everything else (letters, `Play/Pause`, `Mute`, mouse buttons, key pairs, macros) has no opposite.
- Held modifiers stay applied. `ALT_REPEAT` presses only the opposite key, so `Cmd` held + `ALT_REPEAT` after `Left` sends `Cmd` + `Right`. A lone modifier is never recorded, so it never replaces the last action.
- `isRepeatKeyAction()` is true for `REPEAT` and `ALT_REPEAT`. Every place that handles `REPEAT` (tap, hold, double-tap, forced hold, buffered combo candidate, combo action, release after host loss, `CLEAR_PAIRS`) handles `ALT_REPEAT` the same way. A combo accepts it only with `KEY_PRESS` (`ONE_SHOT_CPP` in `server.py`, `isOneShotOrCapsWordCode` in the app, `ADD_COMBO`); older saved configs with `MODIFIER_HOLD` migrate to `KEY_PRESS`. Neither is a key pair member or macro step.
- Across both halves like `REPEAT`, with a flag in the same operations (no new op, so the op numbers stay):
  - `SPLIT_OP_REPEAT` `code` 4 (`SPLIT_REPEAT_CODE_ALT_PRESS`) = `ALT_REPEAT` key on the left half pressed, `arg` = key number 1..127. The release is `code` 0 with the same number. `code` 1 stays `REPEAT`.
  - `SPLIT_OP_REPEAT_RUN` `code` 2 (`SPLIT_REPEAT_RUN_CODE_ALT_PRESS`) = master -> left: press and run the opposite of the last left action. `code` 1 stays `REPEAT`, `code` 0 releases.
  - The half that executes forms the opposite of its own last action (`altRepeatAction`), because only it knows its last action. The master decides who executes with the same rule as `REPEAT` (`repeatLastLeft`). Retry copies, number order and timeouts are the same as for `REPEAT`; a retry duplicate with the same number changes nothing. The refresh of an open press keeps the flag (`SplitRepeatSender.openAlt`), so a half that missed the first packet still runs the opposite.
  - `parseSplitHidPacket()` accepts `REPEAT` `code` 4 only with a number `arg` 1..127. `parseSplitMasterPacket()` accepts `REPEAT_RUN` `code` 0..2 with a number.
- `DACTYL_FW_VERSION` 23: an older master rejects `REPEAT` `code` 4, so `ALT_REPEAT` on the left does nothing; an older left half rejects `REPEAT_RUN` `code` 2, so `ALT_REPEAT` on the right after a left key does nothing. Flash both halves.
- A spoofed MAC can send the new codes like the old ones; the risk is the same as for `REPEAT` (no keycode, no config command, encryption closes it unless the key leaks).
- Tests: `test_firmware_logic.cpp` (`test_alt_repeat_*`: each pair in both directions, no opposite, held modifiers, hand-over with the flag, combo), `test_split_hid.cpp` (`test_alt_repeat_*`: packets, master decision, run on the left half), `test_left_split_keyboard.cpp` (`test_left_alt_repeat_key_queues_the_alt_press_code`), `tests/test_app_logic.js` and `tests/test_server.py` (code, label, combo rule).

### Custom alternate repeat pairs (`userAltRepeats`)

- Up to 16 own pairs `{ key, alt }` per half (`MAX_ALT_REPEATS`, `AltRepeatPair`, 2 bytes, keyboard codes `1..255`, modifiers allowed). `ALT_REPEAT` checks this table first and the fixed table of "Alternate repeat" second (`altRepeatResolve()` in `DactylLogic.h`; `altRepeatCustom()` in `DactylCommon.h`). A pair is directed: `e -> u` says nothing about `u -> e`. The first entry with the same `key` wins, and the commands refuse a second entry with the same `key`.
- Commands (both halves, also over BLE in config mode): `CLEAR_ALT_REPEATS` (RAM), `ADD_ALT_REPEAT <key> <alt>` (RAM, `ERR ARGS` for a value outside `1..255`, `key` equal to `alt`, a missing or extra value, a duplicate `key` or a full list; the app and `server.py` reject `key` equal to `alt` too), `SAVE_ALT_REPEATS` (NVS). NVS keys `num_altrep` (count) and `altrep_data` (`AltRepeatPair[count]`); the data is written first and the count last. An empty saved list (count `0`) replaces the compiled-in list at boot. A count that does not match the data length, or a zero code, keeps the compiled-in list. A layout flash from the app (new `KEYMAP_DEFAULTS_ID`) removes both keys, like key pairs.
- `GET_CONFIG` sends `ALTREP_COUNT:<n>` and `ALTREP_DATA:{"o":<offset>,"e":[[key,alt],...]}` (8 entries per line, `GET_CONFIG_ALTREP_PER_LINE`). Firmware before `DACTYL_FW_VERSION` 34 sends neither line; the app then keeps its local list and does not compare it.
- Config: `altRepeats` (`[{ "key": "KEY_E", "alt": "KEY_U" }]`) per half. `server.py` (`generate_alt_repeats_cpp`) renders the marked block `[[[START_ALT_REPEATS]]]` in both sketches and rejects a non-list, more than 16 entries, a code that is not a keyboard code and a duplicate `key`. `js/config-model.js` validates and normalizes the list (`isValidAltRepeat`, `hasDuplicateAltRepeat`; normalizing drops invalid and duplicate entries), and the layout diff and the load from the device (`buildConfigFromSnapshot`) include it. The full sync (`js/config-sync.js`) sends `CLEAR_ALT_REPEATS`, the pairs and `SAVE_ALT_REPEATS` after the leader phase; firmware without the command answers `ERR UNKNOWN` and the phase is skipped. `countSyncSteps` counts pairs + 1.
- App: the card "Alt-Repeat-Paare" (`js/alt-repeats-ui.js`) adds and deletes pairs (pending change, undo). The button "+ Alt-Repeat-Paare" in the finger-load panel of `index.html` (handler `addAltRepeatsFromSameFingerPairs` in `js/alt-repeats-ui.js`, top pairs from `topSameFingerPairs` in `js/config-model.js`) creates both directions of each top same-finger pair from the layer 0 tap actions (`altRepeatsFromSameFingerPairs` in `js/config-model.js`); an existing `key`, a non-keyboard action, two equal keys and a full list are skipped.
- Across both halves: the half that executes forms the opposite, so the master uses its own list for an `ALT_REPEAT` key on the left half after a right action (`env.altAction` in `splitRepeatMasterEvent`), and the left half uses its own list for `REPEAT_RUN` code 2 (`splitRepeatLeftRunEvent`). Each sketch's repeat env returns `altRepeatResolve()`.
- The finger-load button reads the `tap` field of layer 0 for each position (never the hold action), because the typing statistics count positions, not layers. A key that holds another action on a higher layer is not considered.
- `DACTYL_FW_VERSION` 34: an older half answers `ERR UNKNOWN` to the commands, so the app skips the phase and the pairs do not reach the device. Flash both halves.
- Config mode risk: a nearby BLE client can store up to 16 pairs per half with `ADD_ALT_REPEAT`. They change what `ALT_REPEAT` sends and are not visible on the key matrix; `GET_CONFIG` reads them back. The 3 min limit and the physical combo stay the only protection (see `AGENTS.md`, "BLE Command Authorization").
- Tests: `test_firmware_logic.cpp` (`test_custom_alt_repeat_*`, `test_alt_repeat_commands_validate_and_clear`, `test_alt_repeats_persist_in_nvs`, `test_alt_repeats_get_config_sends_the_list`), `test_split_hid.cpp` (`test_alt_repeat_custom_pair_applies_on_the_master_local_press`, `test_alt_repeat_custom_pair_applies_on_the_left_run`), `tests/test_app_logic.js` (validation, finger-load button, `GET_CONFIG` round trip, sync order and step count), `tests/test_server.py` (`test_alt_repeat_*`).

### Mod-Tap / Layer-Tap (`HOLDMAP`)

- Each key has a tap action (`KEYMAP`) and an optional hold action (`HOLDMAP`, `0` = none), both persisted in NVS (`keymap`, `holdmap`) and generated by `server.py` between `[[[START_KEYMAP]]]` / `[[[START_HOLDMAP]]]` markers.
- A key with a hold action resolves as **hold** when it is held for the tapping term (`tappingTermMs`, default `TAPPING_TERM_MS` 200 ms), also if the release is processed before the next tick, or when another key is pressed while it is undecided; otherwise its release sends the tap action. A forced hold of a combo candidate is sent to the host immediately, before the dependent key.
- A triggered combo cancels the tap-hold decision of both member keys; their individual tap or hold actions do not execute. A hold action without a tap action behaves as a normal key.
- Transparent fallback to Layer 0 applies only when tap, hold and double-tap of the active layer are all `0`.
- The tapping term is a setting per half: `tappingTermMs` (100..500 ms, default 200), command `SET_TAPPING_TERM <ms>`, NVS key `tap_term`, `DEVICE_INFO` field `tapping_term_ms`, config field `settings.tappingTermMs`, rendered by `server.py` in `[[[START_SETTINGS]]]`. It controls Mod-Tap and Tap-Dance; the combo window stays `comboTimeoutMs`.
- The hold-tap decision mode is a setting per half: `holdTapMode` (0 = `holdOnOtherKeyPress`, 1 = `permissiveHold`, 2 = `tapPreferred`, default 0), command `SET_HOLD_MODE <0|1|2>`, NVS key `hold_mode`, `DEVICE_INFO` field `hold_tap_mode`, config field `settings.holdTapMode`, rendered by `server.py` in `[[[START_SETTINGS]]]`.
  - Mode 0 (`HOLD_MODE_OTHER_KEY_PRESS`): any other key press while the mod-tap key is pending immediately resolves it as hold.
  - Mode 1 (`HOLD_MODE_PERMISSIVE`): a rolled key press remains pending; if the second key is both pressed and released within the tapping term (nested press-release pair), the mod-tap key resolves as hold. If the second key stays held or rolls, the mod-tap key resolves as tap upon its release.
  - Mode 2 (`HOLD_MODE_TAP_PREFERRED`): other key presses never force a hold resolution. The mod-tap key resolves as hold only when held past `tappingTermMs`.
- Quick tap is a setting per half: `quickTapMs` (0..500 ms, default 0 = off), command `SET_QUICK_TAP <ms>` (answers `OK SET_QUICK_TAP <ms>`, `ERR ARGS` for a non-number or a value outside 0..500, `ERR NVS` when the write fails), NVS key `quick_tap`, `DEVICE_INFO` field `qt` (firmware 45 and newer; older firmware sends `quick_tap_ms`, the app reads both), config field `settings.quickTapMs`, rendered by `server.py` in `[[[START_SETTINGS]]]`. The full sync sends it as an optional step (older firmware answers `ERR UNKNOWN`).
  - Rule: when the user presses a Mod-Tap key again less than `quickTapMs` after its tap (release), the key resolves as tap at once and stays held, so the host repeats the character. No hold action runs, even when the key is held past the tapping term. The window starts at the release of the tap. A held quick tap that ends also starts a new window.
  - Only an uninterrupted tap counts: a press of any other key clears the stored tap time of all keys (`quickTapValid[][]`, `quickTapAt[][]`, `quickTapHeld[][]` in `DactylLogic.h`). A key with a double-tap action keeps the Tap-Dance behavior. A key without tap or hold action is not affected. `0` changes nothing.
- Hold only after a typing pause is a setting per half: `requirePriorIdleMs` (0..500 ms, default 0 = off), command `SET_PRIOR_IDLE <ms>` (answers `OK SET_PRIOR_IDLE <ms>`, `ERR ARGS` for a non-number or a value outside 0..500, `ERR NVS` when the write fails), NVS key `prior_idle`, `DEVICE_INFO` field `require_prior_idle_ms`, config field `settings.requirePriorIdleMs`, rendered by `server.py` in `[[[START_SETTINGS]]]`. The full sync sends it as an optional step (older firmware answers `ERR UNKNOWN`). `DACTYL_FW_VERSION` is 22.
  - Rule: when the user presses a Mod-Tap key less than `requirePriorIdleMs` after the last key press of either half, the key resolves as tap at once (no wait for the tapping term, no hold). A longer pause keeps the normal decision of `holdTapMode`. The window ends at exactly `requirePriorIdleMs` (a press at that distance is not recent).
  - The last key press is `priorKeyAt` in `DactylLogic.h` (`notePriorKeyPress`, `priorKeyRecent`). Every press of the own matrix sets it after the check, so a held key never counts for its own press. The master also sets it for a press of the left half: `onSplitBeforeLeftPress` (HID press) and `onSplitKeyEvent` (pressed matrix event, also for a left key that sends no HID press). The left half sets it from the `SPLIT_OP_HOLD_PENDING 1` of the master (`masterPriorPressMs` in `dactyl_left.ino`), because the master sends no other op for every press (`ACTIVITY` is throttled to 10 s). A master key without a hold action sends no `HOLD_PENDING`, so the left half sees only the master Mod-Tap presses. A lost packet or a key press of the master without a Mod-Tap key leaves the left window shorter; the effect is a hold instead of a tap in rare cases, never a stuck key.
  - Exempt: Layer-Tap with `MO_n` as hold action and keys with a double-tap action keep their behavior. A key without a tap or hold action is not affected. `resetTapHold()` clears the stored time.
  - Mixed firmware: needs `DACTYL_FW_VERSION` 22 or newer on both halves (the left half learns the master presses from `HOLD_PENDING`; an older left half still works but sees no master press).
  - Time base: only a key press at or before the pressed key counts (32-bit difference). A press that was noted later than the scan time of a held-back key, and a stored press older than about 24 days, do not count. The left half stores the receive time of the master `HOLD_PENDING 1` (`MasterPriorPress` in `DactylLeftLogic.h`), so a master press that arrives a few ms after the left scan time is missed.
- Opposite-hand rule (chordal hold) is a setting per half: `chordalHold` (0 = off, default; 1 = on), command `SET_CHORDAL_HOLD <0|1>` (answers `OK SET_CHORDAL_HOLD <n>`, `ERR ARGS` for any other value, `ERR NVS` when the write fails), NVS key `chordal`, `DEVICE_INFO` field `chordal_hold`, config field `settings.chordalHold`, rendered by `server.py` in `[[[START_SETTINGS]]]`. The full sync sends it as an optional step (older firmware answers `ERR UNKNOWN`).
  - Rule: when a Mod-Tap key is open and the user presses another key of the same half, `resolvePendingTapHoldsAsTapSameHalf()` resolves the open key as tap at once (press and release), and the second key follows. It runs before the decision of `holdTapMode`, so it applies in all three modes. It runs on the half that owns the keys; a left key pressed on the left half is decided by `DactylLeftLogic.h` and the shared `DactylLogic.h` on that half.
  - A press of the other half keeps the decision of `holdTapMode` (`SPLIT_OP_HOLD_RESOLVE` still resolves open keys as hold).
  - Exceptions that keep the decision of `holdTapMode`: the thumb row (`CHORDAL_THUMB_ROW`, the last matrix row) as Mod-Tap key and as second key, Layer-Tap keys with a `MO_n` hold action, keys with a double-tap action, and keys without a tap action (hold-only keys). A key that already resolved as hold stays hold.
  - Combos: a Mod-Tap key whose combo partner is pressed inside `comboTimeoutMs` is not resolved as tap. `checkUserCombos()` triggers the combo in the same scan and the tap does not run.
  - Buffered presses: in modes 1 and 2 a press that waits in the deferred queue (behind an open Layer-Tap key) applies the rule when `replayDeferredQueue()` plays it.
  - Quick tap: the tap of the rule does not start a quick-tap window (`quickTapValid` stays unchanged); only the tap on release does.
  - Order with "Hold only after a typing pause": the chordal check runs first. The pause check applies only to a key that the chordal rule did not resolve.
  - Mixed firmware: needs `DACTYL_FW_VERSION` 20 or newer on the half that holds the key.
- Chordal Hold per-key exclusion list is a setting per half: `chordalHoldExclusions` (64-bit mask, bit `r * NUM_COLS + c`; 42 keys use bits 0..41; default 0 = no exclusion). `DACTYL_FW_VERSION` is 53.
  - Rule: when a Mod-Tap key is marked in the mask, `resolvePendingTapHoldsAsTapSameHalf()` skips it. The key stays open on a press of another key of the same half. The decision of `holdTapMode` or the tapping term then resolves it, normally as hold. A key that is not marked keeps the chordal hold rule. The rule applies to all layers, because the mask uses the matrix position.
  - Commands: `SET_CHORDAL_EX <hex>` (1 to 16 hex digits, whole mask; answers `OK SET_CHORDAL_EX`, `ERR ARGS` for a non-hex value or a bit above bit 41, `ERR NVS` when the write fails), `ADD_CHORDAL_EX <r> <c>` (sets one bit; answers `OK ADD_CHORDAL_EX`, `ERR ARGS` for a position outside the matrix) and `CLEAR_CHORDAL_EX` (sets the mask to 0; answers `OK CLEAR_CHORDAL_EX`).
  - NVS key: `chordal_ex` (8 bytes, `uint64_t`). The firmware ignores a stored value with another length. It clears the bits above bit 41 on load.
  - Report: `GET_CONFIG` sends the line `CHORDAL_EX:<16 hex digits>` before the combo lists. `DEVICE_INFO` does not carry the mask, because the line must stay below the 512 byte limit of a BLE notification.
  - App: the Key-Inspector shows the checkbox "Chordal-Hold-Ausnahme" for a key with a hold action. The config field is `settings.chordalHoldExclusions` (16 hex digits). The full sync sends `SET_CHORDAL_EX` as an optional step (older firmware answers `ERR UNKNOWN`). Export, import and the layout diff include the mask. The diff compares the mask only when the device sends `CHORDAL_EX`.
  - `server.py` writes the mask into `[[[START_SETTINGS]]]` as `uint64_t chordalHoldExclusions`.
  - Mixed firmware: needs `DACTYL_FW_VERSION` 53 or newer on the half that holds the key.
- Retro Tap is a setting per half: `retroTap` (0 = off, default; 1 = on), command `SET_RETRO_TAP <0|1>` (answers `OK SET_RETRO_TAP <n>`, `ERR ARGS` for any other value, `ERR NVS` when the write fails), NVS key `retro_tap`, `DEVICE_INFO` field `rt`, config field `settings.retroTap`, select `#retroTapSelect`. The app sends the command as an optional step of the full sync (older firmware answers `ERR UNKNOWN`).
  - Rule: when a Mod-Tap or Layer-Tap key resolved as hold and the user releases it with no key press on either half in between, `tapHoldOnRelease()` sends the tap action (press and release) after the release of the hold action. Any key press of the own matrix cancels it for all open holds; a press of the left half cancels it on the master.
  - Counter: `retroPressSeq` in `DactylLogic.h` rises in `notePriorKeyPress()`, which runs for each press of the own matrix and, on the master, for each press of the left half. `tapHoldOnPress()` stores the value in `TapHoldKey.retroSeq`; an equal value at the release means no press in between.
  - Exempt: keys with a double-tap action (`tapHoldDtap`), keys without a tap action and keys whose hold action equals the tap action (the hold already sent it).
  - `DEVICE_INFO` shortens `require_prior_idle_ms` to `pi` (line limit 512 bytes). The app reads both names.
  - Both halves: the master sends `SPLIT_OP_MASTER_PRESS` (master -> left only, no values, no retry) to the left half for each press of its own matrix. The left half notes it with `masterPriorPressNote` and `notePriorKeyPress`, so a press on the master cancels an open Retro Tap on the left half. The master sees every left press (`onSplitBeforeLeftPress`). The retro tap itself calls `oslNoteKeyPress`, like every key press.
  - Mixed firmware: needs `DACTYL_FW_VERSION` 31 or newer on both halves; a left half without `MASTER_PRESS` ignores the packet and misses master presses.

### Hold-tap flavor per key (`HOLDFLAVORMAP`)

- Each key has an optional own hold-tap flavor (`HOLDFLAVORMAP`, `0` = `holdTapMode` of the half, `1..3` = fixed mode). The value is the mode plus one: `1` = hold on other key press, `2` = permissive hold, `3` = tap preferred. Example: permissive hold for home row mods and a quick hold for thumb keys.
  - `resolveKeyHoldFlavor()` reads it with the same layer fallback as `resolveKeyActions`; `tapHoldOnPress` stores it in `TapHoldKey.flavor`. `effectiveHoldMode(r, c)` returns the mode of the open key (the key value minus one, else `holdTapMode`). Never compare against `holdTapMode` directly in the hold logic.
  - A press of another key resolves only the open keys with mode `0` as hold at once (`resolvePendingTapHoldsAsHold(..., true)`). `pendingDeferMode()` gives the mode that buffers the next keys: the mode of the newest open key that is not mode `0`. A release uses the same mode.
  - The value acts only with a hold or double-tap action (and a tap action). `server.py` renders `0` for other keys.
  - NVS key `holdflv` (blob of `HOLDFLAVORMAP`, written by `saveKeymapToNVS` / `SAVE_NVS`). It exists when at least one key has a value, or when the compiled-in defaults carry values and the user cleared them (zero blob). A stored value above `3` counts as `0`.
  - `keymapDefaultsFingerprint()` includes `HOLDFLAVORMAP` only when it has a value, so firmware from before this feature keeps the stored layout.
  - Commands: `CLEAR_HOLD_FLAVORS` (RAM, `OK CLEAR_HOLD_FLAVORS`) and `SET_KF <l> <r> <c> <f>` (RAM like `SET_K`: no `OK`, only `ERR ARGS`). `SAVE_NVS` persists them. `GET_CONFIG` sends one `FLAVOR_DATA:{"l":<layer>,"k":[[...]]}` line per layer after `TERM_DATA:`.
  - Config: `layers[l][r][c].holdFlavor` (integer 1..3, absent = `0`). `server.py` (`cell_hold_flavor`, `generate_holdflavor_cpp`, block `[[[START_HOLDFLAVORMAP]]]` in both sketches) rejects values outside 0..3 with HTTP 400; a template without the block stays valid.
  - App: the inspector select `keyHoldFlavorSelect` (`js/editor.js`, `js/editor-events.js`). The full sync sends `CLEAR_HOLD_FLAVORS` as the last setting command (`optional: "args"`, quiet while no key has a value) and a `SET_KF` after each `SET_K` with a value. The layout diff compares the value when the device sends `FLAVOR_DATA`.
  - Split: the left half runs the same logic. The cross-half decision stays with the half mode: `splitDeferTakeResolveRequest` and `HOLD_RESOLVE` ignore the key flavor, so a press of the other half resolves an open key by the mode of the half. The key flavor acts for presses of the same half. `DACTYL_FW_VERSION` 46 added the commands and the NVS key: flash both halves.
  - Test: `test_hold_flavor_per_key_*` in `firmware/tests/test_firmware_logic.cpp` (half mode A, one key with mode B: only this key resolves with mode B), `test_holdflavor_codegen_and_range` in `tests/test_server.py`, "Hold-Tap-Variante je Taste" in `tests/test_app_logic.js`.

### Quick-tap term per key (`QUICKTAPMAP`)

- Each Mod-Tap key has an optional own quick-tap window (`QUICKTAPMAP`, per layer). `0` = `quickTapMs` of the half, `1` (`QUICK_TAP_KEY_OFF`) = quick tap off for this key, `10..500` = own window in ms. Example: off for `Space` and `Enter` so rapid double taps never become a held tap or a hold, and the half value for the letters.
  - `resolveKeyQuickTap()` reads it with the same layer fallback as `resolveKeyTapTerm`. `effectiveQuickTap(value)` gives the window in ms (`0` = off). Never compare against `quickTapMs` directly in the quick-tap logic. A key with its own window works also when `quickTapMs` of the half is `0`.
  - The window of a held quick tap is stored in `quickTapWin[r][c]`, so its release starts the next window with the same value.
  - The value acts only with a hold action and without a double-tap action (as quick tap itself). `server.py` renders `0` for other keys.
  - NVS key `quickflv` (blob of `QUICKTAPMAP`, written by `saveKeymapToNVS` / `SAVE_NVS`). Same rules as `holdflv`: it exists when at least one key has a value, or when the compiled-in defaults carry values and the user cleared them (zero blob). A stored value outside `0`, `1`, `10..500` counts as `0`.
  - `keymapDefaultsFingerprint()` includes `QUICKTAPMAP` only when it has a value.
  - Commands: `CLEAR_QUICK_TAPS` (RAM, `OK CLEAR_QUICK_TAPS`) and `SET_KQ <l> <r> <c> <v>` (RAM like `SET_K`: no `OK`, only `ERR ARGS`). `SAVE_NVS` persists them. `GET_CONFIG` sends one `QTAP_DATA:{"l":<layer>,"k":[[...]]}` line per layer after `FLAVOR_DATA:`.
  - Config: `layers[l][r][c].quickTap` (`0` = off, `10..500` = ms, absent = half value). The firmware value for "off" is `1`; `keyQuickTap` (`js/keycodes.js`) and `cell_quick_tap` (`server.py`) convert. `server.py` (`generate_quicktap_cpp`, block `[[[START_QUICKTAPMAP]]]` in both sketches) rejects other values with HTTP 400; a template without the block stays valid.
  - App: the inspector field `keyQuickTapInput` (`js/editor.js`, `js/editor-events.js`; empty = half value). The full sync sends `CLEAR_QUICK_TAPS` as the last setting command (`optional: "args"`, quiet while no key has a value) and a `SET_KQ` after each `SET_K` with a value. The layout diff compares the value when the device sends `QTAP_DATA`.
  - Split: the left half runs the same logic. `DACTYL_FW_VERSION` 55 added the commands and the NVS key: flash both halves.
  - Test: `test_quick_tap_per_key_*` in `firmware/tests/test_firmware_logic.cpp` (`Space` off and `A` with the half value: a double tap of `Space` never holds), `test_quicktap_codegen_and_range` in `tests/test_server.py`, "Quick-Tap je Taste" in `tests/test_app_logic.js`.

### Tap-Dance / Double-Tap (`DTAPMAP`)

- Each key has an optional own tapping term (`TAPTERMMAP`, ms, `0` = the value of the half, otherwise 100..500). Examples: ring and little finger home row mods need a longer term than a thumb key.
  - `resolveKeyTapTerm()` reads it with the same layer fallback as `resolveKeyActions`; `tapHoldOnPress` stores it in `TapHoldKey.term`, the double-tap window keeps it in `DoubleTapKey.term`. `effectiveTapTerm()` returns the key value, else `tappingTermMs`. It applies to the hold decision (tick and release) and to the double-tap window. The combo window stays `comboTimeoutMs`.
  - The value acts only with a hold or double-tap action (and a tap action). `server.py` renders `0` for other keys.
  - NVS key `tapterms` (blob of `TAPTERMMAP`, written by `saveKeymapToNVS` / `SAVE_NVS`). It exists when at least one key has a value, or when the compiled-in defaults carry values and the user cleared them (zero blob, so the compiled-in values do not return at boot). A missing key keeps the compiled-in values (old behavior); a stored value outside 0/100..500 counts as `0`. A flash from the app (`KEYMAP_DEFAULTS_ID != 0`) replaces it with the compiled-in values.
  - `keymapDefaultsFingerprint()` includes `TAPTERMMAP` only when it has a value, so firmware from before this feature keeps the stored layout.
  - Commands: `CLEAR_TAP_TERMS` (RAM, `OK CLEAR_TAP_TERMS`) and `SET_KT <l> <r> <c> <ms>` (RAM like `SET_K`: no `OK`, only `ERR ARGS`). `SAVE_NVS` persists them. `GET_CONFIG` sends one `TERM_DATA:{"l":<layer>,"k":[[...]]}` line per layer after `DTAP_DATA:`.
  - Config: `layers[l][r][c].tapTerm` (integer, absent = `0`). `server.py` (`cell_tap_term`, `generate_tapterm_cpp`, block `[[[START_TAPTERMMAP]]]` in both sketches) rejects values outside 0/100..500 with HTTP 400; a template without the block stays valid.
  - App: the inspector field `keyTapTermInput` (empty = value of the half) next to the double-tap action; the apply button rejects values outside 100..500. The full sync sends `CLEAR_TAP_TERMS` as the last optional setting command and a `SET_KT` after the `SET_K` of each key with a value. Firmware without `CLEAR_TAP_TERMS` answers `ERR UNKNOWN`: the app skips `SET_KT`, and shows the flash hint only when a key has a value. The layout diff compares the term only when the device sends `TERM_DATA`.
  - `DACTYL_FW_VERSION` 17 added the commands and the NVS key: flash both halves (the left half runs the same logic).
  - Test: `test_tapping_term_per_key_*` in `firmware/tests/test_firmware_logic.cpp` (300 ms stays a tap at 250 ms, a key without a value resolves as hold), `test_tapterm_codegen_and_range` in `tests/test_server.py`, "Tapping-Term je Taste" in `tests/test_app_logic.js`.
- Each key has an optional third action (`DTAPMAP`, `0` = none), persisted in NVS (`dtapmap`), generated by `server.py` between `[[[START_DTAPMAP]]]` / `[[[END_DTAPMAP]]]` (required marker), and sent by `GET_CONFIG` as `DTAP_DATA:`. A double-tap action works only together with a tap action.
- A key with a double-tap action holds back its tap: a second press within the tapping term (`tappingTermMs`) after the first release sends the double-tap action (held while the key is held). Otherwise the single tap is sent when the window expires, or immediately before another key press so the character order stays correct; this also applies to a key press of the other half (see "Double-tap across both halves"). Keys without a double-tap action keep sending without delay.
- Holding the key still resolves as hold; a key with double-tap but without hold action presses its tap action as a normal key when held. A triggered combo cancels a pending or active double-tap of its member keys.
- `keymapDefaultsFingerprint()` includes `DTAPMAP` only when it contains a non-zero code, so firmware updates from before Tap-Dance keep the stored layout. A missing `dtapmap` is filled with the compiled-in `DTAPMAP`.

### Combos per layer (`KeyCombo.layerMask`)

- Each combo has a layer mask (8 bits, bit `i` = the combo applies on layer `i`). The default is `0xFF` (all layers). A mask of `0` is invalid.
- `isComboCandidateKey(r, c)` (`DactylLogic.h`) buffers a key only when a combo with this key applies on the layer of the press. A key outside the mask sends at once, without the `comboTimeoutMs` delay. `checkUserCombos()` and `hasPressedComboPartnerInWindow()` use the same rule, so a combo never triggers on a layer outside its mask.
- The layer of a press is the result of `getActiveLayer()` at the press, including the tri-layer target. The firmware keeps it per key (`comboPressLayer1[][]`) until the release is handled. A layer change between press and release does not change the decision for this press.
- `ADD_COMBO <r1> <c1> <r2> <c2> <behavior> <action> [<mask>]`: the optional seventh value is the mask (1..255). A missing value means all layers. Mask `0`, a value above 255 and an eighth value return `ERR ARGS`. `COMBO_DATA` entries carry the mask as seventh value: `[r1,c1,r2,c2,behavior,action,mask]`. An app that reads a six-value entry (firmware before version 15) uses all layers.
- NVS format `combos_v2` (key `num_combos` keeps the count). The blob has a two-byte header `version` (`COMBO_NVS_VERSION` = 2) and `record size` (`COMBO_NVS_RECORD_BYTES` = 12), then one record per combo:

  | Byte | Field |
  |---|---|
  | 0..3 | `r1`, `c1`, `r2`, `c2` |
  | 4 | `behavior` |
  | 5..6 | `action` (little endian) |
  | 7 | `layerMask` |
  | 8..9 | `r3`, `c3`: third key (`0xFF` = none). A pair outside the matrix loads as "none". |
  | 10..11 | window in ms, little endian (`0` = `comboTimeoutMs`). A value above `COMBO_WINDOW_MAX` (500) loads as `0`. |

  The loader accepts the blob only when the version and the record size match and the length is `2 + count * 12` with `count` in 1..16. With a stored `num_combos` > 0 the loader reads a valid `combos_data` first (length `num_combos * 8`); only without it, it reads `combos_v2` and takes `count` from the blob length, not from `num_combos`. `num_combos` = 0 means an empty list. `SAVE_COMBOS` writes the blob, removes `combos_data`, then writes `num_combos`; an empty list writes `num_combos` = 0 first and removes the blobs only after that. So each power loss leaves a loadable list, and a list written by older firmware after a downgrade wins over a stale `combos_v2`. The third key and the window use the fields that were reserved in the first `combos_v2` records, so no new format was needed. A blob from firmware before version 24 has `0xFF 0xFF 0 0` there and loads as before. Raise `COMBO_NVS_VERSION` only for a change that old readers must not read.
- The old format `combos_data` (8 bytes per combo: `r1, c1, r2, c2, behavior`, one byte padding, `action`) stays readable. Its combos get the mask `0xFF`. `SAVE_COMBOS` writes `combos_v2` and removes `combos_data`.
- Server: `generate_combos_cpp` (`server.py`) validates `layerMask` (1..255, integer; missing = all layers) and renders it as seventh field only when it is not `0xFF`. App: `comboLayerMask`, `comboMaskLayers`, `comboAppliesOnLayer` (`js/config-model.js`); the combo dialog has one checkbox per layer, the table has the column "Ebenen". The file stores `layerMask` only for a restricted combo. The full sync appends the mask to `ADD_COMBO` only when it differs from all layers, so firmware without masks still accepts the other combos. The layout diff compares the mask.
- `lintLayouts`: two combos on the same keys count as a duplicate only when their masks overlap. A "toggle layer" combo is a way into a layer only from the layers of its mask. The hint `combo-hold-cancelled` lists only the layers of the mask.
- The live monitor combo alert (`checkActiveCombos`) does not check the mask: the app shows the viewed layer, not the hardware layer.
- Mixed firmware: a half with firmware before version 15 ignores the mask and reads only six values. Flash both halves.

#### Three-key combos and own window (`KeyCombo.r3`, `c3`, `windowMs`)

- A combo has two or three keys and a window. `windowMs` = `0` uses the global `comboTimeoutMs`; otherwise the combo uses its own window (`COMBO_WINDOW_MAX` = 500 ms in the firmware, 10..500 ms in the app and the server).
- A combo fires when all its keys are held and every pair of press times lies inside the window of that combo (`comboKeysInWindow`). With three keys this means the first and the last press are at most one window apart, not only the neighbours. A key that comes late, or a held key plus two fast ones, does not fire the combo; the buffered keys then go out as single keys.
- `isComboCandidateKey`, `wasComboRecentlyActive`, `isActiveComboMember` and `hasPressedComboPartnerInWindow` treat the third key like the other keys (`comboContainsKey`). A combo that fires marks all its keys as sent and cancels their Mod-Tap decision.
- A buffered candidate waits `comboBufferMs(r, c)` before it goes out as a single key: the largest window of the combos on its layer that contain the key (`comboTimeoutMs` without such a combo). A long own window therefore delays the single key by that time; use short windows for letter keys and longer ones for thumb keys.
- `ADD_COMBO <r1> <c1> <r2> <c2> <behavior> <action> [<mask> [<r3> <c3> [<windowMs>]]]`. Allowed are 0, 1, 3 or 4 optional values: the mask comes first, `r3 c3` as a pair (`255 255` = no third key), then the window (0 or up to 500). A third key must lie in the matrix and differ from the first two. Anything else returns `ERR ARGS`.
- `COMBO_DATA` entries carry `layerMask`, then `r3,c3,windowMs` (ten values) only for a combo with a third key or an own window. All other entries keep seven values, so an older app reads them. The app (`captureListLine`) completes shorter entries with `255,255,0`. `GET_CONFIG_COMBOS_PER_LINE` is 3 so the longest line stays below the BLE limit.
- Server: `generate_combos_cpp` reads `key3` (like `key1`, must differ from `key1` and `key2`) and `windowMs` (10..500, missing = global). It renders `{ r1, c1, r2, c2, behavior, action, mask, r3, c3, windowMs }` only when a third key or a window exists; the left half rejects `key3` on a missing key like the other keys.
- App: `comboThirdKey`, `comboKeys`, `comboWindowMs`, `isValidComboWindow` (`js/config-model.js`). The combo dialog has the optional select "Taste 3" and the field "Eigenes Zeitfenster"; the table shows the third key and the column "Fenster". The full sync appends `<mask> <r3> <c3> <windowMs>` to `ADD_COMBO` only for such combos, so combos with two keys and the global window still work with firmware before version 24. The layout diff compares both values. `lintLayouts` compares combos by their key set (a two-key and a three-key combo on the same keys are different combos); the warning `combo-subset` reports a two-key combo whose keys lie inside a three-key combo with an overlapping layer mask, because both fire when all three keys arrive.
- The firmware accepts the new values from version 24 on. Firmware before version 24 answers `ERR ARGS` to an `ADD_COMBO` with the new values; the app shows the usual sync error. Flash both halves. The live monitor alert (`checkActiveCombos`) shows the combo when all its keys are pressed.
- A Mod-Tap key of a three-key combo waits for the third key: while two keys are held inside the window and the window since the first press has not ended, `hasPressedComboPartnerInWindow` is true (`hasPendingThreeKeyCombo`), so the Mod-Tap hold and the chordal-hold tap do not send before the combo can fire. After the window the key resolves as usual.
- The firmware accepts a window of `0` or `COMBO_WINDOW_MIN` (10) to `COMBO_WINDOW_MAX` (500) in `ADD_COMBO` and in the NVS loader; other values return `ERR ARGS` or load as `0`. The loader also drops a third key that equals key 1 or key 2.

## Split Keyboard

### Split HID protocol (`DactylSplitHid.h`)

- The master's `bleKeyboard` is `SplitArbitratedKeyboard<DactylBleKeyboard>`: it tracks what each half holds in the shared HID report. An input is released in the report only when neither half holds it, so a right Shift release keeps a left Shift held. Uppercase and shifted ASCII codes (`'A'`, `'!'`) press Shift implicitly, and their release clears the Shift bit in the report; when the other half still needs Shift (it holds `KEY_LEFT_SHIFT` or a shifted code), the arbiter re-presses Shift in the same batched report. A release of `KEY_LEFT_SHIFT` keeps Shift in the report while the other half holds a shifted code. A right `releaseAll()` (combos, config combo) clears only right inputs and re-presses left ones inside one batched report (`beginReportBatch` / `endReportBatch` in `DactylBleComposite.h`).
- Left-side tracking (`SplitLeftHeld`): press only sets, release only clears, so retry duplicates of `*_PRESS` / `*_RELEASE` / `RELEASE_ALL` are harmless. `KEY_WRITE`, `MEDIA_WRITE` and `MOUSE_CLICK` are not idempotent: the left half therefore sends `write()` and `mouseClick()` as `PRESS` + `RELEASE` and skips a one-shot action on an input it holds itself. `MOUSE_SCROLL` is never retried (`splitEventRetryable`); a lost scroll step is better than a doubled one. The master still accepts the `*_WRITE` / `MOUSE_CLICK` ops (append-only protocol); `KEY_WRITE` of a held code and `MOUSE_CLICK` of a held button are ignored. `RELEASE_ALL`, the link timeout (`SPLIT_LINK_TIMEOUT_MS`, 3 s without packets) and a receive-ring overflow release **only** the inputs held by the left half. On an overflow, `splitProcessRx` first drains the ring and releases afterwards, so a press queued before the dropped release cannot stay held.
- `splitProcessRx()` holds the gating: without a Mac connection or in config mode the master executes nothing but keeps the link alive. On the transition to "no host" it clears both halves and the report, so no key is stuck after the Mac reconnects; physically held keys must be pressed again.
- The left half sends `RELEASE_ALL` right after ESP-NOW starts (boot, wake, return from config mode). Its acknowledgement also marks the link as up without waiting for the first heartbeat.
- The master prints each executed event as `SPLIT_HID:{"op":..,"code":..,"arg":..}`; the app ignores unknown serial lines.
- Live-monitor diagnostics: after the HID events of a left matrix change, the left half queues `SPLIT_OP_KEY_EVENT` (13) with `splitKeyEventCode(row, col, pressed, layer)` (bit 15 pressed, bits 8..10 layer before the action, bits 4..6 row, bits 0..2 column). It is queued only while the link is up and only while the send queue is at most half full (`queueKeyEventDiagnostic` / `queuePushDiagnostic`, `SPLIT_DIAG_QUEUE_LIMIT`), and it is never retried. A diagnostic event dropped at that limit is counted and reported as serial line `SPLIT_KEY_DROPPED (n verworfen)`; a dropped `KEY_EVENT` does not count toward the ESP-NOW restart. The master has no HID effect for it: `splitProcessRx` reports it through `onKeyEvent`, also without a Mac connection, at most `SPLIT_KEY_EVENTS_PER_RX` (4) per call (a flood from a spoofed left MAC must not block `loop()` with serial output; the excess is counted and printed as one line `SPLIT_KEY_RX_DROPPED (n verworfen)`; the left half's own send-side line is `SPLIT_KEY_DROPPED`), and it does not count as applied. It counts in `SplitRxReport.keyEvents` and resets the master's `lastActivityTime`, so a left key with action `0` keeps the master awake. The master prints it only on USB serial as `SPLIT_KEY:{"r":..,"c":..,"pressed":0|1,"layer":..}`; it never goes over BLE (keylogger protection). The app accepts `SPLIT_KEY` only from the master (`Dactyl.parseSplitKeyLine`, `js/side-routing.js`), assigns it to `Dactyl.getSplitSenderSide()` and drives the live monitor, heatmap and matrix test of the left half. A `SPLIT_KEY` release can be lost, so a press without release is released in the UI after `Dactyl.SPLIT_KEY_STALE_MS` (5 s, `createSplitKeyTracker`). A key with action `0` also sends `SPLIT_KEY`.

### Layer lock (`LAYER_LOCK`)

- `ACT_LAYER_LOCK` (`0x16A`, `DactylCommon.h`, `js/keycodes.js`, `server.py`) turns the highest held MO layer into a toggle layer. The held MO layers of both halves count (`momentaryLayers[]` and `remoteMomentaryLayers`).
- If that layer is already locked, the press releases it. Without a held MO layer, the press releases all locked layers (like `TG_0`).
- `applyLayerLock()` (`DactylLogic.h`) only writes `toggleLayers[]`. The layer sync (`SPLIT_OP_LAYER_STATE`) carries the lock to the other half; there is no new op.
- It works as tap, hold and double-tap action (`dispatchPress`) and as the action of a combo with the behavior `KEY_PRESS`. `ADD_COMBO`, the server and the app reject it with the behaviors `MODIFIER_HOLD` and `LAYER_TOGGLE`. `REPEAT` does not record it.
- `lintLayouts` counts `LAYER_LOCK` on a layer as a lock of that layer and as a way back from a locked layer.
- The firmware needs `DACTYL_FW_VERSION` 16 or higher on both halves, because the left half must know the code.

### One-shot layer (`OSL_0` .. `OSL_7`)

- `ACT_OSL_BASE + n` (`0x180` .. `0x187`, `NUM_OSL_ACTIONS`, `DactylCommon.h`; `OSL_n` in `js/keycodes.js` and `server.py`). The range sits behind the macros (`0x170` .. `0x17F`).
- A tap arms layer `n` for the next key press of either half. After that press, the layer is released. A second tap disarms it. A hold acts like `MO_n` and arms nothing: the key counts as held when it is held for at least its tapping term (`effectiveTapTerm`, `TAPTERMMAP`) or when another key of the same half is pressed while it is down. A tap or a hold key press of an `OSL` key never consumes the armed layer.
- State (`DactylLogic.h`): `oslArmed` (this half), `remoteOslArmed` (the other half), `oslHeld` (held keys; separate from `momentaryLayers[]`, and part of `localMomentaryLayerMask()` so the other half sees a hold like `MO_n`), `oslUsed`. `getActiveLayer()` counts armed layers like MO layers; an armed `OSL_0` forces layer 0 like `MO_0`. Several armed layers stack and the highest wins.
- The press that consumes the layer resolves its action on the armed layer first (`applyMatrixKeyChange` resolves the layer, then `oslNoteKeyPress` clears it). The release uses `pressedAction`, so the key releases the action that it pressed.
- The armed state goes to the other half with its own op `SPLIT_OP_OSL` (27, appended; `LAYER_STATE` has no free bits). `code` bits 0..7 = armed layers of the sender, bits 8..15 = armed layers of the receiver that the sender consumed with a key press; `arg` is 0 (`makeSplitOslEvent`, `splitOslArmed`, `splitOslUsed`). Both directions use it; the left half accepts it from the master in `parseSplitMasterPacket`. It has no HID effect and does not count as activity.
- The half that uses the armed layer reports the use (`oslUsedToSend`). The owner then clears the layer and sends its new state. The user half ignores a late refresh of a consumed bit (`remoteOslIgnore`, `OSL_IGNORE_MS`, until the owner state no longer holds the bit), so the layer is used only once.
- Send (`SplitOslSync`, `splitOslSendIfDue`): on each change, every `SPLIT_LAYER_REFRESH_MS` (1 s) while a layer is armed, every `SPLIT_OSL_USED_REPEAT_MS` (100 ms) while a consumed bit is open. The master uses `esp_now_send`, the left half the send queue. The mirror expires after `OSL_REMOTE_TIMEOUT_MS` (3 s) without a packet (`oslExpireRemote`).
- Clear: `RELEASE_ALL` of the left half, a link timeout, a buffer overflow and a host loss clear the mirror of the left half on the master (`splitProcessRx` calls `onOsl` with an empty state). A host loss, entering the config mode, `restartEspNow`, the config combo and, on the left half, a lost master connection clear all armed layers (`oslClearAll`); the Standby refresh counts armed layers as busy, so the mirror does not expire; the mirror of the other half is reported as consumed so it falls there too.
- `lintLayouts` counts `OSL_n` like `MO_n` as a way into layer `n`. It does not lock the layer, so it needs no way back.
- Combos reject `OSL_n` (`ADD_COMBO` actions run without `dispatchPress`; server, app and `validateConfigShape` return an error). Key pairs and macros allow only keyboard codes. `REPEAT` does not record it.
- The firmware needs `DACTYL_FW_VERSION` 21 or higher on both halves. Mixed firmware: an older half rejects op 27 as invalid, so only its own `OSL` works.
- Known limit: the `used` bits carry no sequence number. If the owner re-arms a layer within `OSL_IGNORE_MS` and both copies of its cleared state were lost, a repeated `used` packet clears the new arm once. The user taps again; no key is mis-sent.
- Spoofing: a transmitter with a spoofed MAC can arm a layer of the receiver for one key press per packet, or clear an armed layer (see `AGENTS.md`, "BLE Command Authorization"). The packet carries no keycode and no config data.
- Hardware check open: the radio path between the halves (consumed report) needs a test on the keyboard.

### Layer sync (`SPLIT_OP_LAYER_STATE`)

- An `MO_n`, `TG_n`, `LAYER_UP`, `LAYER_DOWN` or `LAYER_LOCK` on one half activates the layer on both halves. Each half resolves its own keys on the shared layer.
- Packet: `code` bits 0..7 = held MO layers of the sender, bits 9..15 = toggled layers 1..7. Left `arg`: 0 = `REPORT` (MO only, toggle bits 0), 1..127 = `SET` with a sequence number (the master takes the toggles). Master `arg` < 0: the packet always carries the toggles, bits 0..6 echo the number of the last left `SET` it took (0 = none). Built with `makeSplitLayerEvent` / `makeSplitMasterLayerEvent`, checked by `isValidSplitLayerEvent` (left) and `isValidSplitMasterLayerEvent` (master).
- MO layers belong to the sender. The receiver keeps them in `remoteMomentaryLayers` (`DactylLogic.h`); `getActiveLayer()` treats them like its own MO layers, a remote `MO_0` also forces layer 0. They expire after `SPLIT_LAYER_REMOTE_TIMEOUT_MS` (3 s) without a layer packet (other half off or in deep sleep).
- Toggles are one shared state in `toggleLayers[]`. The master leads. The left half sends `SET` with a new number after its own toggle change and keeps sending it (also in the refresh and in the release packet) until a master packet echoes that number or `SPLIT_LAYER_SET_TIMEOUT_MS` (2 s) pass (`setPending`, `splitLayerAcceptMasterToggles`). Until then it ignores master toggles, so an older master packet does not undo the change, also one with equal toggles. A failed queue push keeps the open `SET` and its number for the next attempt (`splitLayerSendIfDue`); a `SET` that was never queued ends when the toggle reverts before the next attempt (`setUnsent`). `restartEspNow` keeps an open `SET`, starts its time limit again and discards a mailbox packet from before the restart (`splitLayerLeftRestart`). The first left packet after boot or wake-up is a `REPORT`, so the left half takes the master toggles. The number starts at a random value (`esp_random`), so an echo from before a reboot rarely matches.
- Send (`SplitLayerSync`, `splitLayerTake`, `splitLayerSendIfDue`): each half sends on each change and every `SPLIT_LAYER_REFRESH_MS` (1 s) in active mode, or every `SPLIT_STANDBY_REFRESH_MS` (5 s) in quiet standby (standby active, no local key held and no MO layer active; `splitQuietStandby`, `splitRefreshIntervalMs`). The left half queues it in the send queue (retry there; refresh only while the queue is at most half full, `SPLIT_DIAG_QUEUE_LIMIT`; a full queue restores the state and sends again in the next pass). The heartbeat adapts to the same interval (`queueHeartbeatIfDue`), so a master without `LAYER_STATE` keeps the link up. The master has no retry: it sends each change a second time after `SPLIT_LAYER_REPEAT_MS` (30 ms), a failed `esp_now_send` restores the state; it refreshes only while the left link is up and sends at once when the link comes up (`splitLayerMasterAfterRx`).
- Release: before config mode and deep sleep each half sends its state without MO layers (`splitLayerReleaseEvent`; left: `queueSplitLayerRelease`, with an open `SET`, drains a full queue first with `queuePushAfterDrain`; master: `sendSplitLayerRelease`). The master also clears the left MO layers on the link timeout (`splitLayerMasterAfterRx`). The master receives through `splitLayerMasterReceive`, the left half through `splitLayerLeftReceive`. The master takes a left `SET` only with a new number; a retry or refresh with the number it already took changes nothing, so it cannot undo a later master toggle. A left `REPORT` clears the stored number: the left half then has no open `SET`, and its first packet after a reboot is a `REPORT`, so a later `SET` with the same number counts as new. The left send queue keeps the order, so an old `SET` never arrives after that `REPORT`.
- Receive: the master gets it through `splitProcessRx` (`onLayer`, also without a Mac connection; it does not count as activity, so the refresh does not keep the master awake). `onLayer` gets only the newest layer packet of each call, at most once, so a flood from a spoofed left MAC prints at most one `LAYER` line per `loop()`. The left half checks it with `parseSplitMasterPacket()` (master MAC, `ACTIVITY`, `TAP_FLUSH` or a master `LAYER_STATE`) and passes it through a mailbox (`SplitLayerMailbox`, seqlock, newest packet wins) to `loop()`.
- `applyRemoteLayerState()` prints `LAYER: SPLIT -> Layer <n>` when the active layer changes. The app follows every `LAYER:` line and every `KEY_PRESS.target_layer`, also from the non-edited half, because the displayed layer is shared.
- Mixed firmware: both halves need a firmware with `LAYER_STATE`. An older half rejects op 17 as invalid; each half then keeps its own layers, as before the sync. Flash both halves.
- Known limit: a key that is held while the layer changes keeps its action (the release uses `pressedAction`). A combo `LAYER_TOGGLE` also syncs, because it changes `toggleLayers[]`.

### Host LED state and Caps Lock indicator (`DactylHostLeds.h`)

- The host (Mac) writes the keyboard output report (report ID 1, one byte): bit 0 Num Lock, bit 1 Caps Lock, bit 2 Scroll Lock. `DactylBleComposite::onWrite` passes the bytes to `hostLedsOnReport()` (`DactylHostLeds.h`, no Arduino or BLE dependency, host-testable). It only stores the bits and a change counter, because `onWrite` runs in the BLE task. Upper bits are ignored; an empty report changes nothing. `onDisconnect` calls `hostLedsReset()`.
- `loop()` calls `hostLedsService()` (`DactylLogic.h`). It prints each change as `HOST_LEDS:{"num":0|1,"caps":0|1,"scroll":0|1}` on USB serial only, never over BLE. Two changes between two loops print one line with the latest state.
- `DEVICE_INFO` of the master carries `"host_leds":{...}` and `"caps_led":0|1`. The left half has no host and sends neither field (`DEVICE_INFO_HOST_LEDS_BITS` exists only in `dactyl_right.ino`).
- Setting `capsLed` (0|1, default 0, master only). Command `SET_CAPS_LED 0|1` answers `OK SET_CAPS_LED <v>`, `ERR ARGS` for other values, `ERR NVS` when the write fails (the RAM state stays). NVS key `caps_led`. When on, the onboard LED (GPIO 22, active low) lights while Caps Lock is on. When off, the firmware never touches the pin; switching the setting off while the LED is on switches it off once.
- App: pill `#capsLockPill` in the header, visible only while Caps Lock is on. The state comes from `HOST_LEDS` and `DEVICE_INFO.host_leds` over USB from the master and is dropped on disconnect (`forgetHostLeds`). Checkbox `#capsLedCheckbox` in the settings card (master only). The full sync sends `SET_CAPS_LED` as an optional step for the master (`buildSettingCommands`); firmware without it answers `ERR UNKNOWN`.
- `GET_INFO` over BLE in keyboard mode omits `host_leds` and `caps_led` (a nearby BLE client reads only `GET_INFO`); USB and config mode include them. The left half answers `SET_CAPS_LED` with `ERR UNKNOWN`. A BLE disconnect keeps the pill while USB to the master stays up (`forgetHostLeds`).
- Hardware check: GPIO 22 is not in the deep-sleep hold lists; check that the LED is off in deep sleep and that it follows Caps Lock again after the wakeup. Caps Lock on the Mac changes the pill and the LED (GPIO 22); the macOS Caps Lock key press must reach the master as an output report after a reconnect.

### Active mode pills (`MODE_STATE`)

- The master prints `MODE_STATE:{"cw":0|1,"nw":0|1,"sc":0|1,"sh":0|1,"ka":0|1,"ll":0|1,"lli":0..7}` on USB serial only, never over BLE. The fields are Caps Word, Num Word, Sentence Case, Swap Hands (held, armed or locked), Keep Awake and Layer Lock. `ll` is `1` while `layerLockedMask` is not zero (bit `MODE_STATE_LL`, `0x20`). `lli` is the highest locked layer, or `0` when no layer is locked.
- The line also changes when only `lli` changes. `applyLayerLock()` and `clearStatePress()` change `layerLockedMask`, and `modeStateService()` prints the new line in the next `loop()`.
- Pill: the app shows "Layer Lock (Ebene N)" in `#pillLayerLock` while `ll` is `1`. It hides the pill when `ll` is `0` and on disconnect. Lines without `ll` and `lli` (firmware before version 54) show no pill.
- `DACTYL_FW_VERSION` is 54. Flash both halves, because both halves share the version and the app reports a mismatch. An old app rejects no line, because it ignores the new fields.
- `modeStateService()` (`DactylLogic.h`, called from `loop()`) prints one line for each change of the state. It prints no line at start while all modes are off.
- `GET_INFO` over USB makes the next `loop()` print the line again, so an app that connects later sees the state. `GET_INFO` over BLE sets nothing and no notification carries the line (same rule as `HOST_LEDS` and `DM_REC`). The code exists only in the master (`DEVICE_INFO_HOST_LEDS_BITS`); the left half prints no line.
- App: `Dactyl.parseModeStateLine` (`js/side-routing.js`) accepts the line only from the master and only with the five mode flags `0` or `1` (`ll` and `lli` are optional). `js/serial.js` shows one pill per active mode in `#modeStatePills` (`index.html`) and drops the state on disconnect (`forgetModeState`, also in `js/ble.js`) unless USB to the master stays up.

### Layer auto-return timeout (`layerTimeoutMs`)

- Setting `layerTimeoutMs` (stored per half) (`0` = off, `1000..60000`, default `0`; command `SET_LAYER_TIMEOUT <ms>`, NVS key `layer_to`, `DEVICE_INFO` field `lt`). Values `1..999` are invalid for the command; the app and `server.py` raise them to `1000` (app) or reject them (server).
- When no key of either half is pressed for this time, `layerTimeoutExpire()` (`DactylLogic.h`, called in `loop()` of the master only) clears all layers that `TG_n` toggled. `layerLockedMask` marks layers that `LAYER_LOCK` locked; they stay, like `MO_n` and `OSL_n`. Any key press of either half (`retroPressSeq`, set by `notePriorKeyPress`) and any change of the toggled layers restart the timer. Only the master runs the timer, because only it knows `layerLockedMask`; the left half follows through `LAYER_STATE` and counts its key presses through the split link. The left half stores the setting but does not use it, so the value of the master applies to both halves.
- Known limit: the master learns `layerLockedMask` only from its own `LAYER_LOCK`. A `LAYER_LOCK` on the left half reaches the master as a plain toggle, so the timeout clears that layer too. Hardware check: lock a layer from each half and wait for the timeout.
- A key held on the master (for example a mouse move key) keeps the timer from running until its release. A key held on the left half does not: only its press restarts the timer (known limit, same cause as the `LAYER_LOCK` limit).
- Mixed versions: an app from before version 41 does not read `ld`, so it shows no leader timeout from new firmware. Update the app with the firmware.
- When the active layer changes, the firmware prints `LAYER: TIMEOUT -> Layer <n>`.
- Full sync sends `SET_LAYER_TIMEOUT` as an optional step (`optional: "args"`); firmware before version 41 answers `ERR UNKNOWN` and the sync continues. Settings card field `#layerTimeoutInput`.
- `DEVICE_INFO` grew past the BLE limit of 512 bytes, so `leader_timeout_ms` became `ld` (the app still reads the old name). Tests: `firmware/tests/test_firmware_logic.cpp` ("layer_timeout"), `tests/test_app_logic.js`, `tests/test_side_profiles.js`, `tests/test_server.py`.

### Tri-layer (conditional layer)

- Setting `triLayers` per half: up to two rules `{ a, b, target }` (layers 1..7). When layers `a` and `b` are both active, layer `target` becomes active too. The highest active layer still wins, so the target applies when it is higher than every other active layer.
- `getActiveLayer()` (`DactylLogic.h`) collects the active layers from the own MO layers, `toggleLayers[]` and `remoteMomentaryLayers`, then applies the rules once (no cascade: a target does not trigger another rule). The rule works when each half holds one layer. `MO_0` still forces layer 0.
- A rule is valid when `a`, `b` and `target` are in 1..7, `a != b` and `target` is neither `a` nor `b`. Each half keeps its own rules; set the same rule on both halves when both halves must resolve the target.
- Firmware: `triLayerRules[6]` and `numTriLayers` (settings block `[[[START_SETTINGS]]]`). Command `SET_TRI_LAYER <a> <b> <target> [<a> <b> <target>]` stores the rules, `SET_TRI_LAYER -` clears them. Answers `OK SET_TRI_LAYER <count>`, `ERR ARGS` for invalid values, `ERR NVS` when the write fails (the RAM state stays). NVS keys: `tri_n` (count) and `tri_data` (3 bytes per rule). A stored count of 0 overrides the compiled-in rules; a stored invalid rule is ignored. `DEVICE_INFO` carries `"tri_layer":[[a,b,target],...]`.
- Server: `validate_tri_layers` (`server.py`) rejects more than two rules, values outside 1..7, `a == b` and a target equal to `a` or `b`; `generate_settings_cpp` renders the rules.
- App: settings card, two rows of three selects (`triLayerA<i>`, `triLayerB<i>`, `triLayerT<i>`); empty = off. `normalizeTriLayers` (`js/config-model.js`) drops invalid rules. The full sync sends `SET_TRI_LAYER` (`buildSettingCommands`) as an optional step: firmware without it answers `ERR UNKNOWN`, the app shows a flash hint and continues.
- `lintLayouts`: a target layer counts as reachable when `a` and `b` are reachable. A half with keys on the target layer but without the rule gets the warning `tri-layer-other-half`, because each half evaluates only its own rules.
- NVS write order: `tri_data`, then `tri_n`. When the second write fails, the old `tri_data` is written back, so the previous rules stay valid.
- Mixed firmware: needs `DACTYL_FW_VERSION` 14 or newer on the half that holds the rule.

### Double-tap across both halves (`SPLIT_OP_TAP_PENDING`, `SPLIT_OP_TAP_FLUSH`)

- A waiting single tap (see "Tap-Dance / Double-Tap") goes out before a key press of the other half, so the character order stays correct on both halves.
- Right tap, left key: `splitProcessRx` calls `onBeforeLeftPress` before each left press op with a host (`splitIsPressOp`: `KEY_PRESS`, `KEY_WRITE`, `MEDIA_PRESS`, `MEDIA_WRITE`, `MOUSE_PRESS`, `MOUSE_CLICK`, `MOUSE_SCROLL`, `ONE_SHOT_PRESS`, `CAPS_WORD_TOGGLE`). The master callback (`onSplitBeforeLeftPress`) takes `configMutex` and calls `flushAllDoubleTaps()` (`DactylLogic.h`).
- Left tap, right key: the left half queues `TAP_PENDING` (`code` 1 while `anyDoubleTapWaiting()`, else 0) after each change (`queueTapPendingIfChanged`, `SplitTapPendingReporter`; retried by the send queue; without a link the state counts as not reported). The master stores it in `SplitLeftHeld.tapPending` (`splitNoteLeftRx`, also without a host, no HID effect, no activity); a link timeout and a new link clear it, and it expires after `SPLIT_TAP_PENDING_MAX_MS` (600 ms, longer than the largest tapping term). While it is set, the master holds its own matrix changes in `SplitLocalDefer` (16 entries; `rawKeyState` follows the scan, `keyState` follows the applied change), sends `TAP_FLUSH` once per round (no retry) and applies the held changes in order when the left half reports 0 or after `SPLIT_TAP_FLUSH_TIMEOUT_MS` (50 ms). A full buffer applies all held changes at once. The left half calls `flushAllDoubleTaps()` on `TAP_FLUSH`. After each flushed tap, `DOUBLE_TAP_FLUSHED()` (macro in `DactylLogic.h`, `onDoubleTapFlushed` in `dactyl_left.ino`) queues `TAP_PENDING 0` at once, before the events of the key that caused the flush. A replayed change keeps its scan time (`SplitDeferredKey.atMs`, `onMatrixKeyChange(r, c, pressed, atMs)`), so the tapping term and the combo window see the real intervals.
- Mixed firmware: an older master rejects op 19, an older left half never reports `TAP_PENDING`; both keep the old order. Flash both halves (`DACTYL_FW_VERSION` 2).
- Before each left press op, the master applies all held own changes only when the left half reports no waiting tap (`splitBeforeLeftPress`). While the report is 1, the press is the flushed left tap, which came before the held changes. The logic is in `DactylSplitHid.h` (`splitDeferApplyOrHold`, `splitDeferReplay`, `splitBeforeLeftPress`) and `DactylLeftLogic.h` (`serviceTapPending`, `tapPendingReset`); the `.ino` files only connect it. If `configMutex` stays busy for 200 ms (BLE `GET_INFO`), the master prints `WARN: configMutex busy` and keeps the old order for that press. The config combo clears the held changes (`splitDeferReset`).
- Known limits: a right key pressed in the radio delay between the left tap release and the arrival of `TAP_PENDING 1` (a few ms) is not held and goes out first. A pending Mod-Tap decision of one half is resolved as hold by a key press of the other half; see "Mod-Tap across both halves".

### Auto Shift (`autoShift`, `autoShiftMs`)

- Setting per half: `autoShift` (0 = off, default; 1 = all printable keys; 2 = digits and symbols only; 3 = letters only; 4 = symbols only) and `autoShiftMs` (50..500, default 175). Commands `SET_AUTO_SHIFT 0..4` and `SET_AUTO_SHIFT_TERM <ms>`, NVS keys `auto_shift` and `auto_shift_ms`, `DEVICE_INFO` fields `as` and `at` (short names keep the line under the 512-byte BLE limit). Both commands are optional in the full sync (`buildSettingCommands`). Firmware version 27.
- A key whose resolved tap action is a letter, digit or symbol with a shifted US character (`autoShiftedAscii` in `DactylLogic.h`) and that has no hold action and no double-tap action waits in `autoShiftKeys`. At `autoShiftMs` after the press (`autoShiftTick`, or the release if it comes first) the key sends the shifted character (`a` -> `A`, `1` -> `!`, `;` -> `:`). A release before the term sends the plain character.
- Order: a press of any other key first sends every waiting Auto Shift key as plain tap (`autoShiftFlushExcept`), so a fast roll keeps the character order. A key held in a roll that passes the term still sends its shifted character.
- Other half: a waiting Auto Shift key counts as a waiting tap (`anyDoubleTapWaiting`, `flushAllDoubleTaps`), so a key of the other half never passes it. Auto Shift is off for a key pressed while this half holds a modifier or `Shift` (`heldModifierMask`), so `Cmd` + `Z` stays `Cmd` + `Z`.
- Known limits: the check for a held modifier sees only the own half, so `Cmd` on the other half plus a long-held `z` sends `Cmd`+`Shift`+`Z`. A digit held past the term inside Caps Word sends its symbol and ends Caps Word. A waiting key on the left half reports `TAP_PENDING 1`, so a right key can wait up to `SPLIT_TAP_FLUSH_TIMEOUT_MS` (50 ms) for the answer. Auto Shift is off during a Leader capture. The layer of the press decides the character, also when a layer key follows.
- The press and the `KEY_PRESS` notification of an Auto Shift key come at the decision (release or term), at most `autoShiftMs` late. This also applies in config mode and to the live monitor.
- Unchanged: keys with a hold action (Mod-Tap, Layer-Tap), keys with a double-tap action, modifiers, layer keys, the space key, keycodes above ASCII, Caps Word and One-Shot `Shift`. Combos that consume the key cancel the wait.
- Character class filter: `autoShiftModeAllows(mode, c)` in `DactylLogic.h` decides per tap action. A key outside the class of the mode sends at the press, without a wait. Mode 1 equals the former "on". Firmware before version 36 accepts only `0|1` and answers `ERR ARGS` for `2..4`; the full sync (`optional: "args"`) treats this answer like `ERR UNKNOWN`, shows the flash hint and continues.
- The app shows the setting in the settings card (`#autoShiftSelect`, `#autoShiftTermInput`). Server and app limit the values to the ranges above (`SETTINGS_RANGES`).

### Timing assistant (`computeTimingRecommendations`)

- The dialog "Tapping-Term-Assistent" (button `#btnOpenTimingAssistant` in the settings card, modal `#timingAssistantModal`, code in `js/editor-events.js`) records the `MATRIX:` lines of the edited half over USB (with the scan time `t`) while the user types. `feedTimingAssistant` is called from the `MATRIX:` branch in `js/serial.js`. Recording stops at 20000 events or when the edited half changes.
- The pure analyzer `computeTimingRecommendations(samples)` (`js/config-model.js`) pairs press and release per key. A release without press, a press without release, a repeated press and an invalid event count as `incomplete` and give no value; a press at most 30 ms after the release of the same key (bounce) continues the hold; a hold above 500 ms is dropped. The scan time wraps at 2^32 ms; a jump back (restart) clears the open presses.
- Recommendations, each clamped with `clampSetting` to `SETTINGS_RANGES`: `tappingTermMs` = p95 of the hold times + 30 ms; `comboTimeoutMs` = half of the p5 of the overlap between presses of two keys (overlaps above 300 ms, for example a held `Shift`, do not count); `quickTapMs` = p5 of the gap (at most 300 ms) between a release and the next press of the same key, so fast double letters can fall inside the Quick-Tap window; `requirePriorIdleMs` = p10 of the gaps between presses. Below 20 complete holds the result is `enough: false` and has no values. The last three need at least 10 samples each, otherwise that setting is missing.
- During the recording the dialog shows only the event count; the analysis runs when the recording stops. Each new recording starts empty (a restart or a new connection changes the scan time). A change of the edited half clears the samples, and "Werte übernehmen" refuses a result of the other half.
- "Werte übernehmen" writes the values only into the input fields of the settings card. They become part of the config with "Einstellungen in Config übernehmen" and reach the device with the normal sync.

- Per-key suggestions (`computePerKeyTimingSuggestions(samples, config, profile)`, `js/config-model.js`): the same recording gives one hold list per physical key. A key gets an entry when it has at least 10 complete holds, a hold or double-tap action in at least one layer, and its recommended term (p95 of its holds + 30 ms, clamped to `100..500`) differs by at least 25 ms from `tappingTermMs` of the half. Layers where `tapTerm` already equals the recommendation do not count. A hold that the user keeps on purpose (up to 500 ms) counts as a tap, so it can raise the p95 of a key; check the value before you apply it. The dialog lists them (with the layers) under "Tapping-Term je Taste" (`#timingAssistantPerKey`).
- "Werte je Taste übernehmen" (`#btnTimingAssistantApplyPerKey`, `applyPerKeyTimingFromUI` in `js/editor-events.js`) writes `tapTerm` into the matching keys of all layers as one snapshot pending change (`type: "key_term"`). Undo restores the old `tapTerm` values (`revertPerKeyTimingSuggestions`). It refuses a result of the other half. The values reach the device with the normal sync (`SET_KT`).

### Mod-Tap across both halves (`SPLIT_OP_HOLD_PENDING`, `SPLIT_OP_HOLD_RESOLVE`)

- Problem: a Mod-Tap key (tap and hold action, see "Mod-Tap / Layer-Tap") stays undecided until the tapping term ends or another key of the same half is pressed. Before this feature, a key press of the other half did not decide it. Example: the right `R5C0` holds `MO_1` (tap `Delete`) and a left key follows within the tapping term. The right half then sent `Delete` and the left key acted on layer 0.
- Rule: a key press of one half decides each open Mod-Tap key of the other half as hold, before the press acts. Both halves follow the same rule, so a left Layer-Tap key works for a right key as well.
- `HOLD_PENDING` (23, both directions, `code` 1 or 0, `arg` 0): a half reports 1 while at least one of its Mod-Tap keys is undecided (`anyTapHoldPending()`, `DactylLogic.h`), and 0 after the decision (tap, hold, combo). `SplitHoldReporter` / `splitHoldReportIfChanged` send it only on a change. A failed send is not counted as sent and goes out again in the next pass. Without a link nothing counts as reported, so an open key is reported again after the link returns.
- `HOLD_RESOLVE` (24, both directions, no values): the receiver decides all its open Mod-Tap keys as hold (`resolveAllPendingTapHoldsAsHold()`), without waiting for the tapping term. It is idempotent: a retry duplicate finds no open key.
- The half that presses a key while the other reports `HOLD_PENDING 1` holds its own matrix change in `SplitLocalDefer` (the buffer of "Double-tap across both halves": 16 entries, same order, same scan time `atMs`). It sends `HOLD_RESOLVE` once per round (no retry). The other half decides, sends its layer state (`LAYER_STATE`) and then `HOLD_PENDING 0`. After the 0, or after `SPLIT_TAP_FLUSH_TIMEOUT_MS` (50 ms) at the latest, the held change runs and sees the new layer.
- A report is valid for `SPLIT_HOLD_PENDING_MAX_MS` (600 ms, longer than the largest tapping term of 500 ms), so a lost 0 does not slow the other half for good. A link timeout and a new link clear it. `TAP_PENDING` and `HOLD_PENDING` share the hold-back: it ends only when neither is set (`splitLeftHolds`).
- Master side: `onSplitHoldResolve` (`dactyl_right.ino`) decides under `configMutex`, then sends the layer state and `HOLD_PENDING` at once. `onSplitBeforeLeftPress` also decides the open keys of the master before each left press, because the master knows the left press itself; the master needs no extra round trip for that case. Left side: `masterHold` (`MasterHoldState`, `DactylLeftLogic.h`) holds the master report, `leftDefer` the held changes, `applyLeftKeyChange` runs a change. The left half keeps the entered state in `rawKeyState`; `keyState` follows the applied change.
- Order on the radio: the layer state goes out before `HOLD_PENDING 0` on both halves. The left queue keeps the order. The master sends two separate ESP-NOW packets without an order, so `splitSendLayerThenHold` sends the 0 only when the layer state of the decision is sent (`splitLayerInSync`); a layer packet that `esp_now_send` rejects holds back the 0 until the next pass. A packet lost on the air is not detected: the master sends the layer state a second time after `SPLIT_LAYER_REPEAT_MS` (30 ms), and if both copies are lost, the held key runs on the old layer after the time limit of 50 ms. The half with the held key runs it only after it has seen the 0.
- Left loop: the receive callback only puts the master layer into a mailbox. `leftReplayHeld` (`DactylLeftLogic.h`) reads the state "master waits" first, then takes the layer (`processMasterLayerState`), then runs the held changes. The callback writes the time before the state and `masterHoldPending` reads the state before the time (`__atomic_thread_fence`), so a new state never pairs with an old time.
- Only a press asks for a decision: `HOLD_RESOLVE` goes out only when a held change is a press (`splitDeferTakeResolveRequest`, separate from `TAP_FLUSH`). In `HOLD_MODE_TAP_PREFERRED`, `HOLD_RESOLVE` is never sent; in `HOLD_MODE_PERMISSIVE`, it is sent only when a nested press-release pair is observed in the deferred buffer. A release does not decide the key of the other half, like the rule of the same half (`applyMatrixKeyChange`). A roll (press `a`, press the Mod-Tap key, release `a`) keeps the Mod-Tap key open. A release that a half already held before the decision runs first (`splitDeferReplayReleasesThenResolve`): an open Mod-Tap key that the user released before the press of the other half was a tap and stays a tap.
- A left press runs the held master keys first when only `HOLD_PENDING` is set (`onSplitBeforeLeftPress` passes only `splitLeftTapPending` to `splitBeforeLeftPress`): the master key was pressed first and acts first. A waiting left tap (`TAP_PENDING`) still keeps them behind it.
- Mixed firmware (`DACTYL_FW_VERSION` 4): an older half rejects ops 23 and 24 as invalid and never reports `HOLD_PENDING`, so the other half holds nothing and behaves as before. The app hint "Beide Hälften flashen" appears. Flash both halves.
- Known limits: a key pressed in the radio delay between the press of the Mod-Tap key and the arrival of `HOLD_PENDING 1` (a few ms) is not held and acts on the old layer. A key held back for the time limit (50 ms) runs without a decision if the other half does not answer. The config combo clears the held changes of its half (`splitDeferReset`).

### Send queue (`DactylLeftLogic.h`)

- 64-entry queue, one packet in flight. A failed send (callback status, `esp_now_send` error or 200 ms callback timeout) is retried up to 3 times after `ESPNOW_RETRY_DELAY_MS` (30 ms); the order is kept.
- The send callback is matched by a callback counter: each send expects "counter before send + 1" (`queueMarkSent` / `queueCallbackIsCurrent`). Only a callback that arrives more than 230 ms late, after the retry was sent, is credited to the retry.
- A full queue drops the new event (`ESPNOW_QUEUE_FULL`). While the link is up, a dropped release stays held until the next `RELEASE_ALL` (config mode entry, deep sleep or reboot of the left half).
- ESP-NOW restart (`EspNowRestartGuard`, `shouldRestartEspNow`): after `ESPNOW_RESTART_DROPS` (5) dropped events in a row and `ESPNOW_RESTART_DOWN_MS` (5 s) since the first drop, `restartEspNow()` resets the queue, deinitializes ESP-NOW and Wi-Fi and runs `setupEspNow()` again, which queues `RELEASE_ALL`. Serial line `ESPNOW_RESTART`. The backoff starts at `ESPNOW_RESTART_BACKOFF_MS` (30 s) and doubles with each restart without a delivery up to `ESPNOW_RESTART_BACKOFF_MAX_MS` (8 min), so a master that is off or in deep sleep does not cost a restart every 30 s; a delivery resets it. `espNowRestartAllowed()` blocks a restart in config mode, while deep sleep is due and without ESP-NOW. A key held during a restart stays pressed in `DactylLogic.h` but is released at the master (`RELEASE_ALL`); press it again to send it. A failed `setupEspNow()` restarts the board. The guard is a safeguard for a send failure with unknown cause, not a fix of the cause.

### Eager debounce per key (`DactylDebounce.h`)

- Both halves debounce each key on its own (`EagerDebounceKey`, `eagerDebounceUpdate()`). The loop has no global `delay(debounceMs)` any more; it waits 1 ms (standby: 40 ms, unchanged). The active scan rate is therefore higher than with the old `debounceMs` wait (up to 5 to 50 times), which raises the current draw while typing; standby is unchanged.
- `resetMatrixDebounceKey(r, c)` clears the debounce state of one key (config combo reset).
- A press is reported in the first pass that sees it. The key then ignores all changes for `debounceMs` (setting `SET_DEBOUNCE`, default 5 ms).
- A release is reported after the key stayed open for `debounceMs` without a break. A short open glitch while the key is held does not release it.
- Right half: `debouncedMatrixKey()` in `DactylLogic.h` feeds `rawKeyState`; `resetMatrixDebounce()` clears the state. Left half: `updateLeftKey()` in `DactylLeftLogic.h`.
- The config combo reset clears the debounce state of its two keys, so a held key does not release twice.
- Tests: `test_eager_debounce_*` (`test_firmware_logic.cpp`) and the debounce tests in `test_left_logic.cpp`.

### Config mode, NVS, power

- Config mode: hold **`R0C5 + R4C0`** (mirrored: inner top + outer bottom) for 500 ms, or USB serial `ENTER_CONFIG`. The left half sends `RELEASE_ALL`, reboots into an isolated BLE server `Dactyl Config L` (static random address, no HID, no bonding) and returns via `ESP.restart()` or after 3 min inactivity. In config mode ESP-NOW is off.
- NVS: same `loadKeymapFromNVS()` / `saveKeymapToNVS()` / `handleConfigCommand()` as the right half, on the left chip. `KEYMAP_DEFAULTS_ID 0` in the repository.
- `DEVICE_INFO` contains `"side":"L"` (macro `DEVICE_SIDE`, default `"R"` in `DactylLogic.h`). App and server identify the half at a USB port with it; firmware without the field counts as right.
- BLE connection latency: In active typing, the master uses fast parameters (`7.5..22.5 ms`, `latency = 0`, `timeout = 4000 ms`). In standby, `enterStandby()` requests peripheral slave latency via `esp_ble_gap_update_conn_params` (`15..30 ms`, `latency = 20`, `timeout = 4000 ms`, compliant with Apple Accessory Design Guidelines). The BLE radio skips up to 20 empty connection intervals while idle, but sends new key presses on the next interval and returns to active parameters via `exitStandby()`.
- TX power saving: The master sets BLE TX power to `ESP_PWR_LVL_N0` (`0 dBm` via `esp_ble_tx_power_set`) for default, advertising, and active connections. Both halves lower ESP-NOW Wi-Fi TX power to `SPLIT_ESPNOW_TX_POWER` (`34` = `8.5 dBm` via `esp_wifi_set_max_tx_power`), maintaining zero packet loss across the ~20 cm desk distance.
- ESP-NOW modem sleep and wake window: Both halves enable Wi-Fi modem sleep (`esp_wifi_set_ps(WIFI_PS_MIN_MODEM)`). Both halves configure connectionless module wake intervals (`esp_wifi_connectionless_module_set_wake_interval(SPLIT_ESPNOW_WAKE_INTERVAL_MS)` = 100 ms). During active typing, the receiver uses `SPLIT_ESPNOW_WAKE_WINDOW_ACTIVE_MS` (100 ms, continuous listening). In standby, `applySplitWakeWindow(true)` switches the receiver window to `SPLIT_ESPNOW_WAKE_WINDOW_STANDBY_MS` (40 ms) via `esp_now_set_wake_window()`. The left sender retries up to 5 times (`ESPNOW_MAX_RETRIES`), spanning at least 150 ms to guarantee reception within the 100 ms wake interval. In standby, the left loop adds `leftLoopDelayMs()` (40 ms) while the queue is idle, dropping back to 1 ms immediately when keys are pressed.

### Auto-mouse layer (`autoMouseLayer`, `mouseTimeoutMs`)

- The auto-mouse layer turns a chosen layer on when the user does a mouse action. It removes the need for a thumb key that holds a mouse layer.
- Setting `autoMouseLayer` (`0..7`, `255` = off, default `255`). The app dropdown "Auto-Mouse-Ebene" shows "Aus" and "Ebene 1" to "Ebene 7". Layer `0` is stored but has no effect.
- Setting `mouseTimeoutMs` (`100..2000` ms, default `500` ms). The app number field "Auto-Mouse-Zeitlimit" uses the same range. The app clamps values outside the range (`clampSetting`).
- These actions activate the layer and store the time stamp `autoMouseLastMs`: mouse move keys (`MOUSE_UP`, `MOUSE_DOWN`, `MOUSE_LEFT_MOVE`, `MOUSE_RIGHT_MOVE`), the speed keys (`MOUSE_SLOW`, `MOUSE_FAST`), wheel and pan keys, click keys, the same actions in a key pair or a combo, and the mouse events of the left half (`SPLIT_OP_MOUSE_*`, through `splitMouseActivityHook`).
- The layer is a separate state `autoMouseOn` in `getActiveLayer()` in `DactylLogic.h`. It does not change `toggleLayers[]`. The layer sync (`SPLIT_OP_LAYER_STATE`) sends it to the other half like a `MO_n` layer (`localMomentaryLayerMask`).
- `autoMouseExpire(now)` runs in `loop()` of both sketches. It turns the layer off when `mouseTimeoutMs` has passed since the last mouse action. A held move key or wheel key keeps the layer on and restarts the time.
- Each half has its own values and its own state. The master keeps the layer on while the left half holds a mouse button (`autoMouseRemoteHeldHook`). The left half activates the layer for its own mouse keys and reports it to the master with the layer sync. The master also activates it for mouse events of the left half. Set the same values on both halves (the full sync does this).
- The state lives in RAM only. `CLEAR_STATE` (`clearStatePress`), `RELEASE_ALL`, a link loss, the loss of the host, the config mode (`oslClearAll`, `resetMouseMove`), standby and deep sleep clear it (on the left half: `oslClearAll` and `enterStandby`). In the config mode no mouse action turns the layer on. A new value `255` for `autoMouseLayer` clears an active layer at once.
- Commands `SET_AUTO_MOUSE_LAYER <0..7|255>` and `SET_MOUSE_TIMEOUT <100..2000>`. The answer is `OK SET_AUTO_MOUSE_LAYER <n>` or `OK SET_MOUSE_TIMEOUT <ms>`, otherwise `ERR ARGS`. The firmware rejects a non-digit, a value out of range and a value with too many characters.
- NVS keys: `am_layer` (layer) and `am_to` (time limit). The firmware ignores an invalid stored value.
- `GET_INFO` sends the line `AUTO_MOUSE:{"aml":<layer>,"amt":<ms>}` before `DEVICE_INFO`. `DEVICE_INFO` has only 7 bytes of reserve below the BLE limit of 512 bytes, so the fields `aml` and `amt` have their own line. The app reads the line in `handleSerialLine` (`js/serial.js`). "Vom ESP32 laden" adds both fields to `snapshot.info` (`captureDeviceSnapshotLine`). `settingsFromDeviceInfo` maps `aml` to `autoMouseLayer` and `amt` to `mouseTimeoutMs`.
- The app sends both commands in the full sync as optional steps (`optional: "args"`, `buildSettingCommands`). Older firmware answers `ERR UNKNOWN` and the sync goes on. "Ebenen tauschen" (`swapLayersWithRefs`) moves `autoMouseLayer` with the layers. The server checks both values (`SETTINGS_RANGES`, `generate_settings_cpp`) and writes them into the settings block of both sketches.
- The settings UI is in `index.html`, `app.js` (`applySettingsToInputs`) and `js/editor-events.js`. The repository has no `js/settings-ui.js`.
- `DACTYL_FW_VERSION` is 51; flash both halves.
- Tests: `firmware/tests/test_firmware_logic.cpp` ("test_auto_mouse_*", "test_set_auto_mouse_commands_args_nvs_and_info"), `tests/test_app_logic.js`, `tests/test_side_profiles.js`, `tests/test_server.py`.

### Firmware version (`DactylVersion.h`)

- `DACTYL_FW_VERSION` (1..65535) in `firmware/dactyl_right/DactylVersion.h` is the version of both halves. Increase it with each change to the split protocol, the config commands or the NVS format. `DEVICE_INFO` of each half contains `"fw":<n>`.
- The left half sends `SPLIT_OP_FW_VERSION` (op 18, `code` = version) with its first heartbeat after `setupEspNow()` and then with every `SPLIT_FW_VERSION_EVERY` (5th) heartbeat (`queueHeartbeat`, `DactylLeftLogic.h`). It goes into the queue like a diagnostic event (at most half full), so it also arrives while the user types. A master without this op rejects the packet; the heartbeats between keep the link up.
- The master stores the value in `splitLeft.fw` (`splitNoteLeftRx`, also without a Mac connection, no HID effect, no activity). A new link clears it, because a flash of the left half takes longer than `SPLIT_LINK_TIMEOUT_MS`. `splitLeftFwStatus` returns the version, `0` (no link or detection window open) or `-1` (link for `SPLIT_FW_DETECT_MS` = 12 s without a version: old left firmware; longer than two version intervals, so one lost packet gives no false `-1`). The master's `DEVICE_INFO` contains it as `"left_fw"` (macro `DEVICE_INFO_LEFT_FW()`, only on the master) and prints each change on USB serial as `SPLIT_FW:{"fw":<n>}`.
- The app (`Dactyl.createFirmwareVersions`, `Dactyl.parseSplitFwLine`, `js/side-routing.js`) keeps one value per half: `null` unknown, `0` firmware without the field `fw`, else the version. When both are known and differ, the header shows `#fwMismatchPill` "Beide Hälften flashen". A successful flash of a half clears its value until it reports again.

### Firmware diagnostics (`GET_DIAG`)

- `GET_DIAG` (`handleConfigCommand`, `DactylLogic.h`) answers `DIAG:{"reset":"<reason>","uptime_s":n,"heap_free":n,"heap_min":n,"loop_max_us":n}` on both halves; the left half appends `,"sq_max":n,"sq_drop":n` (see below). It works over USB serial and over BLE in config mode. Over BLE in keyboard mode, the command is rejected with `ERR FORBIDDEN GET_DIAG` (uptime and heap values stay off the HID link).
- `resetReasonName(esp_reset_reason_t)` is a pure function: `power_on`, `external`, `software`, `panic`, `int_wdt`, `task_wdt`, `wdt`, `deep_sleep`, `brownout`, `sdio`, `usb`, `jtag`, `efuse`, `pwr_glitch`, `cpu_lockup`, else `unknown`. `buildDiagLine` renders the line (at most 159 bytes). `setup()` of both `.ino` files stores `esp_reset_reason()` in `diagBootReason`.
- `loop_max_us` is the longest `loop()` pass since the start in microseconds, without the final `delay()` (`diagNoteLoopUs` at the end of `loop()` in both `.ino` files). `uptime_s` comes from `esp_timer_get_time()`, `heap_min` from `ESP.getMinFreeHeap()`.
- The app (`Dactyl.parseDiagLine`, `Dactyl.describeDiag`, `js/side-routing.js`; `updateDiagUI`, `requestDiag`, `js/serial.js`) checks every field type and the reason name. The collapsible panel `#diagPanel` "Diagnose" shows one line per half and the button `#btnDiagRefresh` sends `GET_DIAG` on the connection of the active half. The panel is marked when a half reports a reason other than `power_on`, `deep_sleep` or `software`. The left half has its own USB port: connect it to read its values.

- `sq_max` is the highest fill level of the left send queue (`SplitSendQueue.highWater`, at most `SPLIT_QUEUE_SIZE`). `sq_drop` is the number of `queuePush` calls that the full queue rejected (`SplitSendQueue.dropped`). It counts attempts, not lost events: a sender that retries in the next `loop()` pass (layer state, tap pending, repeat note) counts each attempt, and `DactylSplitKeyboard::pushEvent` also keeps its own `droppedEvents()` for HID events, so such an event is in both counters. A value above 0 shows that the queue was full. Both count since boot and survive `queueReset()` (also the ESP-NOW restart). A diagnostic event above `SPLIT_DIAG_QUEUE_LIMIT` is not counted (it has `SPLIT_KEY_DROPPED`). `queuePushAfterDrain` counts only an event that finds no room after `drain()`. The line gets the two fields through `DIAG_SEND_QUEUE_MAX` / `DIAG_SEND_QUEUE_DROPPED` (defined only in `dactyl_left.ino`); the master line and the `DEVICE_INFO` line stay unchanged. The app shows both values in the panel and in the support report (`sqMax`, `sqDrop`; `null` for the master and for older firmware). Firmware version 42.

### Matrix diagnostics and solder tester (`TEST_MATRIX`, `MATRIX_RAW`)

- The command `TEST_MATRIX 1` starts the matrix test mode. The command `TEST_MATRIX 0` stops it. Any other argument returns `ERR ARGS TEST_MATRIX <argument>`. The firmware answers `OK TEST_MATRIX 1` or `OK TEST_MATRIX 0`.
- The test mode is a RAM flag (`matrixTestMode`, `DactylCommon.h`). The default is off. The flag is not saved in the NVS. The flag resets to off when the BLE connection ends, when the keyboard enters deep sleep (`enterDeepSleep`), when the keyboard enters the config mode and when the left half receives `SPLIT_OP_SLEEP`.
- While the test mode is on, each half sends one line for each physical switch change (press and release): `MATRIX_RAW:<side>,<row>,<col>,<1|0>`. `<side>` is `R` or `L`. `1` is a press. `0` is a release. Examples: `MATRIX_RAW:R,2,3,1` and `MATRIX_RAW:L,1,4,0`. The master prints the right half at the debounced scan (`rawKeyState`). The line comes before the layer, tap-hold and combo logic, so it also shows keys without an action.
- The command and the lines work only on USB serial. `MATRIX_RAW` uses `Serial.println` and never `sendConfigNotification`, so no line goes over BLE. In keyboard mode, the firmware rejects every BLE command except `GET_INFO`. In config mode, `TEST_MATRIX` over BLE returns `ERR FORBIDDEN TEST_MATRIX`. This keeps the test from becoming a key logger channel over BLE.
- Split path (`DactylSplitHid.h`):
  - `SPLIT_OP_MATRIX_TEST` (op 34, master to left, `code` 1 or 0, `arg` 0): the master sends it to the left half after `TEST_MATRIX 1|0` (`forwardMatrixTest`). Without a link, the left half stays off.
  - `SPLIT_OP_MATRIX_RAW` (op 33, left to master, `code` from `splitKeyEventCode` with layer 0): the left half sends it for each switch change when the master switched the test on. The master prints `MATRIX_RAW:L,<row>,<col>,<1|0>` on USB serial (`onSplitMatrixRaw`), also without a Mac connection.
  - When the command arrives on the USB port of the left half, the left half prints `MATRIX_RAW:L,...` itself and sends nothing over ESP-NOW (`matrixTestUsb`, `leftMatrixTestReport`, `DactylLeftLogic.h`).
  - The master sends `SPLIT_OP_MATRIX_TEST 1` again when the link to the left half comes up while the test runs. When a `SPLIT_OP_MATRIX_RAW` arrives while the test is off (lost off packet, restart of the master), the master answers with `SPLIT_OP_MATRIX_TEST 0`, at most once per `MATRIX_TEST_STRAY_OFF_MS` (1 s). While the test runs and the link is up, the master also repeats `SPLIT_OP_MATRIX_TEST 1` every `MATRIX_TEST_REFRESH_MS` (2 s). The packet has no acknowledgement; these rules repair a lost packet. A dropped `SPLIT_OP_MATRIX_RAW` is no HID loss for the ESP-NOW restart guard (`restartGuardOnOutcome`).
  - `SPLIT_OP_MATRIX_RAW` goes into the send queue like a diagnostic event (at most half full). The left half does not repeat it, because a repeated packet would count one press twice (`splitEventRetryable`). The master validates it (`isValidSplitHidEvent`): no layer bits, valid row and column. The master handles it at most `SPLIT_KEY_EVENTS_PER_RX` times for each `loop()` pass, with its own budget next to `SPLIT_OP_KEY_EVENT`. A packet above the budget is counted in `SPLIT_KEY_DROPPED` and reported as `SPLIT_KEY_RX_DROPPED`.
  - A transmitter that spoofs the left MAC can send `SPLIT_OP_MATRIX_RAW` and print serial lines on the master while the test mode is on. The packet carries no keycode and has no HID effect.
- App (`js/diagnostics-ui.js`, `js/serial.js`, `js/config-model.js`, `index.html`): the panel `#diagPanel` "Diagnose" has the section "Matrix-Test (Löttester)". The button `#btnMatrixTest` starts the test (`TEST_MATRIX 1`) and stops it (`TEST_MATRIX 0`). The test starts only with a USB connection. The button `#btnMatrixTestClear` clears the counters.
  - `parseMatrixRawLine` checks the line strictly: side of a registered profile, row and column in the matrix, state `0` or `1`. An invalid line returns `null`.
  - `applyMatrixRaw` keeps the pressed switches and the number of presses for each switch and half (`createMatrixRawState`). A press counts when the switch changes from released to pressed. A repeated press, a release without a press, an unknown half and a position without a switch change nothing.
  - `handleSerialLine` uses the line only while the test runs. The half comes from the line, not from the port. The grid for the left and the right half highlights the pressed switches (`is-down`) and shows the total number of presses for each switch.
  - The test stops (`stopMatrixRawTest`) when the user presses the button, when the user closes the panel and when the user closes the USB connection. Each of these sends `TEST_MATRIX 0`. The firmware cannot detect the loss of the USB host. When the app closes the port, it sends `TEST_MATRIX 0` first. After an unplugged cable, the flag stays on until deep sleep, the config mode, a BLE disconnect or a restart; the lines then go to a serial port that nobody reads.
- The test mode does not change the key actions: a key still types on the paired host while the test runs. Use the test with the host unpaired or with a harmless target window.
- When the BLE connection ends or the config mode starts during a test, the half resets the flag and prints `MATRIX_TEST:OFF` on USB serial (`matrixTestEnd`; for the BLE disconnect, the BLE task only clears the flag and `loop()` prints the line, `matrixTestEndDeferred`). The app takes `MATRIX_RAW` and `MATRIX_TEST:OFF` only from the USB transport. The two flags `matrixTestMode` and `matrixTestUsb` are written in a fixed order; a concurrent on and off from two tasks is last-writer-wins. The app then ends the test. In the config mode, ESP-NOW is off: `TEST_MATRIX 1` on the master then tests only the right half. Test the left half on its own USB port. The app also ends the test on `ERR UNKNOWN TEST_MATRIX` (firmware before version 52) and `ERR FORBIDDEN TEST_MATRIX`. A USB test on the left half (`matrixTestUsb`) ignores `SPLIT_OP_MATRIX_TEST` from the master.
- `DACTYL_FW_VERSION` is 52; flash both halves. The firmware before version 52 answers `ERR UNKNOWN TEST_MATRIX 1`.
- Tests: `firmware/tests/test_firmware_logic.cpp` ("test_matrix_test_*", "test_matrix_raw_line_format"), `firmware/tests/test_left_logic.cpp` ("test_matrix_test_report_routes_usb_or_split"), `firmware/tests/test_split_hid.cpp` ("test_matrix_test_packet_validation_both_directions", "test_process_rx_forwards_matrix_raw_*"), `tests/test_app_logic.js` ("parseMatrixRawLine", "applyMatrixRaw", "Matrix-Test starten"), `tests/test_side_profiles.js`.

### Split link status (`SPLIT_LINK`, `left_link`)

- The master counts the state of the radio link to the left half in `SplitLeftHeld` (`DactylSplitHid.h`): `linkChangedMs` (last change up/down), `everUp`, `linkLosses` (link timeouts), `rxDropped` (packets dropped by a full receive ring, from `SplitRxQueue.dropped`) and `keyDropped` (`KEY_EVENT`s over `SPLIT_KEY_EVENTS_PER_RX`). The counters saturate (`splitCountAdd`) and count since the start of the master. A reset (`splitHeldReset`) clears them, so they also restart with each `setupSplitReceiver()`.
- `splitLeftLinkJson` renders `{"up":0|1,"ms":<ms since the last change>,"ever":0|1,"losses":n,"rx_dropped":n,"key_dropped":n}`. The master's `DEVICE_INFO` contains it as `"left_link"` (macro `DEVICE_INFO_LEFT_LINK(buf, size)`, only on the master; the `GET_INFO` buffer is 448 bytes) and prints it on USB serial as `SPLIT_LINK:<json>`. `ms` is 0 without a link history and never negative (the BLE task can read `millis()` before a `linkChangedMs` that `loop()` just wrote). `DACTYL_FW_VERSION` stays unchanged: the radio protocol and the left firmware do not change.
- Signal quality: `onSplitDataRecv` (`dactyl_right.ino`) reads `info->rx_ctrl->rssi` only after `parseSplitHidPacket` accepted the packet (decryption, sender MAC, length, value range), so a spoofed packet does not change the value. `splitNoteRssi` (`DactylSplitHid.h`, the Wi-Fi task is the only writer) keeps an exponential average (weight 1/8, stored in 1/16 dBm in `SplitLeftHeld.rssiAvg16`) and the minimum since the start (`rssiMin`). A value outside -127..0 dBm is no measurement and does not count. `splitHeldReset` clears both. `splitLeftLinkJson` adds `"rssi"` (rounded average) and `"rssi_min"` in dBm, both `null` without a checked packet; the longest line (all counters at 4294967295, `-127`) stays below the 160-byte `linkBuf` and the 448-byte `GET_INFO` buffer (`test_firmware_logic.cpp` checks the tail). `splitLinkReportDue` also reports a new measurement, a new minimum or an average 3 dBm away from the reported value, throttled by `SPLIT_LINK_REPORT_MS`. `DACTYL_FW_VERSION` stays unchanged: the radio protocol does not change, and the app accepts a line without the two fields (older firmware).
- `splitLinkReportDue` (`SplitLinkReporter`) prints a link change at once and a changed counter at most every `SPLIT_LINK_REPORT_MS` (1 s), so a flood of dropped packets (spoofed left MAC) cannot flood the serial output. It prints once after the start, also without a link.
- The app (`Dactyl.parseSplitLinkLine`, `Dactyl.createSplitLinkStatus`, `Dactyl.describeSplitLink`, `js/side-routing.js`; `updateSplitLinkUI`, `js/serial.js`) accepts the line only from the master and checks every field type. The header pill `#splitLinkPill` shows "<label of the sender half>: verbunden" (green), "getrennt seit <time>" (red; time = reception time minus `ms`) or "nie verbunden" (grey); its tooltip names the signal (`rssi` average and `rssi_min` in dBm, only when the firmware reports them) and the counters. The pill turns yellow (`link-weak`, text "(schwaches Signal)") while the link is up and the average is below -80 dBm (`SPLIT_RSSI_WEAK_DBM`); `null` values and older firmware never turn it yellow. `parseSplitLinkLine` rejects a line with only one of the two fields or a value that is not an integer in -127..0. The app takes the state only from USB to the master (`SPLIT_LINK` and the `left_link` of `DEVICE_INFO` on USB): USB pushes each change. `left_link` over BLE is a snapshot of `GET_INFO` that nobody refreshes, so the app ignores it. The pill disappears for firmware without `left_link` and when the master reports `"left_link":null` (config mode or a failed ESP-NOW start: the master does not receive, so a state would only look like "nie verbunden"). A connection that ends clears the state (`forgetSplitLink`), unless a USB connection to the master remains (`Dactyl.splitLinkStaysValid`): USB pushes each change, BLE gives only the snapshot of `GET_INFO`. `linkChangedMs` is the time of the last packet, not of the detection 3 s later (or 12 s in standby), and `ms` is an unsigned age (correct beyond 24.8 days). Link timeout is `SPLIT_LINK_TIMEOUT_MS` (3 s) in active mode, or `SPLIT_STANDBY_TIMEOUT_MS` (12 s) when idle in standby (`!splitHeldAny(bleKeyboard.splitLeft) && splitRemoteLayers.momentary == 0`). The left half uses `SPLIT_LINK_DOWN_MS` (2 s) in active mode and `SPLIT_STANDBY_LINK_DOWN_MS` (11 s) in quiet standby with a 2 s grace period on wake-up (`DactylSplitKeyboard`).
- Power: standby after 5 min (slower scan), deep sleep after 60 min (`deepSleepTimeoutMinutes`). Without a host connection outside config mode (`!bleKeyboard.isConnected()`), both halves enter deep sleep after `SPLIT_DISCONNECTED_DEEP_SLEEP_MS` (3 min, or `deepSleepTimeoutMinutes` if configured lower, disabled when `deepSleepTimeoutMinutes == 0`) once both the time since the last activity and the time since the disconnect exceed the threshold and no local key is held (`splitDisconnectedDeepSleepDue`, `SplitDisconnectedSleep`). Before `enterDeepSleep()`, the master sends `SPLIT_OP_SLEEP` (op 26, master -> left only, `code` 0, `arg` 0, sent 3 times with a 35 ms gap via `sendSplitSleep()`) so the left half enters deep sleep at the same time when idle outside config mode (`consumeMasterSleepRequest`). The left half keeps 240 MHz in standby: a `setCpuFrequencyMhz()` change while Wi-Fi runs made every ESP-NOW send fail until `ESPNOW_RESTART`, so the first keys after wake-up were lost (hardware finding). The master still switches to 80 MHz; its ESP-NOW receive works in standby. Matrix scan settle time uses `MATRIX_SETTLE_US` (`10 us` in `DactylCommon.h`, down from `30 us`). Before deep sleep: `RELEASE_ALL`, ESP-NOW off. Output pins are held `HIGH`: RTC-capable output pins (Cols 4, 5, 6 on the right half; Row 5 `GPIO 4` on the left half) use the RTC driver (`rtc_gpio_hold_en`), while remaining non-RTC lines use `gpio_hold_en` + `gpio_deep_sleep_hold_en()`. Sense pins are RTC inputs with pull-down (rows on the right half, columns on the left half), and Ext1 `ANY_HIGH` triggers wakeup. Single-key wakeup and diode orientation require `ESP_EXT1_WAKEUP_ANY_HIGH`. A key press drives output -> switch -> diode -> input high.
- Synchronized inactivity timers: each applied left event resets the master's `lastActivityTime`. In the other direction, a right key press queues `SPLIT_OP_ACTIVITY` to the left MAC (`SplitActivityThrottle` via `splitNoteLocalKeyChange`, at most one packet per `SPLIT_ACTIVITY_INTERVAL_MS` = 10 s, the last press inside an interval is sent after it). A failed `esp_now_send` keeps the note (`splitActivitySendResult`), so the packet goes out again after the interval. The left half checks it with `parseSplitMasterPacket()` (master MAC, length, `code`/`arg` 0 for `ACTIVITY` and `SLEEP`) and resets its timer for standby and deep sleep (`consumeMasterActivity`), without HID effect. A failed registration of the receive callback prints `ERR ESPNOW_RECV_CB` and shows `ActivityRx=0` in the `STATUS` line; sending still works. Each half keeps its own timeout values in NVS.
- Known limit: a half in deep sleep receives no radio packets. A left key wakes only the left half; a sleeping master receives nothing until a right key wakes it.
- Default layout: QWERTZ positions on the left hand (US-ASCII codes like the right half; with the macOS layout "U.S." the `'y'` on the Z position prints `y`). `R4C5` and `R5C0` do not exist physically.

### ESP-NOW encryption (`DactylSplitCrypto.h`)

- Both halves register the other half as an encrypted peer: `esp_now_set_pmk(SPLIT_ESPNOW_PMK)`, then `splitPeerSetEncryption(peer.encrypt, peer.lmk)`, then `esp_now_add_peer`. ESP-NOW protects each unicast frame with CCMP and the LMK (16 bytes each). The 4-byte `SplitHidEvent` stays unchanged.
- The key is in `firmware/dactyl_right/DactylSplitKey.h` (in `.gitignore`, mode 0600). `bash scripts/generate-split-key.sh` writes it from `/dev/urandom` and prints no key values; it refuses to overwrite an existing key without `--force`. `--if-missing` keeps an existing key and ends with exit code 0. `npm run build:app` and `npm run rebuild:app` run it with `--if-missing` before the build (`package.json`), so the bundle always carries a key. With `--if-missing`, an existing key file must have the generated structure (otherwise exit 1, "beschädigt") and gets mode 0600. An unknown argument returns exit 2. A direct call of `bash scripts/build-app.sh` or `bash scripts/rebuild-app.sh` skips the generator and needs an existing key; without it `build-app.sh` only warns. The key belongs to the checkout: a build from a worktree without a key generates another key than the main checkout. Without the file, `DactylSplitCrypto.h` stops the build with `#error`, so no unencrypted firmware is built silently. CI generates a throwaway key before the compile check; the host tests define a test key before the include.
- Both halves need the same key. After a new key, flash both halves; until then, the halves do not receive each other's packets (the left half reports `ESPNOW_FAIL` and, after the drops, `ESPNOW_RESTART`).
- `build-app.sh` copies the key with the firmware into the bundle (mode 0600), so "Auf Dactyl flashen" compiles with it. Without a key it prints a warning; the flash then fails at the compile step.
- The key is compiled into the firmware. Flash encryption is off, so a person with physical access (USB) can read the key from either board (accepted risk, like the NVS keymap). After a lost or lent half, generate a new key and flash both halves.
- At boot, a failed `setupEspNow()` on the left half restarts the board at most `ESPNOW_BOOT_RETRIES` (3) times in a row (`espNowBootRetryAllowed`, counter in RTC memory, valid only after a software reset); then the half runs without ESP-NOW and prints `[ESPNOW] Start wiederholt fehlgeschlagen`. Config mode and USB stay available.
- The master sets `splitRxReady` only after the encrypted peer was added; a failed `esp_now_set_pmk` or `esp_now_add_peer` prints `[SPLIT] ERR ESPNOW_PMK` / `[SPLIT] ERR ESPNOW_PEER`, and the master then executes no left events. The left half returns `false` from `setupEspNow()` (board restart after a failed `restartEspNow`).

## Configuration and Sync

### Why macOS reconnected during config mode

- On macOS, `bluetoothd` bonds to the keyboard's Public BLE MAC (`2E:BC:BB:81:61:A8`) and locks the HID service (`0x1812`), blocking Web-Bluetooth GATT connections.
- Even if the ESP32 drops `0x1812` from its advertising packet, macOS `bluetoothd` immediately auto-reconnects at the L2CAP/GATT level whenever connectable advertisements appear from the **same bonded Public MAC address**.
- Additionally, `pServer->disconnect(id)` in ESP32 Bluedroid is asynchronous (`ESP_GATTS_DISCONNECT_EVT` fires ~20–50 ms later on the BTC task). Calling `pAdv->start()` before the disconnect event finishes causes `onDisconnect` to race with advertising reconfiguration.

### Static random BLE address in `enterConfigMode()`

- Triggered by holding hardware matrix switches **`R4C5 + R0C0` for 500 ms** (100% layer-independent) or via serial command `ENTER_CONFIG`.
- `enterConfigMode()` sets `isBleTransitioning = true`, stops advertising first (`pAdv->stop()`), disconnects all peers, and waits up to 350 ms until `pServer->getConnectedCount() == 0`.
- It then calls `pAdv->reset()` and configures a deterministic **Static Random BLE Address** (`randAddr[0] |= 0xC0; randAddr[5] |= 0xC0; randAddr[4] ^= 0x55;` via `esp_ble_gap_set_rand_addr(randAddr)` and `pAdv->setDeviceAddress(randAddr, BLE_ADDR_TYPE_RANDOM)`), separated by 25 ms GAP synchronization delays before `pAdv->start()`.
- In `exitConfigMode()`, Bluedroid's `pAdv->reset()` cannot clear GAP `own_addr_type` from `BLE_ADDR_TYPE_RANDOM` back to `BLE_ADDR_TYPE_PUBLIC` without restarting the controller stack. Therefore, `exitConfigMode()` cleanly disconnects peers and invokes `ESP.restart()` (~200ms reboot), restoring hardware state and the bonded Public MAC (`2E:BC:BB:81:61:A8`), allowing macOS to reconnect immediately.

### Staged One-Shot Auto-Sync (`getDevices()` + `watchAdvertisements()`)

- Users can edit keys, presets, layer names, and sleep timeouts in the app **while typing normally on macOS** (`markPendingSync` stages changes locally without blocking alerts).
- Once `"Dactyl Config"` has been paired once in the app via `navigator.bluetooth.requestDevice`, `initModernBleAutoSync()` monitors it in the background using `navigator.bluetooth.getDevices()` and `device.watchAdvertisements()`.
- When the user presses **`R4C5 + R0C0` (0.5 s)** on the keyboard:
  1. The ESP32 enters Config Mode and advertises `"Dactyl Config"` on its Static Random MAC.
  2. The app receives `advertisementreceived` and connects automatically (`connectToBleDevice(dev, true)`).
  3. With **One-Shot Auto-Sync** enabled (`#chkAutoSyncOnCombo`, checked by default), the app immediately runs `writeConfigToESP32({ autoDisconnectAfter: true })`, sending all keys via fast RAM updates (`SET_K <l> <r> <c> <val>`) followed by a single `SAVE_NVS` flash commit, and then sends `EXIT_CONFIG` and disconnects.
  4. The ESP32 immediately returns to normal Mac keyboard mode. The app sends `EXIT_CONFIG` right after the sync, without a delay.

### Full live sync (`requestLiveSync`, `js/config-sync.js`)

- Every change goes through `markPendingSync`. When the connection (BLE preferred, else USB) belongs to the half of the change, `markPendingSync` calls `requestLiveSync(side)`, and the app sends the complete configuration with `writeConfigToESP32` (settings, layer names, all keys, combos, key pairs, macros). It never sends a single `SET_KEY`, `SET_NAME` or `SET_*` setting command. Reason: the device lost its layout during development; a full sync makes the device equal to the app after each change.
- Changes within `LIVE_SYNC_DEBOUNCE_MS` (300 ms) start one sync. A change during a running sync (`isAutoSyncing`) or BLE connection setup (`isConnectingBle`) starts the next sync after it (`LIVE_SYNC_RETRY_MS`). The sync clears only the changes it sent.

### Signed BLE OTA firmware update in config mode

- Allows wireless firmware updates over Web Bluetooth in config mode (`Dactyl Config` / `Dactyl Config L`) without a USB cable. Both halves use `PartitionScheme=min_spiffs` with two 1.875 MB app partitions (`app0` and `app1`) and preserve the NVS partition (`0x9000`) and the macOS BLE bonding keys.
- **Security and Brick Protection:**
  - Because config mode uses a static random BLE address without OS bonding, GATT characteristics are unauthenticated.
  - The firmware accepts and activates an update image (`Update.end(true)`) only after a full **Ed25519 signature verification** (`DactylOtaVerify.h`) against the embedded public key (`DactylOtaKey.h`, generated by `scripts/generate-ota-key.py`).
  - Signature verification streams through SHA-512 ($H(R \parallel A \parallel M)$ per RFC 8032) block by block with minimal RAM usage (~250 bytes).
  - Any manipulated byte or signature mismatch immediately aborts the update (`Update.abort()`) and leaves the board safely on the active partition.
  - On successful boot after an update, `setup()` marks the new app partition as valid (`esp_ota_mark_app_valid_cancel_rollback()`).
- **GATT Transport:**
  - `CONFIG_SERVICE_UUID`: `"4fafc201-1fb5-459e-8fcc-c5c9c331914b"`.
  - Commands run over `CONFIG_CHARACTERISTIC_UUID` (`...26a8`): `OTA_BEGIN <size_bytes> <hex_ed25519_sig_64bytes>`, `OTA_END`, `OTA_ABORT`.
  - Binary chunks are sent to `OTA_CHAR_UUID` (`beb5483e-36e1-4688-b7f5-ea07361b26a9`): 2-byte little-endian sequence number `seq` followed by up to 238 bytes of firmware payload (max. 240 bytes total per packet).
  - The firmware enforces contiguous sequence numbers (`OTA_ERR:SEQ_MISMATCH`), writes to `Update.write()`, and acknowledges every 16 chunks and on the final chunk with `OTA_ACK:<seq>:<written_bytes>`.
- **Inactivity Timeout Handling:**
  - While `otaInProgress` is true and chunks arrive within 15 seconds, the normal 3-minute config mode inactivity timeout is paused.
  - If 15 seconds pass without an incoming chunk, `processOtaTimeout()` automatically aborts the update (`Update.abort()`), sets `otaInProgress = false`, and restores the regular 3-minute inactivity timer.
- **Backend and App Integration:**
  - Backend endpoint `POST /api/compile_ota?side=L|R`: compiles the half with `arduino-cli compile --fqbn ... --build-path <tmpdir>`, signs the binary with `.ota_signing_key.pem`, and streams progress via NDJSON or returns JSON with base64-encoded binary and hex signature.
  - Web Configurator (`js/ble.js`, `js/flash-log.js`, `index.html`): button "Über Bluetooth flashen (OTA)" in the flash tab streams compilation, signing, upload percentage, and verification progress in the live flash dialog.
- "Rückgängig" and "Alle verwerfen" call `requestLiveSync(side, true)`: the app sends the restored state also without a pending change, because an earlier sync can already have sent the undone change.
- While the layout diff runs (`deviceSnapshotRead`, `diffFlowActive`), or when the connection ends before the sync starts, the live sync sends nothing and shows the pending hint; the changes stay pending for the next one-shot auto-sync, BLE connect or "Auf ESP32 speichern". A failed sync keeps the changes pending.
- NVS skips a write when the new value equals the stored value (also for blobs, ESP-IDF `Storage::writeItem`). So a live sync writes only the changed data, for example the `keymap` blob (672 bytes, about 23 entries) after a key change, and always `num_macros` (`saveMacrosToNVS` removes it first). The old `SET_KEY` also wrote all three key blobs, so a key change costs about the same as before. NVS spreads the writes over its 5 pages (wear leveling); about 24 entries per sync give about 2.6 million syncs at 100,000 erase cycles per page. Over USB the live sync also runs in keyboard mode.

### Layout diff (`writeConfigWithDiff`)

- Layout diff: the button "Auf ESP32 speichern" (`writeConfigWithDiff`, `js/config-sync.js`) first sends `GET_CONFIG` to the connected half. While this read runs, `captureDeviceSnapshotLine` takes the `LAYER_NAMES` / `*_DATA` / `CONFIG_SYNC_DONE` lines of that half into a snapshot and does not change the local config. `diffKeymap` (`js/config-model.js`) compares each physical key (tap, hold, double-tap as numeric codes) and each layer name; the dialog `#syncDiffModal` shows the result, and only "Übertragen" starts `writeConfigToESP32` with `expectedSide`; if the connection changed to the other half meanwhile, nothing is sent. `GET_CONFIG` also sends combos, key pairs and macros (see "GET_CONFIG lists"); the dialog lists their differences. If the read fails (timeout 8 s), a confirmation asks whether to sync without a diff. After a timeout, late `GET_CONFIG` lines of that half are still discarded until `CONFIG_SYNC_DONE` or 30 s, so a late reply never overwrites the local config or clears pending changes. While the diff flow runs (`diffFlowActive`), a second click and "Vom ESP32 laden" do nothing; while late lines are discarded, a second click shows a hint. A BLE or USB disconnect ends a running read at once (`abortDeviceSnapshotReadIfDisconnected`). The One-Shot Auto-Sync skips the diff; it does not start while a read or the diff flow runs (`runAutoSync`).

### Physical key capture (`createKeyCapture`, `js/editor-events.js`, `js/leader-ui.js`)

   - The combo dialog (button `btnCaptureComboKeys`) and the leader editor (button `btnCaptureLeader`) have the toggle "Auf Tastatur drücken". While it is on, a press on the keyboard fills the next key slot: key 1, 2, 3 of the combo, or key 1..4 of the leader sequence. The capture stops when all slots are full, with the toggle, when the dialog closes or saves, when the leader sequence is added, or when the edited half changes. Only one capture runs at a time.
   - The state machine is DOM-free (`createKeyCapture`, `keyCaptureStart`, `keyCaptureFeed`, `keyCaptureStop` in `js/config-model.js`). `js/serial.js` feeds it from `MATRIX:` (press and release), `KEY_PRESS:` / `KEY_RELEASE:` and `SPLIT_KEY:` through `feedKeyCapture`. A Bluetooth keyboard also sends the press to the browser as `keydown`: while a capture runs, a capture-phase listener (`blockKeysDuringCapture`) stops `keydown` and `keyup` so that no editor shortcut or focused button reacts. `Tab` and input fields stay free, and `Esc` ends the capture. A `MATRIX:` press that the bounce check flags is not a new press and fills no slot. A rejected press of the kind `unusable`, `duplicate` or `not-physical` shows a toast. The capture also stops on a serial or BLE disconnect and after `KEY_CAPTURE_IDLE_MS` (30 s) without an accepted press. The combo capture clears key 3 at the start, the leader capture clears all four slots. A held key whose release got lost blocks only `KEY_CAPTURE_HELD_MS` (1000 ms). Switching the edited half stops the capture (`switchEditSide`). The capture needs a transport that reports key events (USB serial; over BLE the config mode reports `KEY_PRESS`).
   - Rejected events (`reason`): `wrong-side` (not the edited half), `held` (the same coordinate again before its release; one press arrives as `MATRIX:`, `KEY_PRESS:` and `SPLIT_KEY:` and counts once), `duplicate` (a coordinate that a slot already holds; the combo needs distinct keys), `not-physical` (a position the half does not have, for example `R4C0` on the right half), `unusable` (the leader editor takes only the layer 0 tap of the key if it is a leader key code, so a modifier or layer key does not count), `full`, `inactive`.
   - The leader sequence takes the layer 0 key code at the coordinate and allows the same key again after its release.

### Layout check (`lintLayouts`, `js/layout-lint-ui.js`)

   - `lintLayouts(configs, profiles, labelFor)` (`js/config-model.js`, no DOM) checks the configurations of both halves together, because both halves share the active layer (see "Layer sync"). It returns findings `{ level: "warn" | "info", side, code, message }`, warnings first. `side` is `null` for a finding about both halves. The check changes nothing and blocks nothing.
   - Warnings: `absent-key-action` (an action on a position the half does not have, also outside the matrix such as `R2C6`; the action has no effect), `layer-unreachable` (a layer with its own content, but no key and no combo leads to it), `layer-trap` (a layer that can be locked, but has no key back), `combo-duplicate` (two combos on the same keys with overlapping layer masks), `combo-hold-cancelled` (a combo key has a hold action, which the combo cancels), `override-key-unmapped` (a key override whose trigger key nothing sends on any layer of its mask; it never fires. The check looks at the keys of both halves, because the list applies to both: tap, hold and double-tap actions, key pair members, macro steps, combo actions and leader actions count). Hints: `pair-unused`, `macro-unused`, `combo-hold-cancelled` when the combo key has only a double-tap action.
   - Layer graph: the check follows `MO_n`, `TG_n`, `LAYER_UP` and `LAYER_DOWN` (also as `ACT_` name) from layer 0 through the keys of both halves. It resolves each key like `resolveKeyActions`: a key with no action on a layer falls back to layer 0, a hold action without a tap acts as a tap, a double-tap without a tap does nothing. Only keys that exist on the half count. A combo with the behavior "Layer umschalten" works on every layer and uses the layer `action & 7` like the firmware; `TG_0` clears all locked layers. A combo counts only when both keys exist on the half (`lintComboCanFire`) and the action is a string; the same rule applies to the hints `combo-hold-cancelled` and the check `combo-duplicate`. The layer of a combo action is read like the layer of a key, so `TG_2` and `ACT_TG_2` both count. The hint `combo-hold-cancelled` resolves each key like the firmware (`lintResolvedCell`): a transparent key on a layer inherits hold and double-tap from layer 0, and a layer with its own key without hold is not listed.
   - Malformed data (an imported configuration): the check ignores a combo without keys or with an action that is not a string, and a `combos`, `keyPairs` or `macros` value that is not a list. If the check still throws, `currentLayoutLint` catches the error and returns no findings, so the matrix, the layout diff and the flash never stop because of the check.
   - A layer counts as reachable when a path leads to it. It counts as locked when `TG_n`, `LAYER_UP`, `LAYER_DOWN` or such a combo can lock it; `MO_n` needs no way back. The way back is `TG_n` of the layer itself, `TG_0`, `LAYER_UP`, `LAYER_DOWN` on that layer, or a combo. A layer without own content (a copy of layer 0) is not reported as unreachable.
   - Known limits: the check does not simulate timing (tapping term, combo window) and does not know the host layout. The firmware lets `LAYER_UP` and `LAYER_DOWN` step from the layer where the key acts and clear all other locked layers; the check follows the same step from each reachable layer. It does not model which locked layers are active together.
   - Jump to the entry: findings about a combo carry `combo` (index), findings about a key override carry `override` (index). In the matrix tab they have a button "Zum Eintrag" (`jumpToLintEntry`, `js/layout-lint-ui.js`): it switches to the half of the finding, opens the tab "Combos", scrolls to the row (`data-combo-index`, `data-override-index`) and highlights it for 2.5 s. Tests: `tests/test_app_logic.js` ("Layout-Prüfung: ...").
   - Dead keys: the matrix does not draw a position that the half does not have (`isPhysicalKey`), so an action there is invisible and cannot be edited. The finding `absent-key-action` carries `r`, `c` and `layers`. In the matrix tab it has a button "Entfernen" (`removeAbsentKeyActions`): `clearAbsentKeyActions` returns the new layers and the old cells; the click clears the actions on the listed layers, marks the change as pending (type `key`, title `Taste [R<r>, C<c>] entfernt`, like a key edit in the inspector), saves the half and offers "Rückgängig" (the old cells come back). The function never clears a key that exists on the half. A finding of the other half first switches the edited half, like a click on a key of that half. The layout diff dialog lists the warning without the button, because the configuration must not change during the transfer.
   - Display: `renderLayoutLint` (`js/layout-lint-ui.js`, called at the end of `renderMatrix`) shows a collapsible panel in the matrix tab with the counts. The layout diff dialog (`showSyncDiffDialog`) lists the warnings of both halves. "Auf Dactyl flashen" writes the warnings into the flash log before the compile; the flash runs anyway. These lines have no `stage`, so the dialog keeps its phase text until the server reports the first phase (`openFlashLogDialog` sets the phase only for an event with a `stage`).

### Key swap by drag and cross-half layer mirror (`swapLayerKeys`, `mirrorLayerAcrossSides`)

- `swapLayerKeys(layer, r1, c1, r2, c2)` (`js/config-model.js`, no DOM) returns a new layer with the two cells exchanged. It returns `null` for the same cell, an index outside the 6 x 7 matrix or a layer that is not a list. The input stays unchanged.
- Drag and drop: `createKeycapElement` (`js/editor.js`) makes each keycap of the edited half draggable. A drop on another keycap of the same half and layer calls `swapKeysByDrag`. The revert closure swaps the same two cells again on the current layer, so later edits of other keys stay ("Rückgängig"). A keycap of the other half in the view "Beide" takes no drop.
- `mirrorLayerAcrossSides(layer, srcProfile, dstProfile)` returns a new layer for the other half. Finger keys mirror to column `5 - c`. Thumb keys mirror by the grid of `thumbDefs` (same `row`, column `4 - col`). Absent keys of either half are skipped; unused target positions stay transparent. In tap, hold and double-tap, `KEY_LEFT_*` and `KEY_RIGHT_*` modifiers, left and right arrows, left and right brackets, `OSM_L*` and `OSM_R*`, mouse left and right move and wheel left and right swap sides. - The layer tool operation "Tauschen" (`applyLayerToolFromUI` in `js/editor.js`) calls `swapLayersWithRefs(config, layerA, layerB)` (`js/config-model.js`). It returns a new configuration and leaves the input unchanged; it returns `null` for equal or invalid layers. Besides `layers` and `layerNames`, it swaps every reference to the two layers: `MO_n`, `TG_n` and `OSL_n` in `tap`, `hold` and `dtap` (also with the prefix `ACT_`), the combo `action` and the combo `layerMask`, the `layerMask` of key overrides (bit A and bit B), `settings.triLayers` (`a`, `b`, `target`), `settings.bootLayer` and `settings.numWordLayer`. The masks `0xFF` (all layers) stay unchanged. A `triLayers` rule that the swap moves to layer 0 is dropped (rules need layers 1..7). A short `layerNames` list is padded with the default names. The swap changes only the edited half; the other half keeps its own `MO_n` references, and the confirm text says so. The pending change `layer_tool` is a snapshot; its revert closure restores the whole configuration of before the swap. Copy and clear still use `applyLayerOperation`. Tests: `tests/test_app_logic.js` ("Ebenen tauschen mit Verweisen").
- The button "Auf andere Hälfte spiegeln" (`#btnMirrorLayer`, `mirrorActiveLayerToOtherSide`) asks for confirmation, replaces the active layer of the other half and marks a snapshot pending change (type `layer_mirror`) for that half, like the layer tools. The change carries a revert closure with `sideRevert`: `markPendingSync` keeps it for the other half (other revert closures write into `currentConfig` and are dropped there). The closure restores the old layer list of the target half. A missing target layer is padded with transparent layers. Tests: `tests/test_app_logic.js` ("Tasten tauschen", "Ebene spiegeln").

### Backspace correction heatmap (`recordKeyPress`, `js/heatmap.js`)

- `recordKeyPress(stats, r, c, nowMs, layer, role)` (`js/config-model.js`) counts a press with the role `backspace` as one correction of the key before it, if that key came at most `CORRECTION_WINDOW_MS` (1500 ms) earlier on the same half. The Backspace press clears the key before it, so a second or held Backspace corrects nothing more, and a press after the window creates no correction. The Backspace press itself counts as a normal press. `stats.corrections` holds `{ "r_c": n }`; `lastTypedId` and `lastTypedMs` are RAM only.
- `pressedKeyRole(side, r, c, pressedLayer)` (`js/live-monitor.js`) decides from the config of the half; `keyPressRole(tap)` (`js/config-model.js`) maps the tap action to a role: `backspace` (`KEY_BACKSPACE`), `silent` (no action, modifier, layer key, one-shot, host slot: it leaves the key before it unchanged, so `s`, `Shift`, `Backspace` corrects `s`) or `typed`. A key without action on a higher layer falls back to layer 0, like the firmware. `js/serial.js` passes the role for `KEY_PRESS:` and `SPLIT_KEY:` (`SPLIT_KEY` has no action code). A Backspace that a macro or key pair sends, and a hold or double-tap Backspace, do not count.
- Limits: the statistic is per half, so a Backspace on one half never corrects a key of the other half (a Backspace on a thumb key of the opposite half is not counted). In the mode "Korrekturen" the layer button `#btnHeatmapLayer` is disabled.
- `correctionShares(stats)` returns the share (corrections / presses, all layers) per key; a key with fewer than `CORRECTION_MIN_PRESSES` (5) presses is left out, so one press and one correction do not give 100 %. `topCorrectedKeys(stats, limit = 5)` lists the five keys with the highest share, sorted by share and then by key; `#topCorrectedKeys` shows them as `R2C2: 40 % (4/10)`.
- The button `#btnHeatmapErrors` switches the heatmap to the correction share (`heatmapErrors` in `app.js`, `applyErrorClass` in `js/heatmap.js`). The heat level is the share relative to the key with the highest share; the number on the key is the share in percent. The mode ignores the layer button (`#btnHeatmapLayer`).
- Storage: `serializeTypingStats` adds `corrections: { "r_c": n }` to the `localStorage` object, only if the half has corrections (browser only, same key per half). An older app version discards the key. `createTypingStats` discards invalid positions and counts. The reset of the heatmap clears the corrections.

### Finger load analysis (`fingerLoad`, `js/heatmap.js`)

- Each side profile holds `fingerCols`: the finger of the columns 0..5 of the rows 0..4 (right: index, index, middle, ring, pinky, pinky; left: the reverse). Row 5 and column 6 are the thumb. `fingerOfKey(r, c, profile)` (`js/config-model.js`) returns the finger id (`FINGER_IDS`: pinky, ring, middle, index, thumb) or `null` for a missing or invalid key.
- `fingerLoad(stats)` returns the presses and the share per finger of one half. `halfLoad(entries)` returns the share of each half in all presses. `updateFingerLoadUI` (`js/heatmap.js`) shows both next to the heatmap in `#fingerLoad`: the halves in `#fingerLoadHalves`, the fingers of the edited half in `#fingerLoadBars`. The shares count over all layers, like WPM.
- `recordKeyPress` also counts a same-finger sequence: two different keys of one finger in a row (`sameFingerPairKey`). The thumb does not count, because thumb keys follow each other often. The same key twice does not count. A key that the half does not have does not change the sequence. The pair has no direction (`"a|b"` with `a` before `b` in row and column order). The sequence is per half and in RAM only (`stats.lastKeyId`, `stats.lastKeyMs`); it does not survive a restart. A pause longer than `SAME_FINGER_MAX_GAP_MS` (1 s) starts a new sequence, so two presses minutes apart do not count.
- `topSameFingerPairs(stats, limit = 5)` lists the five most frequent pairs, sorted by count and then by key. `#sameFingerTotal` shows the total, `#sameFingerPairs` the list.
- Storage: `serializeTypingStats` adds `sameFinger: { pairs: { "r_c|r_c": n } }` to the `localStorage` object, only if the half has a sequence. An older app version discards the key. `createTypingStats` reads the older forms (`{ "r_c": n }` and with `layers`) with empty sequences, and discards pairs that are invalid for the half (other finger, thumb, wrong order, missing key, bad count).

### Ergonomic swap suggestions (`suggestErgonomicSwaps`, `js/heatmap.js`)

- `suggestErgonomicSwaps(stats, config, profile)` (`js/config-model.js`) ranks up to `ERGONOMIC_SWAP_LIMIT` (5, optional fourth argument `limit` lowers it) swaps for layer 0. Source keys are frequent keys on a high-effort position: the pinky finger (`fingerOfKey`), the top row (row 0) or a key of the top same-finger pairs (`topSameFingerPairs`). Target keys are the least used keys on the home row (row 2) under index, middle or ring finger. A swap needs a source count above the target count; the list is sorted by source count, and each position appears once.
- Only plain keys count: the layer 0 tap action is a standard key (`isStandardKeyOrModifier`) and not a modifier, and the cell has no hold and no double-tap action. Modifiers, layer keys, macros, key pairs, empty cells and keys that the half does not have stay untouched. The counts are the layer 0 counters (`stats.layerCounts[0]`); older data without layer counters falls back to the total counters.
- `updateErgonomicSwapsUI` shows the list in `#ergonomicSwaps` (panel `#fingerLoad`). The button "Tauschen" calls `swapKeysByDrag(r1, c1, r2, c2, 0)`, which uses `swapLayerKeys` on layer 0 and records a pending change `key_swap` with undo. The list is rebuilt only when the suggestions or their labels change. The counters belong to positions, not to keys: `ergonomicSwappedPositions` (`js/heatmap.js`) passes the swapped positions as the fifth argument `exclude`, so the list does not suggest the swap back. The reset of the heatmap clears the set. The set lives in RAM for the session, per half (`ergonomicSwappedFor(side)`); "Rückgängig" of the swap removes the two positions again, and a swap that `swapKeysByDrag` rejects adds nothing. A swap by drag, a profile load, an import or a mirror action does not touch the set; after such a change, reset the heatmap. The home row has at most four target positions (index twice, middle, ring), so the list holds at most four swaps in practice; the limit of five stays as an upper bound. A home-row key under index, middle or ring finger is never a source.

### Combo suggestions from frequent bigrams (`suggestCombos`, `js/heatmap.js`)

- `recordKeyPress` (`js/config-model.js`) counts each bigram: two different typed keys of the same half pressed one after the other within `SAME_FINGER_MAX_GAP_MS` (1 s), on layer 0 (or without a layer). A `silent` press (modifier, layer key, no action) is skipped and does not break the sequence; a backspace or a press on another layer forms no bigram and ends the sequence. The counters live in `stats.bigrams` (`"r_c|r_c"`, smaller position first, undirected). `serializeTypingStats` stores them under `bigrams`; `createTypingStats` drops invalid entries (`sanitizeBigrams`). An older stored statistic without `bigrams` loads with an empty list.
- `suggestCombos(stats, config, profile)` lists up to `COMBO_SUGGESTION_LIMIT` (5) pairs, most frequent first. A pair needs two adjacent finger keys (also diagonal; the thumb row never counts), a tap action on layer 0 for both keys, and no combo that already uses both keys (any key order, also as two keys of a three-key combo). The layer mask of a combo is ignored on purpose: a pair with a combo on one layer only gets no suggestion for the other layers; add that combo by hand.
- `updateComboSuggestionsUI` shows the list in `#comboSuggestions` (panel `#fingerLoad`). The button "Combo anlegen" calls `openComboModal({ a, b })` (`js/editor-events.js`), which opens the combo dialog with key 1 and key 2 filled in. The list is rebuilt only when the suggestions change. The heatmap reset clears the counters.

### Heatmap CSV export (`buildHeatmapCsv`, `js/heatmap.js`)

- `buildHeatmapCsv(heatmapData, config)` (`js/config-model.js`, no DOM) builds the CSV of the typing statistics. `heatmapData` is `[{ side, stats }]`, `config` maps each side to its config; it only gives the layer 0 label. The button `#btnHeatmapCsv` ("Als CSV speichern") calls `downloadHeatmapCsv` (`js/heatmap.js`), which exports both halves into `dactyl_heatmap_<date>.csv`.
- Columns: `half,row,column,layer_0_label,total,layer_0..layer_7,corrections`. One row for each key with a total counter or a correction, sorted by half order, row and column. A counter that is missing or not a positive integer is written as `0`. Line end is CRLF. A field with `"`, `,` or `;` is quoted; a field of more than one character that starts with `=`, `+`, `-`, `@` or a tab gets a leading `'` so a spreadsheet does not read it as a formula. The file starts with a UTF-8 BOM for Excel. Without a counted key, the button shows a toast and saves nothing.
- Privacy: the file holds only counters per key. It has no typed text, no time of a single press and no key sequence (`bigrams`, `sameFinger`, `recent` and the RAM-only fields are never read). Layer 0 labels come from the config, not from the typing.
- Empty or invalid input (not an array, no entry, an entry without `side` or without `counts` and `layerCounts`) returns `null`; the download then does nothing. A missing config only gives empty labels.

### Flash log stream (`/api/save_and_flash&stream=1`)

   - With `&stream=1`, `/api/save_and_flash` answers with `application/x-ndjson`: one line `{"type":"log","stage":"port|compile|nvs|upload","line":...}` per status line and per `arduino-cli` output line (stdout and stderr, `\r` splits esptool progress lines, `strip_terminal_controls` removes terminal control sequences such as `ESC[1A` and `ESC[2K`; a line that is empty afterwards is dropped), as soon as the line is printed (`run_cli`), and the line `{"type":"result", ...}` last. The response has no `Content-Length` and ends with the connection close. A validation error comes before the stream as normal JSON with HTTP 400. A closed app window does not stop a running upload. Without `stream`, the endpoint answers with one JSON object as before. The `error` text keeps only the last `FLASH_ERROR_TAIL_CHARS` (8000) characters. The app shows the lines in the dialog `#flashLogModal` (`js/flash-log.js`, max. `FLASH_LOG_MAX_LINES` lines); it closes only after the result.

### Automatic backups (`/api/backups`)

   - Provides `/api/backups?side=L|R` for automatic backups of a half in `config_backups/right` / `config_backups/left` of the data directory (local state, in `.gitignore`). `writeConfigToESP32` (`backupConfigOnServer`, `js/config-sync.js`) POSTs the config before its first command; `/api/save_and_flash` calls `create_backup(config, side, "flash")` before the flash. A failed backup only shows a hint or log line; the sync or flash continues. The app aborts the backup request after `BACKUP_TIMEOUT_MS` (3 s) and shows the hint once per failure streak. A backup is skipped when the newest backup has the same config, and a `sync` backup also when the newest backup is younger than `BACKUP_MIN_INTERVAL_S` (600 s; the live sync runs after each change). A `flash` backup ignores the interval. The server keeps the newest `MAX_BACKUPS` (20) per half. Files are `backup-<sequence>-<UTC stamp>.json`; the sequence number sets the order (a clock set back does not make a new backup look old) with `{ created, savedAt, reason, config }`; each config passes `validate_config` of that half. GET returns `{ backups: [{ id, savedAt, reason, config }], skipped }`, newest first; an invalid file is skipped and counted. The dialog "Profile" lists them under "Automatische Backups"; loading one is a snapshot pending change (`backup_load`, flags `pairs` and `macros`), like a profile.

### NVS layout checksum (`keymap_crc`)

   - `saveKeymapToNVS` and the default sync in `loadKeymapFromNVS` write the NVS key `keymap_crc`: a CRC32 (IEEE) over `KEYMAP`, `HOLDMAP` and `DTAPMAP` (`nvsLayoutCrcOfRam`). The sum is written last, after the blobs.
   - At boot, `storedLayoutChecksumInvalid` reads the three stored blobs and compares their CRC32 with `keymap_crc`. A wrong sum, a missing blob or a wrong blob length counts as corrupt. The firmware prints `NVS: Checksumme ungültig! Verwende Firmware-Defaults.`, applies the compiled-in defaults (same path as a new default layout, including the removal of key pairs, macros and leader sequences) and writes a new sum.
   - Exception to `KEYMAP_DEFAULTS_ID 0`: a repository flash keeps the NVS keymap only while its checksum is valid. A corrupt blob gets the compiled-in defaults, also with ID `0`.
   - A write that fails for one of the three blobs removes `keymap_crc` instead of writing a sum of the new RAM data; the next boot keeps the stored layout unchecked and adds a new sum. The sum is written after the blobs: a power loss in that short window leaves a mismatch, and the next boot applies the defaults. Restore the layout with a profile or a BLE sync.
   - A `keymap` blob with a wrong length counts as missing: the defaults apply without the checksum log line (as before this feature).
   - Without `keymap_crc` (firmware before this feature) nothing is checked, also not a torn write from before: the stored keymap stays and the sum is added once both `holdmap` and `dtapmap` exist.
   - The sum covers only the three main blobs. Tapping terms, hold flavors, quick-tap terms, pairs, macros and settings have no sum.
   - A BLE edit goes through `SAVE_NVS` (`saveKeymapToNVS`), so it updates the sum. `DACTYL_FW_VERSION` is 56.
   - Tests: `test_nvs_checksum_corrupt_keymap_falls_back_to_defaults`, `test_nvs_checksum_corrupt_holdmap_and_missing_blob_fall_back`, `test_nvs_without_checksum_keeps_keymap_and_adds_crc`.

### NVS backup during flash (`/api/nvs_backups`, `/api/nvs_restore`)

   - The NVS partition (`NVS_OFFSET` `0x9000`, `NVS_SIZE` 20 KB, `min_spiffs`) holds the keymap and the macOS BLE bond. A chip erase or a broken flash deletes it; macOS then rejects the reconnect until the user forgets and pairs the device again.
   - `flash_firmware` reads the NVS partition with `esptool read-flash` (`dump_nvs`) after the port check before the upload, on the checked port, at 115200 baud. The stage is `nvs`; the app shows "NVS-Sicherung". A compile error or a changed port skips the read.
   - `save_nvs_image` stores the image next to the config backups of that half (`config_backups/right|left/nvs-<sequence>-<UTC stamp>.bin`) and keeps the newest `MAX_NVS_BACKUPS` (10). The sequence number sets the order. An image with a size other than `NVS_SIZE` is never stored. An erased partition (only `0xFF`, `NvsEmptyError`) is not stored either, so it cannot push valid images out. The images hold the BLE bond keys: the folder gets mode 0700, each file mode 0600.
   - A failed read (no `esptool`, error, wrong size, timeout `NVS_TIMEOUT_S`) does not stop the flash: the upload does not write the NVS partition. The log shows a warning, and the result has `nvsBackup: null`. On success, `nvsBackup` is the file name.
   - `find_esptool` uses the newest `esptool` of the arduino-cli ESP32 core (`~/Library/Arduino15/packages/esp32/tools/esptool_py/<version>/esptool`), otherwise `esptool` / `esptool.py` from `PATH`.
   - `npm run flash -- L|R` (`scripts/flash.py`) runs the same `flash_firmware` without the app: it uses the repository sketch (no rendered layout, `KEYMAP_DEFAULTS_ID 0`, so the NVS keymap stays) and stores the NVS image in the backup folder of the app data directory (`DACTYL_DATA_DIR`, default `~/Library/Application Support/dactyl-configurator/data`), so `/api/nvs_backups` lists it. It sets the sketch paths of `server.py` to the checkout, also when `DACTYL_DATA_DIR` is set. It refuses a sketch whose `KEYMAP_DEFAULTS_ID` is not `0UL` (a `.ino` that `python3 server.py` rendered in place): such a flash would overwrite the NVS keymap; `git restore firmware/<sketch>` fixes it. It returns 0 on success, 1 on a failed or refused flash and 2 on a wrong argument. A flash without an NVS backup still returns 0 and prints the warning to stderr.
   - Keymap on a repository flash: `loadKeymapFromNVS` compares `KEYMAP_DEFAULTS_ID` with the NVS key `applied_id` (the last non-zero ID that the device applied). A firmware with ID `0` never replaces an existing keymap, also not after a change of the repository defaults; key pairs, key overrides and macros stay. A new non-zero ID (flash from the app) applies its defaults once and stores the ID; a second boot with the same ID keeps a later BLE edit. The first start and `RESET_CONFIG` (no keymap) apply the compiled-in defaults and remove `applied_id` for ID `0`. `defaults_fp` stays for the migration of firmware from before `applied_id`: without `applied_id` and with a non-zero ID, the fingerprint decides; the `fw_build` migration is unchanged. After the upload, `scripts/flash.py` resets the board (`read_boot_log`, RTS pulse, up to `BOOT_LOG_TIMEOUT_S` 8 s) and reads the boot log until the line `NVS: Neue Default-Belegung` or `NVS: Gespeicherte Keymap geladen` (at most `BOOT_LOG_TIMEOUT_S`). On `NVS: Neue Default-Belegung` it prints the path of the NVS backup of this flash (or the note that none exists) and the restore way: `POST /api/nvs_restore?side=L|R` or the dialog "Profile". Reading the log is best effort and never changes the exit code; without a marker the script prints "Start-Log nicht gelesen", and it reports `NVS: FEHLER` too. The read runs after the USB lock is released, so another process that polls the port at the same time (the app server with `GET_INFO`) can see a second board reset; close the app status polling before `npm run flash` if the log shows no marker. Hardware check: with ID `0`, the keymap stays after `npm run flash`.
   - `flash_firmware` and `restore_nvs` take the USB lock `USB_LOCK_FILE` (`flock` on `$TMPDIR/dactyl-configurator-usb.lock`, shared by the app server and `npm run flash`). A second flash or restore at the same time fails at once with stage `port`; nothing touches the serial port. The lock file opens with `O_NOFOLLOW` and mode 0600; an unusable lock file also gives a stage `port` error. The lock does not cover the render of `/api/save_and_flash`: the app renders into its copy in the data directory, and `npm run flash` compiles the checkout, so they never share a file. Only `python3 server.py` in the checkout renders the `.ino` that `npm run flash` compiles; do not run both at the same time.
   - `GET /api/nvs_backups?side=L|R` returns `{ backups: [{ id, savedAt }] }`, newest first, only files with the correct size.
   - `POST /api/nvs_restore?side=L|R` with `{ "id": "nvs-..." }` writes that image back to `0x9000` (`esptool write-flash`, `restore_nvs`). The id must match the file name pattern and exist in the folder of that half with the correct size; otherwise HTTP 400, before a port is opened. The upload port is the port whose board answers `GET_INFO` with that half; without a match nothing is written. Before the write, `restore_nvs` reads the current NVS and stores it as a new image (`previousBackup` in the result), so the restore stays reversible. A failed read stops the restore before the write. The read restarts the board, so `restore_nvs` checks the side of the port again before the write; an erased partition gives `previousBackup: null`. The server does not compare firmware versions: restore only an image of the same NVS format. The dialog "Profile" lists the NVS backups under "NVS-Sicherungen (USB)" and restores a selected image after confirmation.

### Raw matrix event (`MATRIX:`)

   - `onMatrixKeyChange()` sends `MATRIX:{"r":..,"c":..,"pressed":0|1,"t":..}` for each physical change, independent of layer, tap-hold and combo logic. It sends the line after the HID events of that change (`applyMatrixKeyChange`), so the serial output does not delay the key press. A key with action `0` also sends it; `KEY_PRESS` stays limited to keys with an action.
   - The firmware prints `MATRIX:` only on USB serial (`Serial.println`), never over BLE, also not in config mode: no keylogger channel and no extra BLE load next to the sync acks. The matrix test for keys with action `0` therefore needs USB; over BLE the matrix test still counts keys with an action through `KEY_PRESS`.
   - The app uses `MATRIX:` only for the matrix test (`parseMatrixLine`, `js/config-model.js`). `KEY_PRESS` and `SPLIT_KEY` still mark keys in the matrix test too; marking is idempotent, so the count stays correct. Live monitor and heatmap keep using `KEY_PRESS`. Left keys reach the master's USB as `SPLIT_KEY:`, which also covers keys with action `0`. While the left half itself is connected (BLE or USB), the app ignores `SPLIT_KEY`, because that half reports its keys directly (no double count in heatmap and statistics).
   - `t` is the scan time of the change (`atMs`, `millis()` as 32 bit), not the print time: the master applies a held key later, and a bounce check needs the real scan time. The line is at most 47 characters; `matrixBuf` has 64 bytes.
   - Bounce detection (`recordMatrixBounce`, `MATRIX_BOUNCE_MS` 30, `js/config-model.js`): a press at most 30 ms after the release of the same key counts as one bounce of that key. The gap is computed modulo 2^32, so the `millis()` overflow after about 49 days does not break it. Each release allows one bounce, so a series of presses without a release counts once. The matrix test (`js/matrix-test.js`) marks a bouncing key (`is-bouncing`), lists it with its count and advises to raise `debounceMs`.
   - Blind range: the firmware debounces each key on its own (`DactylDebounce.h`). A press is sent at once; changes of that key are hidden for `debounceMs`, and a release needs `debounceMs` of open contact. A bounce shorter than `debounceMs` therefore stays invisible to the test, and with `debounceMs` of 30 ms or more the test cannot see a bounce any more. If it still reports one, the hint says to send the setting to the keyboard and to check the switch and the solder joint.
   - The remembered release times are cleared when the time goes back (modulo 2^32 gap above 2^31: the keyboard restarted, `millis()` begins at 0) and on each `DEVICE_INFO:` and `MODE:` line (`resetMatrixBounceState`: new connection, mode change, restart). The counted bounces stay. A cleared state can only miss a bounce; it never gives a false one.
   - A line without `t` (older firmware) or with an invalid `t` still marks the key but gives no bounce result. `SPLIT_KEY` has no scan time, so a bounce of a left key shows only when the left half is connected itself (BLE or USB) and sends `MATRIX:`. The bounce counters belong to the matrix test of the half and reset with "Test zurücksetzen".

### GET_CONFIG lists

- After the key matrices, `GET_CONFIG` sends combos, key pairs and macros in short blocks (`sendCombosPairsMacros`, `DactylLogic.h`): `COMBO_COUNT:<n>` and `COMBO_DATA:{"o":<offset>,"e":[[r1,c1,r2,c2,behavior,action,layerMask(,r3,c3,windowMs)],...]}` (3 per line; the last three values appear only for a combo with a third key or an own window), `PAIR_COUNT:<n>` and `PAIR_DATA:{"o":..,"e":[[first,second],...]}` (8 per line), `MACRO_COUNT:<n>` and `MACRO_DATA:{"i":<index>,"n":<steps>,"o":<offset>,"s":[[type,code,ms],...]}` (8 steps per line; an empty macro sends one line without steps), then `CONFIG_SYNC_DONE`. From `DACTYL_FW_VERSION` 26, both halves send `LEADER_COUNT:<n>` and `LEADER_DATA:{"o":..,"e":[[action,k1,k2,k3,k4],...]}` (4 per line) before the macros (see "Leader key"). Each line stays below 160 characters, so it fits one BLE notification at a small MTU (`test_get_config_lines_stay_short_at_maximum`). `DACTYL_FW_VERSION` is 5.
- App: `captureListLine` (`js/config-model.js`) checks each line (decimal count, offset in sequence, combo behavior 0..2, macro step type 1..4) and takes it into the snapshot. An invalid line marks the snapshot as broken. `snapshotListsState` returns `absent` (firmware before version 5 sends no lists), `incomplete` (a line is missing or invalid) or `complete`. `diffKeymap` returns `lists` (`diffLists`): combos, key pairs and macros per index, in list order (the firmware checks combos in this order). With `absent` or `incomplete`, the diff compares nothing; the dialog asks to flash the half (`absent`) or says that the lists arrived incomplete.
- Late list lines after a timeout are discarded like the key lines (`captureDeviceSnapshotLine`).
- "Vom ESP32 laden" reads the complete config: see "Read the complete configuration from the device".
- Security: in config mode, a nearby BLE client can now also read the macros (they can hold typed text). See "BLE Command Authorization" in `AGENTS.md`.

### Read the complete configuration from the device

- The button "Vom ESP32 laden" (`readConfigFromESP32`, `js/config-sync.js`) works on the connected half, and only when it is the edited half. It uses the snapshot path of the layout diff: `readDeviceSnapshot(side, true)` sends `GET_INFO`, then `GET_CONFIG`. `captureDeviceSnapshotLine` stores `DEVICE_INFO` in `snapshot.info` and passes the line on; `handleSerialLine` (`js/serial.js`) then skips the settings writes and the input updates while this read runs (`holdSettings`), so the local config stays unchanged until the confirmation. Firmware version, split link and config mode still update. A late `DEVICE_INFO` after a timeout stays held while the stale read discards late lines.
- `buildConfigFromSnapshot` (`js/config-model.js`) builds the config: keys (tap, hold, double-tap, own tapping term), layer names, combos (with layer mask), key pairs, key overrides, macros and the settings from `DEVICE_INFO` (`settingsFromDeviceInfo`; a field that the firmware does not send keeps the local value). It validates the result with `validateConfigShape` and returns `{ config }` or `{ error }`.
- A snapshot with a lost or invalid line (`snapshotListsState` is not `complete`), firmware without lists (`absent`), an incomplete matrix or a timeout applies nothing: the app shows a message ("Nichts geändert"). Late lines after a timeout are discarded like in the layout diff.
- With a valid config, the dialog `#syncDiffModal` shows the layout diff against the local config (`diffKeymap`; the button reads "Laden"). After the confirmation, `applyDeviceConfig` replaces the config and calls `markPendingSync` with `snapshot`, `pairs` and `macros`, like an import; "Rückgängig" restores the old config. Like an import, the pending change starts the live sync (`requestLiveSync`) for the connected half, so the device receives the loaded config again. The dialog also lists changed settings (`diffSettings`); a missing `DEVICE_INFO` reply fails the load.
- Not in the device data: macro names (the app names them "Makro <n>"), combo names and labels (built from layer 0), the layout lint state.
- Open hardware check: a read over BLE with 16 combos, 16 key pairs, 16 macros of 32 steps and over USB on both halves.

### Layout practice mode (`js/practice-ui.js`)

- Button `#btnPractice` ("Üben") in the layer bar opens the dialog `#practiceModal`. The user enters a text (up to 500 characters; white space becomes one space) and selects "Start". "Wörter aus der Heatmap" fills the text from the most frequent keys of both halves.
- `findCharPosition(ch, configs, profiles, sideOrder)` in `js/config-model.js` is the pure reverse lookup. It returns `{ char, side, r, c, layer, shift, layerKey, shiftKey }` or `null`. It uses `KEYCODES`, the shifted US characters, `DE_MAC_CHARS` (single codes and key pairs) and prefers the lowest layer, then no Shift. A character on layer n > 0 needs a reachable `MO_n` key (`layerKey`); `TG_n` does not count, because the practice never toggles it off. A shifted character needs a Shift key (`shiftKey`); without one, the character has no position. A Shift key of layer 0 counts on layer n only if its cell there is transparent (`NONE`); `shiftAlternatives` lists every usable Shift key, and each of them is a helper key, not an error.
- `buildPracticeSteps(text, configs, profiles, sideOrder)` returns `{ steps, missing }`. `missing` lists the characters without a key position once; the dialog shows them before the start and skips them.
- `practiceKeyPress(session, side, r, c, layer, nowMs)` evaluates one key press and returns `correct`, `error`, `helper` (the layer or Shift key of the step) or `ignored`. An error counts on the expected key (`session.errors`). A press on the right key on the wrong layer is an error; an unknown layer is accepted. A helper key counts only on another layer than the target layer, so a target at the position of the layer key stays the target.
- While a session runs, the dialog discards hardware key events outside the text field and the close buttons (`practiceSwallowKey`), so the keyboard cannot trigger "Start" again. `practiceSpeed(session)` returns WPM (5 characters = 1 word, from the first key to the last correct character), the accuracy in percent and the elapsed time.
- `handleSerialLine` (`js/serial.js`) calls `practiceHandleKeyPress` for `KEY_PRESS` and `SPLIT_KEY`. A press counts only while the dialog is open and a session runs. `SPLIT_KEY` (left half through the master) needs USB; `KEY_PRESS` also arrives over BLE.
- The dialog marks the next key on the matrix of the correct half and the layer (`.practice-target`) and names the layer key and the Shift key.
- Button `#btnPracticeWeak` ("Schwache Tasten üben") fills the text with `practiceDrillText(sources, fallback)` (`js/config-model.js`, `sources` = `[{ config, stats }]` per half). The text uses the keys of `topCorrectedKeys` (see "Backspace correction heatmap") that have a character on layer 0 (`practiceCharForKeyId`). The key with the highest correction share appears most often (rank weight steps of `DRILL_RANK_STEP`, groups of three characters). The top `DRILL_PAIR_LIMIT` same-finger pairs (`topSameFingerPairs`) follow as words `ab ba`. Keys without a position or character on the active layout are skipped. The statistics count per position, not per layer, so the drill uses the layer 0 character of that position. The key words are cut as whole words so that the pair words keep their place within the limit. The text is deterministic and has at most `PRACTICE_MAX_CHARS` characters. Without weak keys the function returns `PRACTICE_FIXED_TEXT` and the UI shows a toast.

### Action search across both halves (`findActionUsages`, `js/editor.js`)

- The search field "Aktion suchen" (`#actionSearchPanel` above the layer overview) reuses the keycode search: the input `data-filter-for="actionSearchSelect"` filters the select `#actionSearchSelect` with `applySelectFilter`. The select lists all actions of `KEYCODES`.
- `findActionUsages(config, code, side)` in `js/config-model.js` is a pure function. It returns one hit per use: `key` (`layer`, `r`, `c`, `slot` = `tap`, `hold` or `dtap`), `combo`, `pair` (`member` = `first` or `second`), `override` (`role` = `key` or `replacement`) and `macro` (`macro`, `step`, `type`). `side` is copied into each hit. `findActionUsagesForSides(configs, code, sides)` joins the hits of several halves.
- Old configs store modifier actions of hold and double-tap as `MOD_*`; `findActionUsages` compares them through `normalizeHoldCode`, so a search for `KEY_LEFT_SHIFT` finds `MOD_LSHIFT`.
- The select also offers the characters that need a key pair (`CHAR_PAIR_<i>`). `findActionUsagesForSides` resolves such a code per half to each stored equal pair `PAIR_<n>` and searches that code. A half without the pair gives no hit.
- `renderActionSearch` runs after each `renderMatrix` and `renderCombosTable`. It skips the rebuild when the code and the hit texts stay equal, so the focus on a clicked hit stays. Macro hits show the German step label (`MACRO_STEP_LABELS`).
- Transparent keys (`NONE`, empty or `0`) never count, and the codes `NONE`, `""` and `0` give no hit. Macro pauses carry no code and never count.
- `renderActionSearch` lists the hits of all halves (`Dactyl.sidesInDisplayOrder()`, configs through `configFor`). A click on a key hit calls `gotoActionUsage`: it selects the half (`switchEditSide`), the layer and the key (`selectKey`). A hit without a key (combo, pair, override, macro) selects only the half. No side literal in the UI code.

### On-screen keyboard picker (`openOnScreenPickerForSelect`, `js/editor.js`)

- Action select elements feature a dedicated picker trigger button (`🎹`, `.action-picker-trigger`).
- Clicking the trigger opens the dialog `#onScreenPickerModal` with the on-screen keyboard.
- The picker displays five tabs: `Tastatur`, `Navigation & Numpad`, `Umlaute & Modifiers`, `Ebenen`, and `Media & Maus`.
- Each on-screen key displays its label and key code. Key widths match physical keyboard dimensions (`1.25U`, `1.5U`, `1.75U`, `2U`, `2.25U`, `6.25U`).
- The picker highlights the active key of the target select with `.active`.
- Clicking an on-screen key calls `pickActionFromOnScreenKey(selectEl, codeHex)`.
- The function clears any active search filter on the target select via `clearSelectFilter`.
- It sets `selectEl.value`, clears filter block flags, and dispatches the `change` event.
- Existing event handlers process the change immediately.
- The picker also supports dynamic macro step selects (`.macro-step-code`) in `js/macros-ui.js`.
